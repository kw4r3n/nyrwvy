# Mini Work Planner

A tool, created and maintained with a Nyrwvy maintained AuthoringSession, that decides the next action for a single work item.

The semantic source is `planner.snapshot.json`. The CLI does not interpret the snapshot directly; it is only an adapter that calls C# generated from the public `declarations` and `emitCSharp.symbols`.

## Decision model

Inputs:

- `PrerequisiteState = Ready | Waiting | Failed`
- `ExecutionState = NotStarted | Running | Failed | TimedOut | Succeeded`
- `ValidationState = NotRequired | Pending | Passed | Failed`
- `attempts: Int64`
- `maxAttempts: Int64`

Outputs:

- `start`
- `wait`
- `retry`
- `validate`
- `complete`
- `needs-human`

In the maintained policy, if execution has succeeded but validation is Failed, the result is `retry` while retry budget remains and `needs-human` otherwise. In addition, `TimedOut` uses the same retry policy as `Failed`: `retry` if budget remains, `needs-human` otherwise.

## Running

From the repository root:

```sh
dotnet run --project mini-work-planner/runner -- Ready Failed Pending 1 3
```

Output:

```text
retry
```

Examples:

```sh
dotnet run --project mini-work-planner/runner -- Waiting NotStarted NotRequired 0 0
# wait

dotnet run --project mini-work-planner/runner -- Ready Succeeded Failed 0 1
# retry

dotnet run --project mini-work-planner/runner -- Ready Succeeded Failed 1 1
# needs-human

dotnet run --project mini-work-planner/runner -- Ready TimedOut Pending 0 1
# retry

dotnet run --project mini-work-planner/runner -- Ready TimedOut Pending 1 1
# needs-human
```

Input names are case-insensitive.

## Small policy check

```sh
dotnet run --project mini-work-planner/runner -- --test
```

This checks only a small matrix that covers each state branch and the retry boundary.

## Materializing from a successful snapshot

From a `workspace.json` generated by a maintained AuthoringSession, such as the successful run of #179:

```sh
python3 mini-work-planner/materialize.py /path/to/workspace.json
```

This process does not read the snapshot's JSON directly as the semantic authority. It:

1. copies the snapshot bytes to `planner.snapshot.json`
2. opens it with a maintained AuthoringSession
3. obtains the public `declarations` / `executionReadiness` / `emitCSharp`
4. generates the runner from the symbol manifest
5. runs the small policy matrix

The outputs are `declarations.json` and everything under `runner/`.

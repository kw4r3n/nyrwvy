# Mini Work Planner

A tool, created and maintained with a Nyrwvy maintained AuthoringSession, that decides the next action for a single work item.

The semantic source is `planner.snapshot.json`. The CLI does not interpret the snapshot directly; it is only an adapter that calls C# generated from the public `declarations` and `emitCSharp.symbols`.

## Schema

`planner.snapshot.json` was first written at snapshot schema 9. On 2026-10-19 it was rewritten in place to the current schema 21 by `Nyrwvy.AuthoringSession migrate --snapshot examples/mini-work-planner/planner.snapshot.json` ([snapshot migration](../../docs/specs/agent-authoring-session.md#snapshot-migration)); `planner.migration.json` is the command's report, which shows a representation-only migration with both fingerprints unchanged. `declarations.json` and `runner/Generated.cs` were then re-materialized from the migrated snapshot with `materialize.py` (below), which also reran the policy check.

## Decision model

Inputs:

- `PrerequisiteState = Ready | Waiting | Failed`
- `ExecutionState = NotStarted | Running | Failed | TimedOut | Succeeded`
- `ValidationState = NotRequired | Pending | Passed | Failed`
- `attempts: Int64`
- `maxAttempts: Int64`

Outputs:

- `start`
- `wait`
- `retry`
- `validate`
- `complete`
- `needs-human`

In the maintained policy, if execution has succeeded but validation is Failed, the result is `retry` while retry budget remains and `needs-human` otherwise. In addition, `TimedOut` uses the same retry policy as `Failed`: `retry` if budget remains, `needs-human` otherwise.

## Running

From the repository root:

```sh
dotnet run --project examples/mini-work-planner/runner -- Ready Failed Pending 1 3
```

Output:

```text
retry
```

Examples:

```sh
dotnet run --project examples/mini-work-planner/runner -- Waiting NotStarted NotRequired 0 0
# wait

dotnet run --project examples/mini-work-planner/runner -- Ready Succeeded Failed 0 1
# retry

dotnet run --project examples/mini-work-planner/runner -- Ready Succeeded Failed 1 1
# needs-human

dotnet run --project examples/mini-work-planner/runner -- Ready TimedOut Pending 0 1
# retry

dotnet run --project examples/mini-work-planner/runner -- Ready TimedOut Pending 1 1
# needs-human
```

Input names are case-insensitive.

## Small policy check

```sh
dotnet run --project examples/mini-work-planner/runner -- --test
```

This checks only a small matrix that covers each state branch and the retry boundary.

## Materializing from a successful snapshot

From a `workspace.json` generated by a maintained AuthoringSession, such as the one the authoring probe produced:

```sh
python3 examples/mini-work-planner/materialize.py /path/to/workspace.json
```

The script uses only public AuthoringSession operations (`declarations`, `executionReadiness`, `emitCSharp`); it does not author the program and does not read the snapshot's JSON as the semantic authority. It:

1. copies the snapshot bytes to `planner.snapshot.json`
2. opens it with a maintained AuthoringSession
3. obtains the public `declarations` / `executionReadiness` / `emitCSharp`
4. generates the runner from the symbol manifest
5. runs the small policy matrix

The outputs are `declarations.json` and everything under `runner/`.

## Provenance

The initial program and the maintenance change were created in the bounded authoring probe recorded in [the experiment note](../../docs/experiments/mini-work-planner-authoring.md) (issue #179). The run's raw artifacts (events, metrics, final state) are in a private artifact root outside the repository; the committed `planner.snapshot.json`, `declarations.json` and `runner/` are what the repository keeps of it. The successful run committed 5 types, 3 functions, and 1 whole-body maintenance change, confirmed identity continuity, execution readiness, and the C# symbol manifest after a restart, and had 0 rejected maintained requests.

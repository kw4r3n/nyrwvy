# Nyason v0 — design constraints and current evidence — 2026-08-25

## Status

**Implemented prototype and mechanically verified candidate. Not yet the canonical persistence format.**

Nyason is a NyamNyam-specific, JSON-like semantic encoding. It is intentionally narrow: it is not a general-purpose JSON replacement and is not a human-authored source language.

The strict JSON codec remains the reference/debug baseline while Q-001 is open. The full Nyason experiment and measured comparison are recorded in [Phase G / Nyason v0](rebuild-phase-g-nyason-20260825.md).

## Primary goal

Nyason is useful only if a dedicated format improves the reliability of AI reading and editing NyamNyam semantic data enough to justify its additional implementation and context cost.

Priority order:

1. minimize AI semantic misreading and incorrect edits;
2. make invalid structure fail early and precisely;
3. preserve local self-description when slices are retrieved independently;
4. keep semantic roles structurally distinct;
5. preserve exactly one authoritative semantic fact;
6. support deterministic canonical encoding and exact schema identification;
7. reduce token and transport cost where doing so does not weaken the previous properties;
8. remain reasonably inspectable by humans for debugging.

Human source-authoring elegance and minimum character count are explicitly not primary requirements.

## Architectural boundary

Nyason is an encoding of the semantic graph. It is not the semantic model.

```text
Persistent semantic graph model
        |
        +-- Nyason encoder/decoder      experimental persistence/transport codec
        +-- strict JSON codec           reference/debug/benchmark codec
        +-- focused AI projections      future query results and semantic slices
        +-- viewer projections          human review
```

No validator, semantic operation, query, lowering pass, or backend may derive program meaning from Nyason-specific spelling or layout. A decoded Nyason document must become the same typed semantic graph that other codecs produce.

## v0 non-goals

Nyason v0 does not provide:

- a general configuration language;
- arbitrary user-defined schemas;
- macros or preprocessing;
- anchors, aliases, includes, or textual reference expansion;
- implicit type conversion;
- a general numeric tower;
- arbitrary map keys;
- executable expressions;
- best-effort parsing or silent recovery;
- compatibility with JSON, YAML, TOML, or TSON syntax;
- a human-authored NyamNyam source language.

Features are added only when the semantic graph or an AI reliability experiment requires them.

## Syntax model

The prototype syntax layer has only:

- atoms;
- quoted UTF-8 strings;
- booleans;
- lists;
- tagged records with named fields.

Example:

```text
direct-call {
  id = node:node-main-validate-call
  target-function = function:function-validate-user
  arguments = [
    argument {
      target-parameter = parameter:parameter-validate-input
      value = node:node-main-input
    }
  ]
}
```

A tag such as `direct-call` is grammar-visible structure rather than a loosely interpreted value hidden inside a generic object.

## Typed stable IDs

Stable-ID domains are visible in the serialized value and checked by the decoder:

```text
type:...
field:...
variant:...
function:...
parameter:...
pattern-binding:...
node:...
effect:...
capability:...
capability-operation:...
capability-parameter:...
obligation:...
snapshot:...
transaction:...
```

A field requiring `FunctionId` rejects `node:...` before graph validation. The opaque payload is percent-escaped for transport and restored exactly.

The production ID allocation policy remains Q-002 and is independent from the textual domain prefix.

## Explicit alternatives and local completeness

A retrieved Nyason construct should remain understandable without a distant header or positional convention.

Therefore v0 avoids representations where:

- field names are declared once in a remote table header;
- serialized position changes semantic role;
- aliases require following unrelated text;
- display names substitute for identity;
- the same semantic fact is repeated in a second authoritative table.

Directly referenced declarations may still be required to understand the referenced entity; the format does not copy whole declarations into every use.

## Option and Result shapes

Nyason deliberately narrows the internal generic representation:

```text
option-type {
  item = ...
}
```

```text
result-type {
  ok = ...
  error = ...
}
```

This prevents invalid Option/Result arity from being representable in Nyason, while the decoder still produces the existing semantic `TypeRef`.

## Closed records

Records and alternatives are closed by default:

- required fields are required;
- unknown fields are errors;
- duplicate fields are errors;
- no ignored extension fields exist;
- no implicit coercion is attempted.

Forward evolution uses a new explicit schema identity rather than silently accepting unknown structure.

## Explicit redundancy versus duplicate authority

Nyason may retain syntactic redundancy when it reduces AI ambiguity and the decoder can enforce consistency.

Acceptable:

- a tagged construct plus named fields;
- typed stable-ID prefixes checked against the expected semantic ID domain.

Not acceptable:

- a DirectCall node plus a separate authoritative call table;
- a variant ID plus an independently editable owner type when owner type is uniquely derivable;
- derived reverse-reference indexes serialized as authoritative facts.

## Schema identity

The current prototype declares:

```text
nayamnyam.snapshot.v0
```

The decoder requires an exact match.

A schema content hash is deferred. No separate authoritative schema artifact currently exists whose hash could be referenced without creating a second source of truth. A manually synchronized or decorative hash would provide false confidence.

## Canonicalization

Canonical output is deterministic for a given semantic snapshot and Nyason profile.

Current rules:

- nonsemantic entity collections sort by stable ID;
- graph nodes sort by stable ID;
- argument and field associations sort by target stable ID;
- union arms sort by variant ID;
- required effects sort by effect ID;
- function parameter order is preserved;
- ordered type arguments retain semantic order;
- display/layout position is never semantic identity.

A test verifies that reordering nonsemantic top-level collections does not change canonical Nyason output.

## AI edit model

Normal agents should still prefer semantic operations over raw Nyason mutation.

Raw Nyason editing is mainly intended for:

- migrations;
- recovery;
- fixture generation;
- codec testing;
- low-level debugging;
- controlled experiments comparing structured editing reliability.

A more AI-readable persistence encoding does not replace the accepted semantic-operation boundary.

## Verified mechanical properties

The prototype has compile-backed tests for:

- complete Milestone 0 graph canonical round-trip;
- nonsemantic collection-order independence;
- exact schema-ID enforcement;
- unknown-field rejection;
- duplicate-field rejection during parsing;
- wrong stable-ID domain rejection before semantic validation;
- malformed syntax rejection without recovery;
- exact percent-escaped stable-ID round-trip;
- coexistence with the corrected Milestone 0 rename/signature/obligation tests.

The latest validation run used .NET SDK `10.0.400`, built with zero warnings and zero errors, and passed all **42 tests**.

## Current JSON comparison

For the complete representative Milestone 0 snapshot:

```text
strict compact JSON:  8,440 UTF-8 bytes
Nyason v0:            16,205 UTF-8 bytes
Nyason / JSON:        1.920
```

Nyason is therefore roughly 92% larger for the current full-snapshot pretty/self-describing encoding.

This is a meaningful cost. It does not by itself outweigh the mechanical clarity benefits, but it prevents promotion to canonical persistence based on the current evidence alone.

## Decision gate

Nyason should not become canonical merely because it is project-specific or mechanically stricter than JSON.

Before Q-001 is resolved, compare JSON and Nyason on AI-oriented tasks such as:

1. identifying node role, type, target, ownership, and effect from a bounded slice;
2. detecting deliberately wrong ID domains;
3. repairing missing or incorrect fields without unrelated changes;
4. updating direct-call arguments by stable parameter identity;
5. reasoning about Result and exhaustive union branches;
6. full-snapshot versus focused-slice context cost;
7. a less whitespace-heavy Nyason transport projection, if it preserves comprehension reliability.

The deciding metric is semantic comprehension/edit reliability at acceptable context cost, not minimum bytes or tokens.

## Current conclusion

> **Nyason v0 passes the mechanical encoding gate and remains a serious candidate. Q-001 stays open.**

Typed Semantic IR work does not depend on this decision and should consume validated semantic graph facts directly rather than either serialized encoding.

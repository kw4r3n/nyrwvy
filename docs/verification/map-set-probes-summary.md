The rrawrlet porting probes have their own [summary](rrawrlet-slice-probes-summary.md).

## What these probes are

Orders 44-47 added `Map<K, V>` and `Set<T>` ahead of probe evidence. Probes 21-24 used them in ordinary code: word counts with a top-k report, and a dependency planner that each probe authored again on the orders the previous probe led to and then extended. Each was compared case by case with a JavaScript reference over a seeded corpus. The method in every probe: the session server built with `dotnet build tools/Nyrwvy.AuthoringSession --configuration Release`; a Node client over the maintained `createGraphTools` handlers (the same path as the [function-abort example](../../examples/function-abort/README.md)); `simulateCreateTypesByName`, `create_function` (`nyrwvy_create_function`) with name-resolved recipes, `commit`, and one `runPureByName` per case. Map and Set values crossed the `runPure` boundary directly as `map` and `set` run values, in arguments and expectations, with no workaround. Node counts are the `nodeCount` of each `create_function` review. The harness, reference, snapshots and transcripts were never committed. Times are warm `runPure` wall time of one call, process start included; from probe 22 on, each scale case ran twice and the second time is shown (the first call of a function in a session also builds it, about 0.2-0.3 s more). A chain of `n` nodes has `n − 1` edges; `chain…`/"built" rows build the input inside the program from `ListRange`, because a run value holds at most 4,096 list items.

### Probe 21 — 2026-10-04

**Baseline:** nyrwvy `eb9748d` (main after #332, clean). The method was new here: the Node client over `createGraphTools` described above.

<a id="probe-21-scope"></a>**Scope.** *Word counts:* `countWords(text): Map<String, Int64>` lowercases, splits on a single space and skips empty words; `topWords(text, k): List<Count>` sorts by count descending, then name ascending, and keeps the first `k`. *Dependency planner:* an `Edge { from, to }` means `from` depends on `to`. `depsOf(edges): Map<String, Set<String>>` gives every node, including nodes that appear only as a dependency, in first-appearance order with duplicate edges removed. `reachable(edges, start): Set<String>` gives the nodes reachable through at least one edge, in breadth-first discovery order. `topoOrder(edges): Result<List<String>, String>` is Kahn's algorithm taking the smallest ready name first; when a cycle is left it returns `Err("cycle: " + the remaining names sorted and comma-joined)`. `dependentCounts(edges): List<Count>` counts each node's direct dependents, zeros included, in the `topWords` order.

**Authored.** 4 types (`Count`, `Edge`, and the loop states `Walk` and `Topo`) and 19 functions, 212 nodes. Word counts: `bump`, `countWords`, `toCount`, `countBefore`, `topWords`, 51 nodes (`MapGet`, `MapInsert`, `MapEmpty`, `MapFold`). Group-by: `addDep`, `depsOf`, 32 nodes (`MapGet`, `MapInsert`, `MapContainsKey`, `SetInsert`, `SetFromList`, `SetEmpty`). Reachability: `expandDep`, `expandNode`, `walkStep`, `reachable`, 46 nodes (`SetContains`, `SetInsert`, `SetToList`, `MapGet`, `MapSize`). Topological order: `nameBefore`, `isReady`, `dropDone`, `topoStep`, `topoOrder`, 64 nodes (`MapFilter`, `MapKeys`, `MapRemove`, `MapFold`, `SetRemove`, `SetSize`). Dependent counts: `zeroAll`, `addDependents`, `dependentCounts`, 19 nodes (`MapFold` twice, `SetToList`; reuses `bump`). Every function was accepted on its first proposal.

**Results.** `countWords` 200/200 (empty, spaces only, mixed case, repeated and empty words); `topWords` 200/200 (`k` from 0 to 4); `topoOrder` 200/200 (empty, a self-loop, a duplicate edge, a 3-cycle with a tail, random DAGs and graphs; 3 cyclic); `reachable` from `a` 200/200; `dependentCounts` 200/200. **1,000/1,000 on the first full run, in 74.5 s.** Nothing blocked.

**Scale.** `topoOrder` on a chain of 50 / 200 / 800: 0.11 / 0.20 / 0.67 s; `reachable` on a chain of 800 from the far end 0.10 s; `dependentCounts` on a chain of 800 0.12 s; `countWords` of 4,000 words, 700 distinct, 0.10 s. `topoOrder` grows about quadratically: each step filters the whole pending map, sorts the ready names to take the smallest, and rebuilds the map to drop the finished name.

**Costs, ranked.** (1) **Counted folds cannot stop early:** `reachable` and `topoOrder` iterate with `ListFold` over `ListRange(0, MapSize(deps))`, the worst-case bound; each needed a state Product (`Walk`, `Topo`) and a step function, keeps running after the frontier is empty or the order is stuck, and `topoStep` passes the state through unchanged on `None`. `ListEffectFold` with a `Result` folder could stop early (as in probe 13) but still needs the bound list and `Err` meaning "done". Rewritten afterwards as self-recursive functions with the loop variables as parameters, the same loops matched the cases with 36 nodes instead of 51 (topological order, no `Topo` type) and 25 instead of 22 (reachability), but bound by the stack. The second ordinary-code observation after probe 15's tail self-call and probe 13's `while`; the subject of the [loop design note](../plans/loops.md) → **order 49** ([tail-self-calls](../decisions/tail-self-calls.md)). (2) **Get-or-default upsert:** every accumulating write is `MapInsert(m, k, MatchOption(MapGet(m, k), f(value), default))`; `bump` is 15 nodes for `m[k] = m.get(k, 0) + 1`, `addDep` 29 nodes for `setdefault(from).add(to)` plus `setdefault(to)`; `MapFromList` indexes and does not accumulate. Candidate `MapGetOrDefault(map, key, default)` (`bump` 13 nodes, `addDep` about 21; each write one expression with no `MatchOption` scope; an update-with-callback form would need a helper at every use site) → **order 48**. (3) **Mapping a map's values:** dropping a finished name from every pending set took a `dropDone` folder (6 nodes) and a `MapFold` rebuilding from `MapEmpty`; candidate `MapMapValues(map, function)` keeping keys and order (first observation) → **order 48**. (4) **Smallest item:** `ListItemAt(ListSortBy(…), 0)`, a full sort for one item each step; candidate `ListMinBy(list, lessThan): Option<T>` (first observation) → **order 48** ([list-sort-and-string-ordering](../decisions/list-sort-and-string-ordering.md)). (5) **Entries as records:** reporting a map needs a record type and a 5-node `toCount` folder (no pair type, no entry list); recorded only. Not needed: `SetFold` (`SetToList` and `ListFold`, 1 extra node, used twice), a Map or Set as a key, Product keys, update-with-callback, merging maps.

<a id="probe-21-candidate-hit-counts"></a>**Candidate hit counts after probe 21.** Map get-or-default: 21 (strong: every accumulating write). Loop with a stop condition (tail self-call as a loop, `while`, `IndexFold`): 13 (`while`), 15 (tail self-call), 21 (two counted folds). Mapping map values: 21. Smallest item of a list: 21.

The tail self-calls held: `reachLoop` ran 300,000 turns and `dfsLoop` 20,000 turns with a stack 20,000 frames deep, with no stack overflow in any run. Time is unchanged from probe 21 where the algorithm is unchanged. The topological order is still about quadratic (each turn filters the pending map and maps every pending set; this naive Kahn's form was chosen to match probe 21, and in-degree counts with a dependents map would make it linear without a language change). Reachability is linear. The cycle path grows quadratically (10,000 to 20,000 turns takes 4.5 times as long), consistent with the slice and append copying the stack each turn.

**Costs, ranked.** (1) **An explicit stack is long and quadratic:** `dfsLoop` is 117 nodes, 28% of the program; peek, pop and replace-top are `ListItemAt(stack, ListLength(stack) − 1)`, `ListSlice(stack, 0, ListLength(stack) − 1)` and `ListAppendItem` of a `ProductUpdate`, the slice and append each copying; 20,000 frames take 1.95 s and 40,000 exceed the limit. The body nests two `MatchOption`s and two `Bind`s with shifting positional references (the harness needed a comment per level, though every function was accepted first time). The natural recursive `visit(node)` is not a tail call, so order 49 does not make it a loop (stack-bound at a few thousand frames). Candidates: a last-item access, or a list whose append and drop-last do not copy (first observation) → **order 50** ([list-last-and-drop-last](../decisions/list-last-and-drop-last.md)). (2) **Finding an item's position:** taking the stack from `w` to the top needed `collectFrom` (16 nodes), a fold that starts collecting at the first frame equal to `w`; candidate `ListFindIndex` or `ListIndexOf` (first observation) → **order 51** ([list-index](../decisions/list-index.md)). (3) **Removing several keys:** `MapFilter` with a 4-node `notIn` callback, then `MapMapValues` and `SetDifference` (3 more nodes); recorded only. Not needed: a loop construct, `IndexFold`, mutual recursion, `SetFold`, a pair type. No self-call had to be rearranged into tail position, and the [decision](../decisions/tail-self-calls.md)'s trap (a wrapped call such as `ResultOk(loop(…))`) did not arise; the review does not mark tail calls, but nothing was misread, so neither of the decision's revisit conditions is met.

### Probe 23 — 2026-10-05

**Baseline:** nyrwvy `4ed78e8` (main after #340, clean); corpus seed 23, so the graphs differ from probe 22's.

<a id="probe-23-scope"></a>**Scope.** [Probe 22's scope](#probe-22-scope) unchanged, with `findCycle` rewritten on orders 50 (`ListLast`, `ListDropLast`) and 51 (`ListIndexOf`, `ListFindIndex`), plus two additions. *Linear topological order:* `kahnOrder(edges)` gives `topoOrder`'s result (smallest ready name first, the same `Err` on a cycle) from in-degree counts and a dependents map, decrementing the chosen name's dependents and adding those that reach zero to a ready set. *Components:* `components(edges): List<List<String>>` is Tarjan's algorithm, iterative (roots in first-appearance order, dependencies in insertion order, components in closing order, each sorted), with two stacks, index, low-link and next-dependency maps and an on-stack set, all as parameters of one tail-recursive `tarjanLoop`. The reference was checked against mutual reachability on all 200 graphs.

**Authored.** 3 types and 54 functions, 801 nodes in all, including 119 nodes of scale wrappers that build chains and combs in the program; `Frame` was declared and left unused. Every function was accepted on its first proposal. Probe 21's scope 175 nodes (unchanged); levels 43 (unchanged). Cycle path `cyclePath`, `dfsLoop`, `findCycle` 128 nodes (probe 22: 145 with `frameNode` and `collectFrom`): the stack holds names and each node's next index lives in a `Map`, so neither `Frame` nor `ProductUpdate` is used; `ListLast` peeks and `ListDropLast` pops; `dfsLoop` 105 nodes (was 117), since the map read and write cost most of what the frame removed; `cyclePath` (12) is `ListIndexOf` and a `ListSlice`, replacing the 16-node `collectFrom`. Linear Kahn (new): `depCount`, `noDependents`, `addDependent`, `addDependents2`, `isZero`, `isPositive`, `isZeroIn`, `decrement`, `kahnLoop`, `kahnOrder`, 100 nodes, twice the naive form's 45; seven of the ten are one-expression callbacks (33 nodes); a turn needs the new counts and the newly ready names, obtained by a fold returning the counts and a `ListFilter` reading them back, so no pair type was needed. Components (new): `lowerParent`, `tarjanLoop`, `components`, 236 nodes, `tarjanLoop` alone 208; `ListIndexOf` finds the component's start and two `ListSlice`s split it.

**Results.** `countWords`, `topWords`, `topoOrder` (71 cyclic), `reachable`, `dependentCounts`, `levels`, `findCycle`, `kahnOrder`, `components`: 200/200 each. **1,800/1,800 on the first full run, in 174.9 s.** Nothing blocked.

**Scale.** A chain's DFS is shallow (its first root `n1` depends only on `n0`); a closed chain adds `n0 → n(n−1)` so the search goes the whole length; a comb is a closed chain whose every `n(i)` depends first on a leaf `l(i)` and then on `n(i−1)`, so every push follows a pop.

\* From the isolation session below. Building a comb is not the cost: in a second session on a copy of the snapshot, building a 40,000-node comb took 0.13 s and its dependency map 0.52 s, while the search from 10,000 to 20,000 nodes took 2.7 times as long and 40,000 exceeded the limit; on the closed chain, where only pushes follow pushes, the same search is linear. This is the known limit the [order 50 decision](../decisions/list-last-and-drop-last.md) recorded (0.80 s and 2.4 s at 10,000 and 20,000), now measured past the run limit. The components loop is quadratic on the comb for more than one reason, which the probe did not separate: the call stack pushes after a pop; every leaf becomes a one-name component, so `ListIndexOf` scans the component stack from the front to find it at the top; and the component stack is truncated with `ListSlice` and pushed onto again. The linear Kahn's algorithm confirms probe 22's claim: 100,000 names in 1.8 s against 4,000 over the limit for the naive form, with no language change. Tail self-calls held throughout.

**Costs, ranked.** (1) **A push after a pop copies the stack:** the cycle path of a 40,000-node comb and the components of a 20,000-node comb exceed the 5 s limit, while a closed chain of 300,000 does not; the input is constructed but its shape (a node with a leaf dependency before a deep one) is ordinary. The [order 50 decision's revisit condition](../decisions/list-last-and-drop-last.md#revisit-conditions) is met by a constructed input, which the owner counted (an input whose shape could occur in a real program) → **order 52**, the persistent-vector list of the [design note](../plans/list-stack-operations.md) ([decision](../decisions/persistent-vector-list.md)); the components also needed the component start found without scanning from the front → **order 53** ([decision](../decisions/list-last-index-and-set-difference.md)). Second observation of the stack. (2) **Loop state threaded through every self-call:** `tarjanLoop` has 10 parameters and 7 self-calls; 47 of its 70 arguments pass a parameter through unchanged, about 23% of its 208 nodes; `dfsLoop` passes 20 of 30 through. The harness hid this with a JavaScript helper spreading unchanged arguments, which a recipe cannot do; scope depths still needed a comment per level. Candidates: a recipe shorthand for a self-call naming only the changed arguments, or a state Product with `ProductUpdate` (first observation) → **order 54** ([self-call-keep-unlisted](../decisions/self-call-keep-unlisted.md)). (3) **One-expression callbacks:** seven in the linear Kahn's algorithm (1 to 9 nodes), each a declared function; Map callbacks take the key even when they ignore it; recorded with probe 22's `zeroFor` and `notIn`. (4) **An `Option` that cannot be `None`:** `ListIndexOf(scc, top)` runs only when `top` is on the component stack, but its `None` arm still needs a body; recorded only. Not needed: a loop construct, mutual recursion, a pair type, `ListFindIndex` (`ListIndexOf` covered both uses), `ListLast` other than on the stack top. Every self-call was again in tail position without rearranging.

<a id="probe-23-loop-state-product"></a>**Follow-up: loop state in a Product.** After orders 52 and 53, cost 2's untried alternative was authored in the same session: `tarjanLoop2(deps, roots, root, state)` keeps the seven changing values in a `Tarjan` Product, reads them with `FieldAccess` and passes `ProductUpdate(state, changed fields)` to each self-call. It was accepted first time, matched `components` on all 200 graphs, and ran the comb of 10,000 / 20,000 / 40,000 in 0.67 / 0.97 / 1.73 s, the same as the parameter form. It is **236 nodes instead of 208** (+13%): each self-call names only changed fields, removing the 47 pass-through arguments, but every state read becomes a two-node `FieldAccess` instead of a one-node `Parameter`, the loop reads the state more often than it passes it through, and the type adds a declaration; positional scope references are unchanged. So `ProductUpdate` does not cover cost 2, and a self-call naming only the changed arguments, expanding to the full `DirectCall`, would remove the 47 nodes (about 23%) without the reads' cost.

<a id="probe-23-candidate-hit-counts"></a>**Candidate hit counts after probe 23.** Last item / non-copying stack operations: 22; **done as order 50**, used here by both searches; non-copying push after pop (persistent vector): 22, 23, over the run limit on a comb. Position of an item in a list: 22; **done as order 51**, used twice here; searching from the end: 23. Self-call naming only the changed arguments: 23 (a state Product with `ProductUpdate` was 13% larger, not smaller).

### Probe 24 — 2026-10-05

**Baseline:** nyrwvy `2e7b8db` (main after #346, clean); corpus seed 24. Unlike probe 23's harness, every self-call recipe names only the arguments it changes and sets `keepUnlisted`, as an author would write it.

<a id="probe-24-scope"></a>**Scope.** [Probe 23's scope](#probe-23-scope) unchanged, on orders 52 (persistent-vector list), 53 (`ListLastIndexOf`, smaller-side `SetDifference`) and 54 (`keepUnlisted`), plus two additions. *Shortest dependency path:* `shortestPath(edges, from, to): Option<List<String>>`, a breadth-first search over dependencies in insertion order with a queue of names dequeued with `ListSlice(queue, 1, length)` and extended with `ListConcat`, and a parent map that also marks visited names; `walkBack` follows the parents from `to` and the path is reversed; `None` when `to` is not reached, `[from]` when they are equal. *Project length:* `projectLength(tasks: List<Task>, edges): Result<Int64, String>` with `Task { name, days }`: the names are ordered with probe 23's `kahnOrder` (its `Err` passes through), then folded into a finish map where a name finishes its own days (0 when no task names it) after the latest finish of its dependencies; the result is the largest finish or task duration, 0 for nothing.

**Authored.** 4 types and 71 functions, 998 nodes in all, including 183 nodes of scale wrappers; `Frame` again declared and unused. **Costs, ranked.** (1) **A breadth-first queue copies itself on every dequeue:** the shortest path and probe 21's `reachable`, unchanged for three probes, exceed the 5 s limit on a fan of 40,000 and are quadratic from 10,000 (0.65 s) to 20,000 (2.58 s); `reachable` passed every chain case only because a chain's queue holds one name. The input is constructed but its shape (one name with many dependencies) is ordinary. The [order 52 decision's revisit condition](../decisions/persistent-vector-list.md#revisit-conditions) for a breadth-first queue is met by a constructed input. Options: a non-copying front removal on the persistent vector, a queue type, or documenting the two-stack idiom (+9 nodes, linear) (first observation) → **order 55**, option (1), a slice from any start shares structure ([list-slice-sharing](../decisions/list-slice-sharing.md)). (2) **One-expression callbacks:** 5 of the 10 new functions are callbacks of 3 to 6 nodes (`notParented`, `setParent`, `addTask`, `laterFinish`, `maxOf`: 23 nodes; `maxOf` only wraps `int64Max` for a `ListFold`); third probe in a row (22, 23, 24); none proposed. (3) **An `Option` that cannot be `None`:** `walkBack` reads a parent that always exists on the path, but `mapGet`'s `None` arm still needs a body; second observation (23); recorded only. Not needed: a loop construct, mutual recursion, a pair type, a `ListMax` (one fold), a separate visited set (the parent map is one); `keepUnlisted` covered every pass-through argument and no new loop needed more than four parameters.

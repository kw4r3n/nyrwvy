## What these probes are

Each probe re-authored a slice of **rrawrlet**, a separate Python application by the same author (an OpenCode-based agent-team tool), in Nyrwvy through the maintained `Nyrwvy.AuthoringSession` JSON-lines protocol, by name only, and compared its outputs case by case with the real Python functions (the oracle). The probe scripts (`author.py`, `mkcases.py`, oracles, session clients) and the raw case files were never part of this repository and are private, as is rrawrlet itself. Each row below states what was observed at the recorded Nyrwvy and rrawrlet commits; a reader can verify the language changes the probes motivated through the linked decisions, specs and tests, but cannot rerun the comparison.

Unless a row says otherwise, the method was: name-resolved `simulate*ByName` requests, `commit` and `runPureByName` (no `declarations` call from probe 3 on); the session server built with `dotnet build tools/Nyrwvy.AuthoringSession --configuration Release`; a case matches when its output and the ordered list of host or fake calls with their arguments are equal. From probe 10 on, cases ran in `runPure` batches through a `runCases` entry (up to 40 per run). "Order N" is the numbered entry of the [implementation queue](../plans/post-m2-roadmap.md#immediate-execution-queue) a finding became.

### Re-probe — 2026-09-28

**Baseline:** nyrwvy `70995fa` (main after #225 Bool operators); rrawrlet `903f2ce`. `preview`, `usage_is_complete` and `summarize` were unchanged since the 2026-09-25 probe's `d02990a` (identical AST). Python 3.14.7 ran the real functions, extracted read-only from `rrawrlet/team.py`. It re-ran the [2026-09-25 slice](../plans/post-m2-roadmap.md#queue-from-the-2026-09-25-probe) after queue orders 1-5 using `simulate*ByName`, `commit`, `declarations` and `runPureByName` only; no exact-ID authoring request was needed, and the driver looked up no names or IDs.

**Authored.** Data (`usage_is_complete`, `summarize`, `preview`): 3 types (`UsageEntry`, `Attempt`, `Summary`), 12 functions (+1 body replacement), 33 requests / 17.4 KB, ~199 nodes. Leader skeleton: 7 types, 1 effect, 4 capabilities (`Leader`, `Workspaces`, `Agent`, `Repo`), 16 functions (+1 body replacement), 58 requests / 44.4 KB, ~379 nodes. Only 3 data functions and 4 skeleton functions (`memberBody`, `memberWorker`, `teamLoop`, `runTeam`) carry rrawrlet logic; the rest were workarounds. The skeleton follows the [concurrency decision's sketch](../decisions/concurrency-control.md#sketch-rrawrlets-team-as-one-loop): `runTeam` opens a `TaskScope`; `teamLoop` calls `Leader.next(turn, report)` and matches `Action = Spawn | Wait{members, all, limitMillis} | Stop | Integrate | Finish`; `Spawn` is `TaskStart` of `memberWorker` (`UseResource(Workspaces.create/remove)` around `Agent.run`, `CancellationRequested` mapped to `Stopped`); `Wait` is `TaskWait` any/all with an `Option<Int64>` limit; `Stop` is `TaskCancel` then a wait; `Integrate` is a zero-limit wait then `Repo.integrate`; a turn budget returns `Err`. Bool operators replaced every Python `and`/`or`/`not`.

**Results.** 26/26 against Python: `summarize` 6/6 (spawn count, `usage_complete`, `reported_usage` compared as maps), `usage_is_complete` 11/11, `preview` 9/9 including Python's `text[-0:]` and negative floor division. `reported_usage` key order differs (first appearance vs set iteration), which is not semantic. Skeleton: 6/6 as expected and identical on two full re-authoring runs. S1 any-wait selected the faster member (`running;done:m2:c2;`, 2/2 workspaces removed); S2 timed wait expired and stop from outside (`running;` → `stopped:m1;`, integrating m1 refused); S3 member failure with reversed start order failed only m1 (argument-keyed `cases`); S4 finish while members run (zero-limit integrate reports "still running", an unknown id is an error, the scope cancels and awaits both); S5 turn budget `Err("turn budget reached")` with the member cancelled and released; S6 a member host exception fails the whole run with `RunRuntimeFailure` (`FakeCapabilityException`), where rrawrlet records `failed` (expected, by design). A `runPureByName` run took ~1.8-2.2 s, mostly build; 58 authoring requests ~2 s.

**Frictions, ranked.** (1) The 64-node recipe limit: the one-body loop was ~204 nodes and failed with `StructuralRecipeNodeLimitExceeded`; the split needed 2 bundling Products (`Crew`, `LoopState`) and 5 helpers, `onWait` (42) and `teamLoop` (48) stayed near the limit, and the error gave no count or largest subtree (→ order 6). (2) Keyed lookup of task handles: `Task` could not be stored in declared types and there was no list indexing, so selecting a member took parallel lists, an `IndexSearch` type and 4 functions (`indexStep`, `pick`, `select`, `selectInto`) with an "Err means found" `ListEffectFold`; this met the Map revisit condition (→ order 8). (3) No Int64 division: floor-halving for `preview` took 4 helpers (~50 nodes), one recursive (→ order 7). (4) Self-recursion needed a placeholder and a body replacement: `ProtocolError: Unknown function 'powersUpTo'.` with no hint (→ order 9). (5) A member's host exception cannot become a member status (by design; capabilities return `Result`). (6) Output in exact IDs only: an ~8-line field ID→name map and an operation ID→name map; `ExpressionCapabilityMissingEffectRequirement` and `TaskTypeInDeclaredType` printed IDs under `…ByName` (→ order 10). (7) Verbose run-value encoding (~20-line encoder; inherent). (8) `TaskWait` mode fixed per node (accepted). (9) Positional `scopeDepth` (depths up to 3 and 4 nested binds, right first time; an off-by-one between same-typed binds would type-check silently; watch). The data part published on the first run apart from the expected self-reference rejection; the skeleton needed one restructure.

**Against the 2026-09-25 costs.** The ~30-line name→ID helper is resolved for authoring and inputs (output side remained, friction 6); nested conditionals for and/or/not resolved; timed Any wait and stopping one member resolved, deterministic on the virtual clock; call-order-only fakes resolved; String preview resolved apart from Int64 division; the Map-like upsert (`UsageEntry` plus `sameKey`, `bumpEntry`, `addUsageEntry`, `addAttemptUsage`) unchanged and deferred, with a second keyed-lookup consumer now present.

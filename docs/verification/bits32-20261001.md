# Bits32 — 2026-10-01

**Status:** Complete. Post-M2 order 30 added the [`Bits32` domain](../decisions/bits32-domain.md): a primitive type of exactly 32 bits and ten total operations (`Bits32FromInt64`, `Bits32ToInt64`, `Bits32Xor`, `Bits32And`, `Bits32Or`, `Bits32Not`, `Bits32Add`, `Bits32RotateRight`, `Bits32ShiftRight`, `Bits32ShiftLeft`). Probe 12's SHA-256 was re-authored by name with it. It matches the NIST vectors, including one million `a`, and hashes about 20 times faster than the Int64 port on the same build. A 17.5 MB input now hashes in one run, where the Int64 port timed out at 2.2 MB.

**Date:** 2026-10-01

Baseline: nyrwvy `6b037db` (main after #271) plus this change. Timings are wall time of one `runPureByName` request to a `Nyrwvy.AuthoringSession` built with `--configuration Release`, three runs each, on the machine probe 12 used. Each includes the per-run build and process start (0.15–0.4 s for a trivial entry).

## What was checked

The fast Core suite covers, in `Bits32Tests`:

- recipe type errors for every operand position (Int64 where Bits32 is expected, a Bits32 amount, a Bits32 result declared as Int64), and wire arity (a missing `right`, an extra field, `left`/`right` on a shift, a `bits32Literal` kind) as protocol errors;
- persisted-graph validation with `Bits32OperandTypeMismatch`, and `ValueEqual` over Bits32;
- all ten kinds through name-resolved authoring, snapshot JSON and Nyason round trips with an unchanged fingerprint, reopen, Typed Semantic IR, Execution IR, the viewer (`Amount` dependency role and labels) and the emitted C# (`uint`, `unchecked((uint)…)`, `BitOperations.RotateRight(…, (int)(amount & 31L))`, the explicit shift bounds);
- malformed Bits32 run values (negative, `4294967296`, `"+1"`, `"0x10"`, `1.5`, null, missing, extra fields, flat `itemKind`) as protocol errors, and a Bits32 passed for an Int64 as `RunArgumentTypeMismatch`.

The Extended suite compiles and runs the emitted code:

- `Bits32FromInt64` then `Bits32ToInt64` of 0, 1, -1, -2, `2^32`, `-2^32`, `2^32 + 5`, `2^32 - 1`, `Int64.MinValue`, `Int64.MaxValue` and `-2^31` gives the value floor-modulo `2^32`.
- `Bits32RotateRight` of `0x80000001` by 0, 1, 31, 32, 33, -1, -31, 64, `2^62 + 1`, `Int64.MinValue` and `Int64.MaxValue`.
- Both shifts of `0x80000001` by -1, 0, 1, 31, 32, 64, `Int64.MinValue` and `Int64.MaxValue`.
- Xor, And, Or, Not and a wrapping Add (`4294967295 + 2 = 1`) through wire run values, with the decimal-string output form, an unsigned `Bits32ToInt64` of `3735928559`, and a mismatch report.
- SHA-256 authored by name through the session (the port below) against the FIPS 180-4 vectors: `""`, `"abc"`, the 448-bit and 896-bit messages, and one million `a` (built in the program by doubling, so the run argument stays small), plus 2-, 3- and 4-byte UTF-8 and the 55-, 56-, 64- and 119-byte padding edges against .NET's SHA-256.

## The port

It keeps probe 12's structure: a fold over the code points feeds 1–4 UTF-8 bytes into a `Sha` state (hash words, current word, pending words, byte count), every 16th word runs `compress`, and padding and the bit length follow. Only the words changed. They are Bits32 instead of Int64 in `[0, 2^32)`, so `bits3`, `op3`, `rotr` and the `mod 2^32` after every addition are gone. The four Σ/σ functions are `Bits32Xor` of `Bits32RotateRight`/`Bits32ShiftRight`, `choose` and `majority` are And/Xor/Not, `feed` packs bytes with `Bits32ShiftLeft` and `Bits32Or`, and hex digits come from `Bits32ShiftRight`, `Bits32And` and `Bits32ToInt64`. The 64 round constants stay an Int64 list, converted with `Bits32FromInt64` where used, and the 8 initial words are `Bits32FromInt64` of literals.

| | Int64 port (probe 12) | Bits32 port |
| --- | --- | --- |
| SHA-256 part | 17 functions, 622 nodes | 17 functions, 547 nodes |
| Bit operations (Σ/σ, choose, majority) | 7 functions, 138 nodes (`bits3` 67) | 6 functions, 63 nodes |
| Round constants | 1 function, 65 nodes | 1 function, 65 nodes |
| Schedule and rounds | 3 functions, 205 nodes | 3 functions, 178 nodes |
| Byte feeding, padding and hex | 6 functions, 214 nodes | 7 functions, 241 nodes |

As in probe 12, the shared helpers `at` (List item or zero, 7 nodes) and `hexd` (one hex digit, 6 nodes) are not counted; with them the port is 19 functions and 560 nodes. Feeding grows by 27 nodes because the hex digits are extracted by a fold over nibble positions (`hexNibble`) instead of probe 12's shared `hex4` helper, and the initial hash words are two nodes each.


## Throughput

The input is a 52-character ASCII line repeated inside the program (probe 12's `scaleHash`), so the argument is small and the time is the digest plus the build. Both ports ran on this build.

| Input | Int64 port | Bits32 port |
| --- | --- | --- |
| 260 KB | 1.8–3.5 s | 0.41–0.49 s |
| 546 KB | 2.0–2.5 s | 0.46–0.54 s |
| 1.09 MB | 3.37–3.42 s | 0.44–0.52 s |
| 2.18 MB | `RunTimeout` (5 s) | 0.59–0.63 s |
| 4.37 MB | — | 0.86–0.92 s |
| 8.74 MB | — | 1.41–1.45 s |
| 17.5 MB | — | 2.40–2.45 s |
| 1,000,000 × `a` (1 MB) | — | 0.53–0.66 s |

Probe 12 recorded 3.84 s for 1.05 MB and a timeout at 2.1 MB for the Int64 port; this build reproduces both (3.4 s, timeout). Beyond the fixed cost the Bits32 digest takes about 0.12 s per MB (about 7.5 µs per 64-byte block) against about 2.5 s per MB (about 0.16 ms per block) for the Int64 port, about 20 times the throughput. Python's `hashlib` takes about 0.6 ms per MB, so the port is now about 200 times slower than `hashlib` rather than about 7,000. *Inference:* most of the remaining cost is the per-byte `feed` call and the List-based schedule and state, not the bit operations.

## Compatibility

No snapshot, Nyason or IR schema version changed. A snapshot without Bits32 keeps its bytes and fingerprint, and the existing suites pass unchanged apart from the recipe-surface inventory test. A reader that predates Bits32 rejects a snapshot that uses it as an unsupported primitive or an unknown node kind.

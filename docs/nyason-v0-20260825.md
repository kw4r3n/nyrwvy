# Nyason v0 design constraints — 2026-08-25

## Status

**Design candidate. Not yet the canonical persistence format.**

Nyason is the working name for a Nayamnyam-specific, JSON-like semantic encoding. The name intentionally reflects its narrow role: it is not intended to become a general-purpose JSON replacement.

The verified Phase B/C JSON codec and the Phase D schema-3 JSON codec remain reference implementations and comparison baselines while Q-001 is open.

## Primary goal

Nyason exists only if a dedicated format measurably improves the reliability of AI reading and editing Nayamnyam semantic data.

Priority order:

1. minimize AI semantic misreading and incorrect edits;
2. make invalid structure fail early and precisely;
3. preserve local self-description when slices are retrieved independently;
4. keep authoritative facts visually and structurally distinct from derived or presentation data;
5. support deterministic canonical encoding and exact schema identification;
6. reduce token and transport cost where doing so does not weaken the previous properties;
7. remain reasonably inspectable by humans for debugging.

Human source-authoring elegance and minimum character count are explicitly not primary requirements.

## Architectural boundary

Nyason is an encoding of the semantic graph. It is not the semantic model.

```text
Persistent semantic graph model
        |
        +-- Nyason encoder/decoder      candidate canonical persistence
        +-- strict JSON codec           reference/debug/benchmark codec
        +-- focused AI projections      query results and semantic slices
        +-- viewer projections          human review
```

No validator, semantic operation, lowering pass, or backend may derive program meaning from Nyason-specific spelling or layout. A decoded Nyason document must become the same typed semantic graph that other codecs produce.

## v0 non-goals

Nyason v0 does not attempt to provide:

- a general configuration language;
- arbitrary user-defined schemas;
- macros or preprocessing;
- anchors, aliases, includes, or textual reference expansion;
- implicit type conversion;
- a general numeric tower;
- arbitrary map keys;
- executable expressions;
- comments unless a concrete debugging need appears;
- compatibility with JSON syntax;
- compatibility with YAML, TOML, or TSON;
- a human-authored Nayamnyam source language.

Features are added only when the semantic graph or an AI reliability experiment requires them.

## Required value forms

The first useful Nyason prototype needs only enough data forms to encode the Milestone 0 graph schema:

- UTF-8 strings;
- booleans;
- small integers for format/schema metadata if still needed;
- typed stable IDs;
- named records;
- lists;
- explicitly tagged alternatives;
- explicit absence where a field is genuinely optional.

Null should not be introduced unless Nayamnyam later needs a semantic distinction between a present null value and an absent field.

## Typed stable IDs

Stable-ID domains should be visible to both the decoder and an AI reader.

Illustrative syntax only:

```text
function:019c...
parameter:019c...
node:019c...
type:019c...
field:019c...
variant:019c...
```

A field whose schema requires `FunctionId` must reject `node:...` before semantic validation. The exact production ID allocator remains Q-002 and is independent from this textual prefix decision.

## Explicit alternatives

A tagged semantic alternative should be distinguishable by grammar/shape rather than by a loosely interpreted string inside an otherwise generic object.

Illustrative syntax:

```text
node direct-call {
    id: node:019c...
    target-function: function:019c...
    arguments: [
        argument {
            target-parameter: parameter:019c...
            value: node:019c...
        }
    ]
}
```

This is intentionally more verbose than a positional encoding. An agent should be able to identify the semantic role of every ID without consulting column position or an earlier header.

## Locality rule

A retrieved Nyason semantic slice should remain understandable without unrelated preceding text.

Therefore v0 should avoid encodings where:

- field names are declared once in a distant table header;
- a later value changes the interpretation of earlier values;
- aliases require searching another document region before a node can be understood;
- serialized position supplies semantic identity or evaluation order.

Locality may include directly referenced declarations supplied with the slice. It does not require copying the full declaration into every reference.

## Explicit redundancy versus duplicate authority

Nyason may retain syntactic redundancy when it reduces AI ambiguity, but it must not create two mutable sources of truth for one semantic fact.

Acceptable examples include:

- an explicit construct tag plus fields whose shape is checked against that tag;
- a typed stable-ID prefix that is checked against the schema-required ID domain.

Unacceptable examples include:

- storing a call once as a graph node and again in a separate call table;
- storing both a variant ID and an independently editable owner-type ID when the owner is uniquely derivable from the variant;
- storing derived reverse-reference indexes as if they were authoritative graph facts.

## Closed shapes

Records and alternatives are closed by default:

- required fields are required unless explicitly optional;
- unknown fields are errors;
- duplicate fields are errors;
- duplicate association targets are rejected either by decoding or semantic validation;
- no best-effort coercion or ignored extension fields exist in v0.

Forward compatibility should use a new explicit schema identity, not silent acceptance of unknown structure.

## Schema identity

Every complete persisted document must identify the exact schema contract used to decode it.

The preferred direction is an immutable schema identity plus a content hash or equivalent exact fingerprint. A simple integer `schemaVersion` may remain in the reference JSON codec but is not considered sufficient evidence for the final Nyason design by itself.

Nyason v0 does not require a self-hosted schema language. The first schema may be defined by the F# decoder and a canonical external description. A meta-schema should be added only if it improves actual AI or migration reliability.

## Canonicalization

Canonical output must be byte-for-byte deterministic for an identical semantic snapshot and Nyason schema/profile.

Canonical order must not accidentally become semantic order.

Current intended treatment:

- entity collections whose order is not semantic: sort by stable ID;
- association collections keyed by stable target identity: sort by target ID;
- function parameters: preserve declared parameter order until parameter-order semantics are explicitly revisited;
- builtin generic type arguments: preserve semantic argument order (`Result<ok,error>` is ordered);
- display ordering that is not semantic belongs in presentation metadata rather than implicit file position.

## AI edit model

Normal agents should prefer semantic operations over raw Nyason mutation. Nyason editing is primarily expected for:

- migrations;
- recovery;
- fixture generation;
- codec tests;
- low-level debugging;
- controlled experiments comparing direct structured editing reliability.

This constraint is important: a more AI-readable persistence format does not replace the accepted semantic-operation boundary.

## Evaluation against JSON and TSON

Nyason should not become canonical merely because it is project-specific. Once the Phase D graph fixture is representative enough, compare at least:

1. strict canonical JSON;
2. Nyason candidate syntax;
3. TSON where a suitable implementation/experiment is practical.

Measure:

- token count on full snapshots and focused slices;
- correct identification of node role, type, target, and ownership;
- mutation success for rename, field/variant changes, parameter addition, and obligation repair;
- malformed-edit detection quality;
- behavior when only a local slice is provided;
- parser/decoder implementation size and complexity;
- deterministic round-trip behavior;
- Git diff usefulness;
- schema migration clarity.

The deciding metric is not minimum bytes or tokens. It is semantic edit reliability at acceptable context cost.

## Initial grammar sketch

This sketch is deliberately non-normative. It exists to constrain experiments, not to freeze punctuation.

```text
schema nayamnyam.graph.phase-d sha256:...

snapshot {
    id: snapshot:...
    parent: snapshot:...

    types: [
        type product {
            id: type:...
            name: "RawUserInput"
            fields: [
                field {
                    id: field:...
                    name: "name"
                    type: primitive string
                }
            ]
        }
    ]

    functions: [
        function {
            id: function:...
            name: "validate_user"
            result-type: builtin result [
                named type:valid-user
                named type:validation-error
            ]
            body: value-graph {
                nodes: [
                    node field-access {
                        id: node:...
                        source: node:...
                        field: field:...
                    }
                ]
                result: node:...
            }
        }
    ]
}
```

## Gate before implementation

Do not build a full Nyason parser until the Phase D semantic model compiles and its test fixtures expose realistic shape. The first prototype should encode only those verified structures, then be compared empirically with the reference JSON codec.

## P0: MCPの操作結果・レビュー取得

**観測:** 大きなbatch reviewがcompact応答の16KiB制限に達した。エラーでもpending proposalが残った例があり、一覧を確認してrejectし、小さいbatchで再提案した。レビューの省略箇所は `readProposal` のページを追って確認した。先に別proposalをcommitした場合は、古い基底のproposalをrejectして作り直した。

**改善案:**

- proposal作成の成否とレビュー表示の成否を区別し、応答の生成に失敗した場合も作成有無・proposal ID・基底snapshotを取得できるようにする。
- 大きなレビューは上限内の要約と明示的な継続情報を返す。省略された範囲・項目数・続きの取得方法を機械的に判別できるようにする。
- 基底が変わった場合の再提案手順を診断から辿れるようにする。内容を確認せずに自動再適用・自動commitする方向にはしない。

**改善を確認する条件:** 同じ大きな変更で、応答の上限超過から操作結果を推測せず、未確認の差分と残存proposalを列挙・回収できる。既存のreview／readiness／明示commitを維持する。

## P1: 標準Runner・ホストSDK

**観測:** `画面 → HTTP → Pythonのプロセス管理 → 生成C#` を接続し、ECMAScript互換操作にはNode.jsを使った。型変換とUTF-16の保持、常駐プロセスの再利用、業務エラーと通信障害の分類を実装した。30万件のタグ索引を毎回転送する方式は不適切で、Runner内に型付き値を保持し、owner別の参照IDでアクセスする形にした。

**改善案:**

- exported関数・型・symbol manifestから接続コードを生成し、アプリ側で生成名やフィールド順を推測させない。
- 通常の業務エラーと通信切断・不正応答・timeoutを区別する常駐Runnerと、JS／Pythonからの非同期呼び出し例を提供する。
- 大きな型付き値の参照・解放・所有者の分離・セッション終了時の解放を共通化する。再起動後に古い参照を再利用できないことも明示する。

**優先する範囲:** まず今回の接続処理から再利用可能な最小部分を取り出す。キャッシュの業務方針、HTTP認証、保存先、アプリの再起動判断までを言語機能に取り込まない。

**改善を確認する条件:** 次の小さなJS／Python連携アプリで、同じcodec・子プロセス管理・値の参照管理を独自実装せず、失敗時も既存の保持値を不必要に失わない。

## P1: recipeの作成支援

**観測:** `listLength` は `list` ではなく `value`、`mapKeys` は `map` ではなく `value`、`float64Literal` は `value` ではなくIEEE-754の `bits` を要求した。既存の `recipe_reference` を確認して修正した。

**改善案:** 既存referenceを再利用した入力時のスキーマ検証、正しい最小例、誤ったプロパティへの修正候補を用意する。通常の数値から正確なliteralを作る補助を提供し、必要な場面のビット指定は残す。

**改善を確認する条件:** 上記の誤入力に対し、参照文書を探し直さずに正しい形へ修正できる。新しい独立仕様や二重管理のrecipe一覧は作らない。

## P1: effect診断と修正支援

**観測:** UUID／日時／ECMAScript互換操作をcapabilityにすると、兄弟式の観測順が未指定のままでは `AmbiguousEffectOrder` になった。`Bind` で順序を明示した。effect付きcallbackは `ListMap` で拒否され、`ListEffectFold` に変更した。validationのabortも順序付けの対象だった。

**改善案:** 問題の式・競合するeffect・不足する順序を示し、`Bind` や `ListEffectFold` への具体的な書き換え例を返す。順序検査を緩めたり、未指定の評価順を勝手に決めたりしない。

**追加の検討案:** 小文字化などの決定的な操作を、安全な純粋ホスト関数として扱えるか確認する。これは未調査の設計案であり、例外・locale・環境依存性を無視してpureと見なさない。UUIDや現在日時のeffect管理とは分けて検討する。

**改善を確認する条件:** 同じ拒否事例で、必要な修正位置と書き換え方を診断だけで特定でき、effect順序と失敗伝播の保証を維持できる。

## P2: ブラウザー向け実行経路

**観測:** 今回利用したmaintained backendはC#で、ブラウザー内で直接実行する経路は使えなかった。このためローカルサーバーと複数プロセスの接続が必要だった。

**改善案:** JSまたはWasmによるブラウザー内実行を検討する。Web用途の移植を継続して行うなら効果は大きい。一方で、ブラウザーで動かす困難は他の非Web向け言語にもあるため、今回の1例だけで新backendの実装を最優先にはしない。先に標準Runner／SDKで負担を下げ、残る費用を確認する。

## P2: 明示的な互換ライブラリ

**観測:** Unicode小文字化、UTF-16添字・孤立サロゲート、空白集合、日時・JSONの解釈に元のJS／Pythonとの差があった。汎用のホスト操作とcodecで補い、比較テストを追加した。

**改善案:** UTF-16やECMAScript互換など、必要な仕様を選ぶライブラリ・adapterと比較用のテスト例を提供する。Nyrwvy全体の文字列や数値の意味を元言語に合わせて変更しない。

**優先度を下げる理由:** 完全互換の負担は言語間移植に共通する。標準の意味と互換操作の境界が明確なら、言語本体にすべての互換処理を追加する必要はない。

## さらに優先度を下げるもの・対象外

- **保存競合・古い応答の破棄・IndexedDB完了待ち:** 非同期アプリ一般の問題。SDKで支援できても、業務上の適用判断はアプリ側に残る。
- **二乗時間の重複排除:** 今回は既存の `SetFromList`／`SetToList` で解決した。新しい言語機能の不足とは扱わない。
- **ブラウザーの版違い・sandbox・外部レビューの承認:** 開発環境側の問題。Nyrwvyの意味論を変更する根拠にはしない。ビルド失敗の原因が未確定だった事例も断定しない。
- **移植時の業務ルールの取り違え:** 他言語でも比較テストが必要。今回の不存在slotの扱いは移植側の修正で解決した。

## 推奨する順序と未確認事項

MCP応答の改善 → 標準Runner／SDK → recipe・effectの作成支援を推奨する。アプリごとに繰り返した接続・調査の負担を減らし、言語間移植に共通する費用と区別して効果を確認する。

現行実装での各候補の解消状況・重複機能・実装工数は未調査。実NovelAI API・実ディスプレイでの手動ダイアログは今回の移植で未検証。これらを検証済みの根拠として使わない。

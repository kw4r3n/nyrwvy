# Snapshot-backed agent authoring session

For measured full-review CPU/allocation costs, complete structured saved reviews and the
remaining limits of bounded wire paging, see the [encoding measurements](../verification/review-encoding-cost-20261020.md).

**Status:** Current

This specification defines the Milestone 3 maintained authoring boundary tracked by issue #153. It composes the existing semantic query, reviewed mutation, structural expression, persistence, execution-projection, and backend APIs. Later declaration-authoring slices join this same session boundary without creating another workspace authority.

## Purpose

An ordinary agent must be able to open one explicitly selected Nyrwvy snapshot, discover stable declarations, propose and review semantic changes, persist accepted changes across authoring-process restarts, close the process, and later resume from the same committed semantic identities.

The maintained path is a single-workspace, single-writer session. Frozen M1/M2 evaluation protocols remain historical verification surfaces and are not imported as the production authoring protocol.

## Pinned snapshot dependencies

`create --snapshot <local> --dependency <existing-source-snapshot>` selects one independent, strict, complete source snapshot and retains its canonical JSON in `<local>.dependency.json`. `open --snapshot <local>` validates and uses that retained content, never the latest version at the original source path. Upstream commits or removal no longer invalidate the selected version. Clone/move the local snapshot **and its sidecar together**; no original-machine absolute path is needed to reopen. Sources with their own dependencies are flattened (see below).

The embedded manifest has exactly `path`, `snapshotId`, `fingerprint`, and one of `snapshotJson` (a canonical strict snapshot JSON **string**, avoiding an extra graph nesting level) or `snapshotRecords` (the same content in the [record form](#persistence-format), chosen when the dependency file's extension is `.nyrec`); the key marks the embedded form and `fingerprint` is the model fingerprint either way. `path` is original-source provenance only. The local snapshot's dependency ID and canonical-source digest still bind the exact retained content: removing/replacing/corrupting the manifest cannot silently change the pin or turn the graph into a standalone one. Publication rechecks the exact manifest bytes against the opened selection. Creation writes the sidecar and local snapshot separately atomically; a failed create may leave an orphan sidecar that must be inspected/removed before retrying. No cross-file crash atomicity or power-loss durability is promised. The graph codec and fingerprint domains are unchanged; old clients that only accept three-field manifests cannot read the embedded format.

**Several dependencies.** `create` accepts `--dependency` more than once (the MCP `open` tool takes `dependencies: [...]`). Each source is pinned exactly as above, and the workspace resolves against their combination under the import collision policy (Q-002). Imported declarations keep their typed identities. A declaration reached through more than one dependency, such as a type both libraries copied from a shared library, is imported once only when its content is identical. Identical means equal in every respect, including the order of parameters and type parameters, because that order is meaningful: the same declaration with reordered parameters is a conflict, never normalized and merged. Product fields, Union variants and their fields, and Capability operations are sets keyed by ID, persisted in ID order, so they are compared in ID order. Any other identity that appears in two dependencies with different content is rejected with its kind and ID, and a collision with a local declaration fails snapshot validation, so distinct objects are never merged. Selecting the same source twice is rejected. The sidecar is then `{ "dependencies": [ <embedded member>, ... ] }`, with at least two members, each in the embedded form above; a single dependency keeps the one-object form. The combined imported graph has a deterministic SnapshotId derived from its members' fingerprints, independent of order, and the local snapshot binds to its canonical digest. Tampering with any member is detected on open. `pin` with a source applies only to a single legacy dependency. The `dependency` request reports `{ "dependencies": [ ... ] }` for a set.

**Multi-level dependencies.** A selected source may itself be a workspace with pinned dependencies. It is flattened into its complete graph: its local declarations are resolved against its own retained sidecar content, checked for completeness, and pinned as one exact snapshot. The app therefore needs neither the intermediate's sidecar nor the upstream sources afterwards. Because flattening keeps imported identities, a library reached through several paths (a diamond) is deduplicated by the same identical-content rule, and differing content under one identity is rejected.

**Explicit upgrade.** Reproducing the pinned version (`open`, `pin`) and moving to a new version are separate operations. Inside a session, `{ "op": "previewDependencyUpgrade", "source": "<new version>", "replaces": "<old SnapshotId>" }` pins the new source as a candidate, flattening it if needed; `replaces` is required only when several dependencies are selected. It reports `replacedSnapshotId`/`replacedFingerprint`, `newSnapshotId`/`newFingerprint`, and the `added`, `removed` and `changed` imported declarations as `{ kind, id }`. It also reports `issues` from validating the unchanged local graph against the upgraded imports, and `compatible` when there are none. Nothing is written. Applying is a startup mode: `upgrade --snapshot <local> --dependency <new version> --expect <newFingerprint> [--replaces <old SnapshotId>]` (MCP `open` mode `upgrade` with `dependency`, `expectedFingerprint`, `replaces`). It recomputes the plan under the workspace lock, refuses a source whose fingerprint differs from the reviewed one or a candidate with issues (`WorkspaceValidationFailure`, leaving both files byte-identical), and refuses the already-selected version. Otherwise it rewrites the sidecar and re-binds the local snapshot to the new dependency digest, keeping local declarations and identities, and opens the upgraded session. The sidecar is replaced first; if replacing the local snapshot then fails (for example disk full or permission denied), the previous sidecar content is restored and the error is reported, so the unchanged workspace still opens and the upgrade can be retried. As with creation, this is not cross-file crash atomicity: a process crash between the two replacements can still leave them mismatched. An upgrade that breaks local references is refused rather than applied partially; local references must first be made compatible with the new version.

**Atomic dependency-set upgrade.** When a shared declaration changes across a diamond, reviewing each member against the still-old others correctly reports an identity collision. Review the final selection together: `{ "op": "previewDependencyUpgrades", "upgrades": [{ "source": "<new A>", "replaces": "<current A SnapshotId>" }, { "source": "<new B>", "replaces": "<current B SnapshotId>" }] }`. The list must be nonempty, with distinct explicit current targets; unchanged members retain their exact pins. The response includes per-member changes, aggregate changes, final `issues`/`compatible`, and an opaque `reviewFingerprint`. Close the session and apply `upgrade --snapshot <local> --upgrades '<same JSON array>' --review <reviewFingerprint>`, or MCP `open` mode `upgrade` with `upgrades` and `reviewFingerprint`. Do not combine batch fields with single-member fields. The review binds exact current local bytes, current sidecar bytes, workspace path, replacement targets, source paths and new selected content. An edit, changed pin, relocated replacement, retarget or changed source requires a fresh review. Only the complete final imports are combined and validated; intermediate collisions are never ignored or persisted. Local identities and unnamed pins remain unchanged. Application uses the same lock, complete validation, external-file recheck and rollback as single-member upgrade; the existing cross-file crash limitation still applies.

Consolidating or splitting dependency libraries uses the same review/apply transaction without pretending there is a one-to-one mapping. Pass `selection: { "sources": ["<complete new sources>"], "replaces": ["<current SnapshotIds>"] }` instead of `upgrades` to `previewDependencyUpgrades`, then the identical `selection` and `reviewFingerprint` to MCP `open` mode `upgrade` (CLI `--selection '<same JSON object>' --review <reviewFingerprint>`). Both lists must be nonempty; targets must be distinct current members, and final source paths and SnapshotIds must be distinct. All unnamed old members remain pinned. The response's `replaced` and `selected` list exact old/new member identities and fingerprints; aggregate declaration changes describe the complete final imports. A no-op final selection is refused. Pair-based `upgrades`, arbitrary-cardinality `selection`, and single-member options are mutually exclusive.

**Dependency update with local repairs.** If the final imports break local constructors, readers or callers, use the ordinary proposal lifecycle rather than persisting an incompatible intermediate graph. `simulateDependencyUpgrade` (or `simulateDependencyUpgradeByName`, shared tool `upgrade_dependencies`) takes exactly one of the same `upgrades` or `selection` descriptions, plus `repairs`. It combines final imports with explicit repairs and runs the maintained structural simulation, recipe materialization, whole-snapshot validation, readiness and fingerprint checks. A successful reply is a pending `dependencyUpgrade` proposal; inspect its dependency changes and local declarations, then use the existing `commit` with its exact `proposalId`. Nothing is written by simulation, and `reject`/close discard the pending proposal.

`repairs` has optional arrays `fields`, `functions`, and `operations` (omitted arrays are empty). Exact-ID fields are `{typeId,fieldId,newType}`; function repairs are `{functionId,parameterTypes:[{parameterId,type}],resultType,replacement}`; operation repairs are `{operationId,parameterTypes:[{parameterId,type}],resultType}`. Name-resolved forms use `{type,field,newType}`, `{function,parameterTypes:[{parameter,type}],resultType,replacement}`, and `{capability,operation,parameterTypes:[{parameter,type}],resultType}`. Names and recipes resolve against the **final imports**, while existing local owner/type-parameter identities remain available. Fields must be existing local Product fields. Function/operation parameter maps must contain every existing parameter exactly once; order, IDs, names, effect declarations and unchanged local content remain authoritative. Imported declarations are read-only. This does not create/delete declarations, add/remove parameters, or change operation failure/effect contracts; those use their maintained workflows.

Repairs are materialized together under their final signatures, so local transitive callers and local field consumers can change in the same candidate. A missing repair that leaves the final graph invalid is rejected; validation is never bypassed to accept an intermediate mismatch. The review contains the exact proposed snapshot, local changed declarations and selected dependency fingerprints. Commit retains that candidate (including system-allocated body IDs), refuses a changed local graph/current manifest/new source content or target, and uses the existing single-writer lock and dependency-pair persistence with rollback on a graph-write failure. A failed write retains a retryable proposal when rollback succeeds; a changed source needs a new simulation. After commit the session adopts the new read-only imports, and reopen uses their retained content. Before every commit the session re-reads the sidecar (and, for a legacy selection, the source); only content that was read and differs invalidates the session with `DependencyFailure`, while a read that fails (permissions, a transient I/O error) is reported as `IoFailure`, leaves the proposal retryable and does not invalidate the session. The existing two-file crash/power-loss limitation still applies; the previous sidecar is kept as `<snapshot>.dependency.json.previous` during the replacement so an interrupted one is recoverable (see [snapshot migration](#snapshot-migration)).

A local snapshot with a dependency binding but no `<snapshot>.dependency.json` fails with `DependencyFailure` naming the missing sidecar and asking to restore its exact copy. Opening, pinning or importing that snapshot does not guess the lost selection or authorize a new version. Genuine malformed snapshot JSON retains the codec diagnostic.

**Legacy migration and same-content recovery:** old manifests containing only `path`, `snapshotId`, and `fingerprint` retain their original fail-closed behavior on ordinary open/commit. `pin --snapshot <local>` explicitly retains the exact selected source in the sidecar and starts a session. If the old path is unavailable or now points at another version, use `pin --snapshot <local> --dependency <exact-original-copy>`. Pin validates source completeness, selected ID/fingerprint, the local digest and the combined graph before replacing only the manifest. Local graph bytes, identities and fingerprints do not change. It honors the single-writer lock and rechecks both files before replacement; replacement failure retains the old selection. Pin is idempotent on an already embedded selection, and cannot attach a dependency to a standalone workspace. The [migration command](#snapshot-migration) retains a legacy selection the same way (with the same `--dependency <exact-original-copy>` recovery) while rewriting the workspace to the current schema; after the [legacy cutover](../plans/post-m2-roadmap.md#legacy-cutover-planned) it is the only way to open a legacy manifest.

This implements the **retained immutable content** strategy from [issue #209](https://github.com/kw4r3n/nyrwvy/issues/209); version changes go only through the explicit upgrade above. Pin cannot accept changed content, even under the same SnapshotId. No semantic upgrade is implied or authorized by a provenance-path change. A legacy pin whose original contents have been lost cannot be reconstructed from a digest; an exact old copy is necessary. Semantic version changes use the reviewed single-member or complete selection upgrade above. Local-reference changes remain ordinary reviewed graph edits, and the final imported/local graph must validate before an upgrade is written.

The shared MCP/OpenCode `nyrwvy_open` supports `mode: "create"`, `"open"`, `"read"`, `"pin"`, or `"upgrade"`. Mode `read` starts `open --snapshot <path> --read-only`: no workspace lock is taken, so it works while another session holds the snapshot; inspection, simulation, runs and emission work, and commit fails with `ReadOnlySession`. Because a dependency upgrade replaces the sidecar and the snapshot in two renames, a read-only open that races one can fail on the mismatched pair; it never reads a mixed state. Its optional `dependency` argument selects a source for create, same-content pin or reviewed single-member upgrade; `dependencies` selects several sources only for create. Reviewed `upgrades` or `selection` is used only for upgrade. Relative source paths resolve against the selected workspace. Open never silently migrates storage or accepts another selection. A structurally valid dependency with any open obligation is rejected at create, pin and reopen before a commit-blocked workspace is admitted. Standalone incomplete authoring and ordinary commit policy are unchanged. Malformed manifests and access failures return controlled errors and release the lock.

The read/review/workspace and C# emission projection use the validated union of imported and locally authored declarations. Imported declarations keep their exact stable identities. Only the dependency's **exported** declarations are visible to the dependent ([declaration visibility](../decisions/declaration-visibility.md)): a private imported type, effect, capability or function is left out of `declarations`, of provenance and of name resolution (a by-name request that names one fails as an unknown name), and a proposal whose candidate refers to one by exact ID, in a signature, field type, operation type, required effect or body, is rejected before registration with `ImportedDeclarationNotExported`. The resolved graph still holds every imported declaration, since an exported function may call a private one, so execution and emission are unchanged. Local graph snapshots persist **only** local declarations and references to imported IDs; the sidecar separately retains the selected imported snapshot as immutable dependency content. Validation rejects duplicate identities, missing references and invalid combined graphs. Read-only imports are a policy of the authoring session, not of the semantic core: the resolved snapshot does not record which declarations are imported, and `SemanticWorkspace` and `Transaction.simulate` apply an operation to any declaration of it, so another library consumer must enforce the rule itself. The session's simulation rejects edits to imported declarations as `ImportedDeclarationModified` before returning a proposal handle or review. This checks the workflows' resulting affected owners, including caller and match repairs, not just the primary requested target. Publication retains the independent check that no imported declaration changed or disappeared. The selected provenance is inspectable via the read-only `dependency` operation. Dependency versions are selected at workspace creation or by an explicit reviewed upgrade, not added by a graph mutation proposal. Same-content pin only changes storage/provenance; declaration and body edits still use ordinary simulation, review and explicit commit. One full snapshot or a complete set of full snapshots is retained under the import collision policy. Package resolution and import namespaces remain outside this boundary. Standalone strict snapshot decoding continues to reject dependency-bearing local files without resolution.

## Session lifecycle

A session starts in exactly one of four explicit modes:

1. **Open** an existing snapshot file. The file is decoded with the existing strict `SnapshotCodec`, validated, and wrapped in `AgentWorkspace`.
2. **Create** a new snapshot file. The session creates `Snapshot.empty` with a system-owned snapshot ID, validates it through `AgentWorkspace`, serializes it with `SnapshotCodec`, and creates the selected persistent file before reporting success.

3. **Pin** an existing dependency selection using the same-content migration/recovery rules above, then open that existing graph. This is storage maintenance.
4. **Upgrade** one or several explicit dependency members to the reviewed complete versions, validate the final imported/local graph, persist the selection with rollback on a reported graph-write failure, then open that existing graph. It requires the single-member reviewed fingerprint or context-bound batch/selection review fingerprint.

Opening a missing file is an error. Creating over an existing file is an error. There is no implicit fallback between modes.

Besides the four session modes, `migrate --snapshot <local> [--dependency <exact copy of a legacy pin's source>] [--to <new path>]` is a maintenance command that starts no session: it rewrites the workspace to the current snapshot schema, or with `--to` writes it to a new path in the form that path's extension selects, and exits ([snapshot migration](#snapshot-migration)).

A live session owns one workspace path. Proposal handles are process-local and may be discarded when the process ends. A new process reopens the last published snapshot and must simulate/review any later change again.

## Persistence guarantee and failure boundaries

The maintained storage contract is **atomic snapshot visibility and persistence across authoring-process restarts**, not machine-crash or power-loss durability:

| Boundary | Maintained guarantee |
| --- | --- |
| Successful create/commit response | The complete snapshot has been written, the temporary file has been closed, and the selected path has been created/replaced before success is reported. A later authoring process can reopen the published state while the OS/filesystem remains healthy. |
| Authoring-process termination after success | The published file does not depend on the terminated process's memory or proposal handles. Normal close and abrupt process termination preserve the acknowledged snapshot under the same healthy-OS assumption. |
| Snapshot visibility during publication | Same-directory replacement is the publication boundary; supported storage must provide the local filesystem's atomic rename/replace and exclusive-lock semantics. Network, distributed, or unusual filesystems are not independently certified by this contract. |
| OS crash, reboot after kernel failure, or power loss | **No guarantee.** `File.WriteAllText` plus `File.Move` does not explicitly flush file contents or parent-directory metadata to durable media. An acknowledged commit may be lost or damaged under these failures. |
| Response lost during/after publication | The mutation outcome is unknown. Reopen, decode/validate, and inspect the persisted state before deciding the next action; do not replay the mutation or reuse the old proposal handle automatically. |

This scope describes the existing implementation rather than claiming stronger storage behavior from process-reopen tests. A future machine-crash guarantee needs an explicit supported OS/filesystem scope, durable file and directory synchronization, and targeted failure-injection evidence. Its error protocol must distinguish a pre-replacement failure from a post-replacement synchronization failure: the latter cannot safely be described as an unchanged authoritative file.

See `AuthoringSessionTests` for acknowledged publication/reopen, abrupt process termination, single-writer exclusion, and reported I/O/external-modification failure checks. These tests establish process-level behavior, not power-loss durability.

## Single-writer and external modification rule

The maintained session is intentionally not collaborative storage.

- One authoring session owns a sidecar exclusive lock for the selected workspace path.
- The session remembers the exact persisted source it opened or last published.
- Immediately before publication it verifies that the authoritative snapshot file still contains that exact source.
- A mismatch, deletion, or replacement is reported as an external-modification error. The session does not merge, rebase, or revive an earlier approval against the new file.

The lock coordinates maintained authoring sessions. The persisted-source comparison detects writers that do not honor that lock.

## Proposal and publication lifecycle

Queries do not mutate state. Simulation and review do not execute capabilities.

A mutation follows this lifecycle:

1. Build an intent using one of the existing agent authoring APIs.
2. Simulate against the current `AgentWorkspace` and return the existing review facts plus an ephemeral proposal handle. A request that names the snapshot its author inspected (`expectedSnapshotId`, see [Inspected base snapshot](#inspected-base-snapshot)) is rejected instead when the current snapshot differs.
3. The caller either rejects the proposal or asks to commit that exact handle.
4. Core commit/review validation produces an immutable candidate `AgentWorkspace` or rejects it as invalid/stale.
5. On a candidate commit, serialize the candidate workspace through the existing strict snapshot codec.
6. Re-check the persisted-source token, write the complete candidate to a temporary file in the same directory, and replace the authoritative file as one publication boundary.
7. Only after persistence succeeds does the session replace its in-memory workspace and report commit success.

A reported temporary-write or replacement failure leaves the session's current workspace at the previously published state and does not intentionally publish the candidate file. The existing I/O-failure tests retain the previous authoritative file. This is not a promise about OS/storage failure or a lost response after a successful replacement; those boundaries are distinguished above. A rejected semantic commit never reaches the persistence step.

Every simulate operation validates the base snapshot, runs its own preflight, builds the proposed snapshot, validates it as a whole, classifies readiness and fingerprints the receipt. A base snapshot that fails validation rejects with `InvalidBaseSnapshot` and a proposed snapshot that fails full validation rejects with `InvalidProposedSnapshot`, whatever the operation, with one diagnostic per validator issue whose message is `<issue code>: <message>`. Operation-specific preflight diagnostics are reported before the proposed snapshot is built.

The session does not provide a durable proposal database. Existing proposal handles that become stale after another publication are allowed to fail through the existing stale-base checks. These checks protect the window between simulation and commit; the window between inspection and simulation is protected only when the request carries `expectedSnapshotId`.

## Read/query surface

The maintained session exposes read-only discovery over the current workspace:

- current snapshot ID plus structural and semantic fingerprints;
- declaration discovery for functions, product/union types, effects, and capabilities;
- focused function inspection, including stable graph-node identities and impact facts already supplied by semantic queries;
- callers, callees and open obligations through the function focus, and every referencing site of a declaration or member through the `references` query;
- the pending proposals of the session (`proposals`), with their count in `status`.

Read projection may expose semantic facts and stable IDs, but it grants no raw snapshot publication authority.

## Mutation surface

The session is an adapter over existing authoring contracts:

- ordinary `AgentWorkflow` operations: display-name rename of a function, type, field, Union variant, function parameter, Effect, Capability, Capability operation or Capability operation parameter, add function parameter, remove a function parameter, remove a Union variant, add Product field with exhaustive constructor plans, remove an unused Product field, add a Capability operation with exhaustive implementation plans, delete an unreferenced function/type/effect/capability/operation, resolve missing argument, and add/remove required effects (each by exact ID through `simulateOperations` or by display name through `simulateOperationsByName`);
- whole-body `ExpressionRecipe` replacement;
- targeted `ExpressionRecipe` replacement from issue #148;
- atomic function creation with ordered `ParameterSlot` references from issue #149;
- atomic product/union declaration creation defined by [type declaration authoring](type-declaration-authoring.md);
- atomic effect declaration creation defined by [effect declaration authoring](effect-declaration-authoring.md);
- atomic capability/operation declaration creation defined by [capability declaration authoring](capability-declaration-authoring.md);
- exact reviewed commit/reject and readiness/diagnostics from those workflows.

Production graph-node, parameter, function, type, variant, field, effect, capability, capability-operation, capability-parameter, pattern-binding, transaction, and snapshot IDs created by these operations remain system-owned. The transport may only reference identities where the corresponding authoring contract accepts existing IDs.

Milestone 3 initially excluded declaration creation. The staged function, Product/Union, Effect, and Capability/Operation authoring contracts now all compose through the same maintained session without changing its persistence or single-writer authority.

## Execution boundary

Semantic readiness, execution/lowering readiness, and actual backend execution are distinct results.

The session may project the committed workspace with `AgentExecution.projectTypedSemanticIr`, lower it with `ExecutionIr.lower`, and pass the result to an explicitly selected existing backend/profile. Simulation and review never invoke this path. `runPure` is a separate explicit execution request: it selects a chosen function by stable `FunctionId` and every transitive structural function dependency from the exact committed snapshot before semantic readiness checks and execution lowering, retains every type and capability declaration with capability operations as external implementations, builds a temporary executable, and returns the actual value and optional expected-value comparison for the typed inputs. Capability parameters are bound only to scripted fakes supplied in the request; the runner never connects a host service. It never edits the snapshot or generated C# source and refuses a changed snapshot or dependency pin before running. Live capability execution therefore remains controlled by the explicit backend/profile/provider setup rather than by editable C# or an implicit live service.

## JSON-lines process protocol

The maintained executable uses one JSON object per input line and emits exactly one JSON object per input line. A blank or whitespace-only line is malformed input and gets a `ProtocolError` reply with a null `id`, like any other line that is not a request object. The process is started with one selected snapshot path and explicit open/create mode; the path is not repeated in request messages.

Every request has:

```json
{"id":"caller-token","op":"status"}
```

Every response echoes `id` and has either:

```json
{"id":"caller-token","ok":true,"result":{}}
```

or:

```json
{"id":"caller-token","ok":false,"error":{"code":"...","message":"..."}}
```

Besides the operation-specific codes below and the session error codes (`SnapshotFileNotFound`, `IoFailure`, `SnapshotCodecFailure`, `WorkspaceValidationFailure`, `ProposalNotFound`, `CommitRejected`, …), the transport uses: `ProtocolError` for malformed or unresolvable input, `UnsupportedOperation` for an unknown `op`, `SessionError` for an operation the session state does not allow, and `InternalError` for any other unexpected failure. `InternalError` answers only that request: its `message` is a fixed text that names no exception (the exception type and message go to the process's stderr only), the session keeps running, and its state is unchanged (the in-memory workspace and pending proposals are updated only after a successful write). A graph that would nest deeper than the snapshot codec's 1000 JSON levels cannot be persisted or fingerprinted; the simulation or commit reports a `SnapshotCodecFailure` whose message names `MaximumDepthExceeded` and the limit instead of failing the process. Only nesting (branch, arm and Bind bodies inside one another) is bounded this way. A flat dependency chain inside one body, such as `n1 -> n2 -> ... -> nN`, has no separate limit beyond memory: the validator's cycle check, the type resolver and the effect-order check keep their own stacks instead of recursing along the chain, so a body of tens of thousands of chained nodes is validated and loaded like any other. Error `message`s are sentences, never F# value dumps; `SnapshotCodecFailure` and `WorkspaceValidationFailure` spell out the first validation issue and list them all under `details.issues` as `{ code, message }`. When the process cannot start at all (`SnapshotFileNotFound`, `SnapshotFileAlreadyExists`, `LockUnavailable`, a codec or dependency failure), it writes the same `<code>: <message>` line to stderr and exits with status 2.

Unknown properties that would change request meaning are rejected rather than ignored. Duplicate property names in request objects, including nested recipes and declarations, are rejected as `ProtocolError` rather than resolved by first- or last-value precedence.

A request line may nest up to **835** JSON levels. The bound is derived from the recipe node limit ([decision](../decisions/expression-recipe-bounds.md#consequences)): 3 envelope levels above a recipe root (`functionRewrites[i].replacement` is the deepest), 3 levels per recipe node (the node object, a child list such as `arguments` or `arms`, and the entry holding the child) for all 256 nodes the limit allows, and 64 levels at the leaf for an explicit TypeRef. Any recipe within the node limit therefore parses and is judged by the recipe bounds, so a recipe deeper than 32 nodes gets `StructuralRecipeDepthLimitExceeded` (which states its actual depth) rather than a JSON error. Only a line nested deeper than 835 levels is a `ProtocolError` (`Invalid JSON: The maximum configured depth of 835 has been exceeded…`). Responses are encoded with a 2000-level allowance, twice the snapshot codec's 1000, so any graph the session can persist can also be read back (a nested scope costs a response at most 4/3 of its snapshot levels). Responses for deep graphs can nest well beyond 64 JSON levels; clients should parse without a small depth limit (Node's `JSON.parse` has none).

### Operations

The maintained operation set is:

| `op` | Purpose |
| --- | --- |
| `status` | Current snapshot ID and fingerprints, and `pendingProposalCount`, the number of proposals simulated in this session and neither committed nor rejected, and `build`, the session tool's InformationalVersion (version and source commit) so a caller can tell which build is running. `open` of the agent tools includes this status. |
| `proposals` | The pending proposals: `{ count, proposals: [{ proposalId, kind, baseSnapshotId, baseIsCurrent, summary }] }` in proposal-ID order. `kind` is the review kind the simulate reply reported; `baseIsCurrent` is false for a proposal simulated against an earlier snapshot, which commit will reject as stale; `summary` is one line naming the requested change and its targets by display name (for an operations proposal, each operation). Reading lists nothing but handles; the review itself is read with `readProposal`. |
| `references` | Every site of the current snapshot that refers to a declaration or one of its members ([reference query](#reference-query)). |
| `unreferenced` | Local functions, capability operations and types with no references from other declarations. Optional `roots` is an array of function names; when supplied, reports local declarations unreachable by following function and operation uses and type references from those roots. Results are sorted by name and include stable IDs. |
| `dependency` | Read-only provenance path, snapshot ID, fingerprint and `storage` (`embedded` or `legacySource`), or null. Does not return the retained graph payload. |
| `previewDependencyUpgrade` / `previewDependencyUpgrades` | Read-only compatibility review of replacing one pinned dependency, or of an atomic set of replacements or a consolidating/splitting `selection`; nothing is written ([pinned dependencies](#pinned-snapshot-dependencies)). |
| `simulateDependencyUpgrade` / `simulateDependencyUpgradeByName` | Propose a dependency update together with explicit local repairs, reviewed and committed like any other proposal (shared tool `upgrade_dependencies`). |
| `declarations` | Stable-ID declaration discovery. |
| `readFunction` | Structured function graph by exactly one of `function` (display name) and `functionId`; `detail: "compact"` leaves out the per-node graph, while `detail: "outline"` adds a bounded indented body with node IDs and short operands, reporting `outlineTruncated` when capped ([contract](agent-graph-tools.md)). |
| `bindingScopes` | The pattern bindings visible at one node of a function, innermost first with their `scopeDepth` ([contract](agent-graph-tools.md)). |
| `search` | Declarations whose display name contains `text`, and string literals that contain it, ignoring case ([contract](agent-graph-tools.md)). |
| `viewFunction` | Write the committed function's human-readable Function Focus HTML and return its path; exactly one of `function` and `functionId`, optional `.html` `output` ([contract](agent-graph-tools.md#human-readable-view)). |
| `viewProposal` | Write a pending proposal's human-readable Change Review HTML and return its path; required `proposalId`, optional `.html` `output`. Publishes nothing ([contract](agent-graph-tools.md#human-readable-view)). |
| `simulateOperations` | Simulate a list of existing `AgentOperationIntent` operations, including `addUnionVariant` with one arm recipe per `matchUnion` over the Union. |
| `simulateOperationsByName` | Resolve display names in a list of operations (deletions, removals, renames, parameter/field/operation/variant/effect additions and missing-argument resolution), then simulate them as `simulateOperations` does. |
| `simulateCreateFunction` | Simulate atomic function creation with an `ExpressionRecipe`. |

`simulateOperations` accepts `{ "kind": "addFunctionParameter", "functionId": "<existing>", "displayName": "<new>", "type": <TypeRef>, "callSites": [{ "kind": "bind", "callNodeId": "<existing>", "valueNodeId": "<existing>" } | { "kind": "leaveMissing", "callNodeId": "<existing>" }] }`. The parameter ID is system-owned. Every direct call of the function needs exactly one call-site plan (`CallPlanMismatch` otherwise); `leaveMissing` creates an open missing-argument obligation and the review diff reports `parametersAdded`, `argumentsAttached` and `obligationsCreated`. Only direct calls can be planned. A function that is also used as a List callback, worker or scoped body, as a function value (`functionReference`), or as a capability implementation (`capabilityConstruct`) is rejected with `ParameterAdditionNonCallUse` before any plan is checked, since those uses fix its signature. The message names the function and every using function by display name and ID with its kinds of use, for example `Function 'double' (fn-1) is used other than as a direct call by 'mapAll' (fn-2) (callback); 'doubler' (fn-3) (capability implementation).` Replace those uses before adding the parameter.

`simulateOperations` also accepts `{ "kind": "addProductField", "typeId": "<existing>", "displayName": "<new>", "type": <TypeRef>, "constructions": [{ "constructNodeId": "<existing>", "valueNodeId": "<existing>" } | { "constructNodeId": "<existing>", "value": <ExpressionRecipe> }] }`. Every affected Product construction (including nested branches) needs exactly one plan, with exactly one of `valueNodeId` or `value`. The field ID is system-owned; a `valueNodeId` must select an existing value with the exact new field type and valid lexical scope. A `value` recipe is bound and type-checked in the construct's lexical scope, as a targeted replacement of that node would be (function parameters and the pattern slots visible there); it must produce the new field type within the function's required effects, and is materialized with fresh node IDs just before the construct. A construct node that does not exist is `ProductFieldPlanTargetNotFound`, a recipe of another type is `ProductFieldValueTypeMismatch`; see the [decision](../decisions/product-field-value-recipes.md). The review diff reports `productFieldsAdded` and `productFieldsBound`. `{ "kind": "removeProductField", "fieldId": "<existing>" }` removes a Product field and its constructor bindings only after field accesses have been repaired. Affected functions must have no declared effects; otherwise the operation refuses to risk discarding effectful evaluation. Its review diff reports `productFieldsRemoved` with affected constructor IDs. `{ "kind": "deleteFunction", "functionId": "<existing>" }` deletes only a function that no other function references and that has no open obligations targeting its body. Its removed node IDs appear in `functionsRemoved`; when its body owns resolved obligations, that entry also has `retiredObligations`, the exact removed records: `{obligationId, originTransactionId, callNodeId, parameterId, status:{kind:"resolved", transactionId, valueNodeId}}`. The records are sorted by obligation ID and shown in HTML review. Unrelated obligations remain exact; no obligation is retired from a surviving body. Resolving an open obligation and then deleting its caller is allowed in one ordered reviewed batch. A failed batch publishes neither deletion nor retirement. The existing whole-body replacement restriction remains. This is an additive review field only when retirement occurs, with no snapshot schema or status change; see [obligation retirement](failure-obligation-policy.md#retiring-a-resolved-obligation-with-its-function). A function's references to itself (a `SelfCall`, or itself as a callback inside its own body) disappear with its body and never block the deletion, so a self-recursive function is deleted in one operation. A rejection (`FunctionStillReferenced`) names the function and every referring function by display name and ID, for example `Function 'leaf' (fn-1) is still referenced by 'caller' (fn-2), 'other' (fn-3).` A batch may delete mutually referencing functions in any order; references from declarations deleted in the same batch do not block deletion. `{ "kind": "deleteType", "typeId": "<existing>" }` removes an unreferenced Product or Union; the diff lists its removed type, variant and field IDs in `typesRemoved`. References from functions, other types, capabilities, graph nodes, or obligations must be repaired or removed first. Dependent functions may be deleted in the **same** operation batch in any order; field edits and deletion of that type must be reviewed in separate transactions to avoid misleading net diffs. `{ "kind": "deleteCapability", "capabilityId": "<existing>" }` and `{ "kind": "deleteEffect", "effectId": "<existing>" }` remove unused declarations only after all references have been repaired or removed. `capabilitiesRemoved` lists operation and parameter identities; `effectsRemoved` lists the effect identity. A dependent function, its Capability, and the required Effect may be removed in one reviewed batch in any order. A type, effect, capability or capability-operation deletion is rejected with its `*StillReferenced` code only for validation issues the deletion itself introduces. An issue an earlier operation in the batch already left is not attributed to the deletion: a later operation may still repair it, and otherwise the final validation reports it as `InvalidProposedSnapshot` under its own validator code. These operations use the same reviewed transaction and stale-base protection as the existing operations.

`simulateOperations` renames by exact ID with `{ "kind": "renameFunction", "functionId", "displayName" }` and `{ "kind": "renameType", "typeId", "displayName" }`, and in the same shape `renameField` (`fieldId`, a Product field or a Union variant field), `renameVariant` (`variantId`), `renameParameter` (`parameterId`), `renameEffect` (`effectId`), `renameCapability` (`capabilityId`), `renameCapabilityOperation` (`operationId`) and `renameCapabilityParameter` (`parameterId`, a Capability operation parameter). A rename changes only the display name; every stable ID and graph reference is kept. A blank name is `InvalidDisplayName`. A name already held in the renamed member's scope is `DuplicateDisplayName`, and the message names the scope: fields are unique within their Product or Union variant, variants within their Union, parameters within their function, operations within their Capability, operation parameters within their operation, and types, functions, effects and capabilities among all of their kind. Pre-existing duplicates are left alone. Each entry of the review's `renames` has `kind` (`type`, `function`, `field`, `variant`, `parameter`, `effect`, `capability`, `capabilityOperation` or `capabilityParameter`), `id`, `oldDisplayName` and `newDisplayName`; a scoped entry also has its owners: `ownerTypeId` (and `ownerVariantId` for a variant field) for fields and variants, `ownerFunctionId` for parameters, `ownerCapabilityId` for operations, and `ownerCapabilityId` and `ownerOperationId` for operation parameters. Field and variant renames list their type in `affectedTypeIds`, parameter renames their function in `affectedFunctionIds`. The [decision](../decisions/structural-renames-and-removals.md) records the rationale. `{ "kind": "setExported", "typeId" | "functionId" | "effectId" | "capabilityId": "<existing>", "exported": <bool> }` changes one declaration's visibility and nothing else ([declaration visibility](#declaration-visibility)); the review's `diff.visibilityChanges` (present only when non-empty) lists each net change as `{ kind, id, displayName, exported }`, and the changed function or type is in `affectedFunctionIds` or `affectedTypeIds`. The same visibility is `VisibilityUnchanged`, a batch that sets and resets one is `NoChange`, naming no or several declarations is a `ProtocolError`, and an imported declaration is `ImportedDeclarationModified`.

`{ "kind": "removeFunctionParameter", "parameterId": "<existing>" }` removes one function parameter. Every direct call of the function loses its argument binding for it; the bound value node stays in the caller graph. Every obligation for the parameter, open or resolved, is retired. The review's `parametersRemoved` entries have `ownerFunctionId`, `parameterId`, `displayName`, `affectedCallNodeIds` and `retiredObligations` (records in the `functionsRemoved` form); the function and its callers are in `affectedFunctionIds`. It is rejected while the body still references the parameter (`ParameterStillReferenced`), when the function is used other than as a direct call (`ParameterRemovalNonCallUse`, naming the users as `ParameterAdditionNonCallUse` does), when a function that would lose an argument binding declares effects (`ParameterRemovalMayDiscardEffects`), and for a parameter added earlier in the same transaction (`ParameterCreatedInTransaction`). Removing the only parameter that mentions a type parameter still used by the result type or body fails the final validation as `InvalidProposedSnapshot` with the validator's `TypeParameterNotDeclared`.

`{ "kind": "removeUnionVariant", "variantId": "<existing>" }` removes one Union variant. Every `MatchUnion` arm drops it; an arm left with no variant is removed with its nested body; a shared arm left with one variant binds that variant's fields (with new pattern-binding IDs derived from the transaction), since a one-variant arm binds each field exactly once. The review's `unionVariantsRemoved` entries have `ownerTypeId`, `variantId`, `displayName`, `removedFieldIds` and `affectedMatchNodeIds`; the type and the match owners are in `affectedTypeIds` and `affectedFunctionIds`. It is rejected while any `UnionConstruct` builds the variant (`UnionVariantStillConstructed`), for the Union's last variant (`UnionVariantLast`), when a function whose arm would be dropped declares effects (`UnionVariantRemovalMayDiscardEffects`), and with `UnionVariantStillReferenced` for any validation issue the removal itself introduces, for example an obligation owned by a removed arm. `parametersRemoved` and `unionVariantsRemoved` appear in the diff only when non-empty. Renames and removals of imported declarations are rejected as `ImportedDeclarationModified`.

`{ "kind": "deleteCapabilityOperation", "operationId": "<existing>" }` removes one unused operation without deleting its owning Capability or siblings. Invocation references (including nested graphs) must be repaired or removed first. The review's `capabilityOperationsRemoved` entries contain `ownerCapabilityId`, `operationId`, `displayName`, and `removedParameterIds`; HTML review also shows the removed identities. An empty Capability is retained, and its values and type references remain valid. A caller may be deleted earlier in the same batch, and an Effect that is no longer referenced may be deleted afterward. Unknown targets fail with `TargetNotFound`, surviving invocations with `CapabilityOperationStillReferenced`; failed batches publish no changes. Imported operations are read-only, just like their owning Capability.

`{ "kind": "addCapabilityOperation", "capabilityId": "<existing>", "displayName": "<new>", "parameters": [{ "displayName", "type": <TypeRef> }], "resultType": <TypeRef>, "effectId": "<existing>", "implementations": [{ "constructNodeId": "<existing>", "functionId": "<existing>" }] }` adds one operation to an existing Capability, the counterpart of `deleteCapabilityOperation`. The Capability keeps its ID; the operation and parameter IDs are system-owned and appear in the review. A [program implementation](program-capability-implementations.md) must cover exactly the Capability's operations, so every `capabilityConstruct` node of the Capability (in any function, nested bodies included) needs exactly one implementation plan naming the function that implements the new operation; `CapabilityImplementationPlanMismatch` lists the constructions otherwise, and a Capability with no construction takes an empty list. Each planned function is checked with the implementation contract before the proposal is built, so a wrong signature, a generic function or an impure one rejects with the validator's own code (`CapabilityImplementationSignatureMismatch`, `GenericCapabilityImplementationUnsupported`, `ImpureCapabilityImplementation`, `UnknownCapabilityImplementationFunction`) naming the construction and its function. A blank operation or parameter name is `InvalidDisplayName`, a name another operation of the Capability has is `DuplicateCapabilityOperationDisplayName`, repeated parameter names are `DuplicateCapabilityParameterDisplayName`, an unknown effect is `EffectNotFound`, and deleting the operation in the same batch is `CapabilityOperationCreatedInTransaction`. The review diff reports `capabilityOperationsAdded` (`ownerCapabilityId` and the complete `operation` with its new IDs) and `capabilityImplementationsBound` (`ownerFunctionId`, `constructNodeId`, `operationId`, `functionId`), both present only when non-empty, and the owners of bound constructions are in `affectedFunctionIds`. Host implementations are outside the graph: a C# host must be extended alongside the published graph, as for a signature migration. Adding an operation to an imported Capability is `ImportedDeclarationModified`.

`{ "kind": "addUnionVariant", "typeId": "<existing Union>", "displayName": "<new>", "fields": [{ "displayName", "type": <TypeRef> }], "arms": [{ "matchNodeId": "<existing matchUnion>", "body": <ExpressionRecipe> }] }` adds one variant with arbitrary fields to an existing Union; the Union keeps its ID, and the variant and field IDs are system-owned and appear in the review. Because every `matchUnion` is exhaustive, each `matchUnion` node over the Union (in any function, nested bodies included) needs exactly one arm plan, the rule `addProductField` applies to constructions and `addCapabilityOperation` to implementations; `UnionMatchArmPlanMismatch` lists the matches by node and owning function otherwise. The arm `body` is an ordinary expression recipe evaluated in that arm's scope: the new variant's fields are the arm's own pattern slots at `scopeDepth` 0, referenced as `{ "kind": "patternReference", "scopeDepth": 0, "slot": "field", "field": "<new field name>" }` (by display name, since the field has no ID on the wire yet), and the match's enclosing bindings follow at depths 1 and beyond, as a targeted replacement inside the arm would see them; parameters and declarations are referenced as in any exact-ID recipe. The body is bound against the current snapshot with the new variant already present, so it may construct the new variant, and it must produce the match's type (`UnionMatchArmTypeMismatch`); a plan naming a node that is not a `matchUnion` over this Union is `UnionMatchArmPlanTargetMismatch`, an unknown node `UnionMatchArmPlanTargetNotFound`. A generic Union's new field types may name the Union's own type parameters (`{ "kind": "typeParameter", "name": "T" }` binds to the declared parameter; another name is rejected), and each arm binds the fields at the match input's type arguments. A blank name is `InvalidDisplayName`, an existing variant name `DuplicateUnionVariantDisplayName`, and removing the variant in the same batch `UnionVariantCreatedInTransaction`. The review diff reports `unionVariantsAdded` (`ownerTypeId` and the complete `variant` with its new IDs) and `unionMatchArmsAdded` (`ownerFunctionId`, `matchNodeId`, `variantId`, `patternBindingIds`), both present only when non-empty; the Union is in `affectedTypeIds` and the match owners in `affectedFunctionIds`. Constructing the new variant elsewhere is ordinary later authoring (`simulateReplaceTarget`, a new function), once the review has shown its IDs; within one batch the operation composes with the other operations, for example adding a variant while removing another and renaming the Union. The persisted field order is canonical (by ID), as for every declaration. `simulateAddUnionVariantLike` remains the form that copies an existing variant's arms instead of taking recipes.

`{ "kind": "addRequiredEffect", "functionId": "<existing>", "effectId": "<existing>" }` and `{ "kind": "removeRequiredEffect", "functionId": "<existing>", "effectId": "<existing>" }` add or remove one declared required effect. An unknown function is `TargetNotFound`, an unknown effect `EffectNotFound`, an effect already declared `FunctionRequiredEffectAlreadyPresent` and one not declared `FunctionRequiredEffectNotPresent`. The review diff reports `requiredEffectsChanged` entries `{ kind: "added" | "removed", functionId, effectId }`; a declaration removed and re-added in one batch nets out, and callers are not rewritten (the final validation checks caller/callee consistency). `{ "kind": "resolveMissingArgument", "obligationId": "<open>", "valueNodeId": "<existing>" }` binds an existing value node of the caller to the parameter an open missing-argument obligation names, attaching the argument to the obligated call; the diff reports `argumentsAttached` and `obligationsResolved` (`obligationId`, `callNodeId`, `parameterId`, `valueNodeId`). A missing or already resolved obligation is `ObligationNotOpen`; a call node that no longer exists is `ObligationTargetMismatch`.

`simulateAddUnionVariantLike` takes `{ "typeId", "sourceVariantId", "displayName", "additionalFields": [{ "displayName", "type": <TypeRef> }] }` (`additionalFields` optional). The new variant receives copies of the source variant's fields with fresh FieldIds and the same names and types, followed by the additional fields. Every `MatchUnion` arm for the source variant, in every function and nested body, is cloned for the new variant; an arm that names the source variant together with others instead gains the new variant and keeps its one body. The clone gets fresh node and pattern-binding IDs, copied field bindings are remapped to the new fields, and additional fields are bound but unused. The program therefore stays exhaustive and valid in one publication. Arm bodies can then be refined with targeted replacement, now that the new variant and field IDs exist; requests never guess future IDs. Blank or duplicate field names (including copied ones) reject with `UnionVariantEvolutionFieldDisplayNameInvalid`, and an existing variant name with `UnionVariantEvolutionDuplicateVariantDisplayName`. The earlier fieldless-only `simulateAddFieldlessUnionVariantLike` was retired on 2026-10-18; this operation with no `additionalFields` covers it. The review kind is `unionVariantEvolution` (named `fieldlessUnionVariantEvolution` until 2026-10-19, renamed with the review-shape change of [declared function type parameters](../decisions/declared-function-type-parameters.md); the implementing workflow is `AgentUnionVariantEvolutionWorkflow`), including the added variant with its fields. `simulateAddUnionVariantLikeByName` takes `{ "type", "sourceVariant", "displayName", "additionalFields": [{ "displayName", "type": <name-resolved TypeRef> }] }`, the variant resolved within the Union.

<a id="incomplete-publication"></a>**Incomplete publication.** `commit` rejects a proposal whose readiness is `incomplete` (open missing-argument obligations, for example from an `addFunctionParameter` plan that left a call missing) with `CommitRejected` and a `BlockingObligations` diagnostic listing the obligation IDs. `"allowIncomplete": true` on the commit request publishes it anyway (`CommitPolicy.AllowBlockingObligations`): the snapshot is persisted with its obligations open, the receipt's `readiness` reports them, and the program is not executable until each is resolved with `resolveMissingArgument` in a later reviewed change. Everything else about the commit is unchanged: the proposal must still be the exact reviewed candidate against the current base, and a rejected or stale proposal is not published. Use it to publish a signature change before its callers' values exist; never to publish an invalid snapshot, which no policy allows.

<a id="reference-query"></a>**Reference query.** `references` lists every site of the current snapshot that refers to one declaration or member, so an agent can repair or remove them all before a `deleteType`, `deleteEffect`, `deleteCapability`, `deleteCapabilityOperation`, `deleteFunction`, `removeProductField` or `removeUnionVariant`, each of which rejects while a reference remains. The request names `"kind"` and the subject by its exact ID key or by display names, never both: `{ "kind": "function", "functionId" | "function" }`, `{ "kind": "type", "typeId" | "type" }`, `{ "kind": "effect", "effectId" | "effect" }`, `{ "kind": "capability", "capabilityId" | "capability" }`, `{ "kind": "capabilityOperation", "operationId" | "capability" + "operation" }`, `{ "kind": "variant", "variantId" | "type" + "variant" }` and `{ "kind": "field", "fieldId" | "type" + "field" (a Product field) | "type" + "variant" + "field" }`. The reply is `{ subject: { kind, id, displayName, owner… }, count, references: [{ ownerKind, ownerId, ownerDisplayName, site, … }] }`. `ownerKind` is `function`, `type` or `capability`. `site` is `parameterType` (`parameterId`), `resultType`, `requiredEffect`, `fieldType` (`fieldId`, and `variantId` for a Union field), `operationParameterType` (`operationId`, `parameterId`), `operationResultType`, `operationFailureType`, `operationEffect` (`operationId`), or `node` (`nodeId` in the owning function's body, nested bodies included, and `role`). Roles name how the node refers to the subject: `directCall`, `callback`, `worker`, `body`, `functionValue` and `implementation` for a function; `construct`, `productUpdate`, `fieldAccess`, `match`, `patternBinding` and `typeArgument` for a type, variant or field; `capabilityConstruct`, `invoke`, `release` and `implementation` for a capability or operation. A node is listed once per role; a function's references to itself are listed with the function as owner. References inside imported declarations are listed like local ones, since a local deletion cannot repair them. An undeclared subject is `SemanticQueryFailure`; an unknown or ambiguous name, or a request naming its subject both ways, is `ProtocolError`. A deletion rejected by `TypeStillReferenced`, `EffectStillReferenced`, `CapabilityStillReferenced`, `CapabilityOperationStillReferenced` or `UnionVariantStillReferenced` lists every blocking validation issue in its message (` ; `-separated, with the count), not only the first.

`simulateProductFieldTypeMigration` takes `{ "fieldId", "newFieldType": <TypeRef>, "functionRewrites": [{ "functionId", "replacement": <recipe> }] }`. The affected set is every function that constructs the owning Product, reads the field (`FieldAccess`) or updates it (`ProductUpdate`), at any nesting depth, and it must be covered exactly (`FieldTypeMigrationRewriteMismatch`, `FieldTypeMigrationDuplicateRewrite`). Each replacement is bound and type-checked against the retyped declaration, and the whole candidate is validated once, so neither a stale construction, read or update nor a type-invalid intermediate is ever published. The TypeId, FieldId, field order, and function and parameter identities are kept; functions that neither construct the Product nor read/update the field are untouched. Union variant fields are not targets of this operation (`FieldTypeMigrationFieldNotFound`). The new field type is checked like a declared field type before any replacement is bound against it: an unknown named type or capability, a function type parameter or a wrong builtin generic arity rejects with `FieldTypeMigrationUnknownNamedType`, `FieldTypeMigrationUnknownCapabilityType`, `FieldTypeMigrationTypeParameterNotAllowed` or `FieldTypeMigrationBuiltinGenericArityMismatch`. The review kind is `productFieldTypeMigration`, with `fieldChange` (`typeId`, `fieldId`, `oldType`, `newType`) and `bodyRewrites`.

`simulateProductFieldTypeMigrationByName` takes `{ "type": <declaration selector>, "field": "<owner-local field name>", "newFieldType": <name-resolved TypeRef>, "functionRewrites": [{ "function": <declaration selector>, "replacement": <name-resolved recipe> }] }`. It resolves through the same current declarations, exact-ID/name/providing-pin/ownership guards, and owner parameter/type-parameter binding as named function replacement. It then calls the exact same atomic migration workflow. An ambiguous name or stale pin is refused; an unknown ID never falls back to its name. Imported edits still require a dependency upgrade. Exact-ID keys are not accepted in named recipes.

For example, if `elapsedOrZero(event:Event):Int64` is the only function reading `Event.elapsed`, its replacement after an Option migration is:

```json
{"op":"simulateProductFieldTypeMigrationByName","type":"Event","field":"elapsed",
 "newFieldType":{"kind":"builtinGeneric","generic":"option","arguments":[{"kind":"primitive","primitive":"int64"}]},
 "functionRewrites":[{"function":"elapsedOrZero","replacement":{
   "kind":"matchOption","input":{"kind":"fieldAccess","type":"Event","field":"elapsed","source":{"kind":"parameter","name":"event"}},
   "someBody":{"kind":"patternReference","scopeDepth":0,"slot":"value"},"noneBody":{"kind":"int64Literal","value":"0"}}}]}
```

Every constructor/read/update owner must still be repaired. `FieldTypeMigrationRewriteMismatch` keeps its code and names the missing/unrelated functions beside exact IDs. On the wire `details.repair.missing` and `unrelated` give `totalCount`, `truncated` and at most five `items`, each with `id`, `displayName`, `displayNameTruncated`, `ownership`, `sourceCount`, `sourcesTruncated` and at most five providing `{snapshotId,fingerprint}` pins. Long names are marked as truncated; unknown unrelated IDs have unknown ownership. This advice does not resolve or authorize an edit.

`simulateResultTypeMigration` takes `{ "targetFunctionId", "newResultType": <TypeRef>, "targetReplacement": <recipe>, "callerRewrites": [{ "callerFunctionId", "replacement": <recipe> }] }`. It is the result-type counterpart of `simulateParameterTypeMigration` and shares its reviewed, all-or-nothing contract. The target's FunctionId, parameters and ParameterIds are kept; the target body is replaced by a recipe of the new type; and the complete set of direct callers must each receive exactly one replacement body (`ResultTypeMigrationCallerRewriteMismatch` names missing and unrelated callers). Recipes reference parameters by stable ID and may call the target by its existing FunctionId. The target replacement may call the target itself, by its FunctionId or by `selfCall`; the call is typed against the new signature (a self call binding a parameter the target does not own is a `TargetRewriteInvalid` rejection naming `TargetSelfCallArgumentNotFound`) and persists as an ordinary DirectCall to the target. A target that already calls itself is therefore migrated like any other: because its body is replaced as a whole, its own call sites are neither callers to rewrite nor listed in `affectedCallSites`. Generic targets and callers keep their own type parameter identities in the migrated signatures and bodies. Every recipe kind is accepted in both migrations, including Option/Result construction and matching, Bind and List operations. Only one final candidate snapshot is validated and published. An unchanged type, stale base, invalid target or caller body, callback references to the target (`ResultTypeMigrationUnsupportedCallerUse`), a target or caller replacement that uses the target as a callback or function value instead of calling it directly (`ResultTypeMigrationUnsupportedRewriteUse`, and `ParameterTypeMigrationUnsupportedRewriteUse` for the parameter migration), and obligation-referenced bodies are rejected before publication. The review kind is `resultTypeMigration`, with `resultChange` (`functionId`, `oldType`, `newType`), `affectedCallSites` and `bodyRewrites`.

#### Capability operation signature migration

`simulateCapabilityOperationSignatureMigration` takes `{ "operationId", "parameterTypes": [{ "parameterId", "type": <TypeRef> }], "resultType": <TypeRef>, "functionRepairs": [{ "functionId", "parameterTypes": [{ "parameterId", "type": <TypeRef> }], "resultType": <TypeRef>, "replacement": <recipe> }] }`. `parameterTypes` lists every existing operation parameter exactly once, and each repair lists every existing parameter of its function exactly once (`OperationSignatureMigrationParameterMismatch`, `OperationSignatureMigrationRepairSignatureMismatch`). Parameter count, order and names, effects and `FailureType` are unchanged; the capability, operation, parameter and function IDs are kept. The affected set is derived from actual uses: every function that invokes the operation (including nested `CapabilityInvoke`), every function mapped to it by a `CapabilityConstruct`, the functions owning those constructions, and, recursively, every function that references an affected function whose signature changes. The repairs must cover exactly this set (`OperationSignatureMigrationRepairMismatch` names missing and unrelated functions; `OperationSignatureMigrationDuplicateRepair`). All repaired signatures are installed before any replacement is bound, each replacement is bound against them (`OperationSignatureMigrationRepairInvalid` carries the binding code), and the whole candidate is validated once before registration. New types are checked like declared types (`OperationSignatureMigration…` type-reference codes). An unchanged signature (`OperationSignatureMigrationTypeUnchanged`), an unknown operation (`OperationSignatureMigrationOperationNotFound`), a stale base (`OperationSignatureMigrationExpectedBaseMismatch`) and an obligation-referenced body (`OperationSignatureMigrationBodyReferencedByObligation`) reject before publication; migrating an imported Capability is `ImportedDeclarationModified`. `simulateCapabilityOperationSignatureMigrationByName` takes `capability` and `operation` names instead of `operationId`, `parameter` names instead of IDs, and `function` names in repairs; type parameters already declared by a repaired function keep their identities. The review kind is `capabilityOperationSignatureMigration`, with `diff` (`capabilityId`, `oldOperation`, `newOperation`, `signatureChanges` as before/after function summaries, `bodyRewrites`) and `functionEffects`. The [decision](../decisions/capability-operation-signature-migration.md) records the rationale.

`runPure` also accepts Products as `{ "kind": "product", "typeId": "<stable TypeId>", "fields": [{ "fieldId": "<stable FieldId>", "value": { "kind": "int64", "value": "42" } }] }` in arguments and expectations, and emits the same shape in results, with display names added beside the IDs (see *Display names in run output*). Type and field identities, not display names, determine the shape: each declared field must occur exactly once with a value of its exact declared type. A field value uses the same tagged run-value format as a top-level value of that type (for example a flat `list` with `itemKind` for `List<String>`, a nested `list` with `itemType` for `List<Item>`, or another `product`/`union`/`result`), and is validated recursively. Missing, duplicate, foreign or mistyped fields reject with `RunProductShapeMismatch` (also for an inner Product); a representation error inside a field, such as a typed List whose child has the wrong scalar type, rejects with `RunContainerTypeMismatch`; a different type identity rejects as an argument/expectation type mismatch. The limit is 256 fields and, for each input/expectation Product, 65536 aggregate String UTF-16 code units. Empty Products are valid. Field input order is irrelevant; responses (including `expected`) sort fields by stable ID, and comparisons use this canonical order. Int64 field values use decimal strings in responses. The runner uses generated constructor/property symbols derived from validated IDs, never caller-supplied C# expressions.

Unions use `{ "kind": "union", "typeId": "<stable TypeId>", "variantId": "<stable VariantId>", "fields": [{ "fieldId": "<stable FieldId>", "value": { "kind": "string", "value": "payload" } }] }`. A fieldless variant uses `fields: []`; `typeId`, `variantId`, and `fields` are always required. The variant must belong to that Union, and fields must exactly cover the selected variant with values of their declared types, in the same recursive format as Product fields; foreign/unknown variants and field-shape errors reject with `RunUnionShapeMismatch`. As with Products, field order is irrelevant and responses sort fields by stable ID. Equality compares Union identity, variant identity, and fields, so distinct fieldless variants never match. Input/expectation String payloads share the 65536 aggregate UTF-16 limit. This slice accepts Unions with 1–256 variants, each with at most 256 fields of supported types. **All** variants must satisfy that restriction, even if the supplied or expected variant has no fields. Runtime null/unknown variants are process diagnostics, never silently converted into a valid variant.

List/Option may contain supported non-scalar values, including other Lists/Options, Results, Products and Unions. Use `itemType: <TypeRef>` instead of `itemKind` for these containers, and **fully tagged** child values: `{ "kind": "list", "itemType": { "kind": "builtinGeneric", "generic": "option", "arguments": [{ "kind": "primitive", "primitive": "int64" }] }, "items": [{ "kind": "option", "itemKind": "int64", "hasValue": false }] }`. A nested Option uses `{ "kind": "option", "itemType": <TypeRef>, "hasValue": true, "value": <tagged value> }`, or omits `value` when false. `itemType` is mandatory even for empty Lists/None. Scalar elements accept either the original `itemKind`/raw-scalar format or `itemType` with fully tagged children; specifying both metadata fields is invalid. Every child must match the declared item type, and named field identities are checked recursively. An invalid nested item type yields `RunContainerTypeMismatch`. Responses preserve this distinction between flat and nested formats.

Results with at least one non-scalar side use a nested form with full type references instead of `okKind`/`errorKind`: `{ "kind": "result", "okType": <TypeRef>, "errorType": <TypeRef>, "isOk": true, "value": <tagged value of the active side> }`. Results whose sides are both String/Bool/Int64 accept this typed form as well as the flat scalar form. A payload that does not match the active side rejects with `RunContainerTypeMismatch`. Mixing `okType` with `errorKind` (or the reverse) is a protocol error. Responses retain the existing flat scalar shapes, including canonicalized `expected`, fake case arguments and recorded call values. Typed scalar inputs and legacy scalar expectations (or the reverse) compare equally. These rules apply recursively and to fake responses; the existing depth, item, string and node limits still apply.

Float64 uses `{ "kind": "float64", "value": <number or string> }`. A finite value other than -0.0 is a JSON number; responses write the shortest decimal that reads back to the same binary64 (for example `0.1`, `3.5000000000000004`, `1E+308`, `5E-324`), and requests may write any JSON number, read as the nearest binary64 (`1e-400` reads as 0). A number beyond the finite range, such as `1e400`, is a protocol error. NaN, +Infinity, -Infinity and -0.0 are the strings `"NaN"`, `"Infinity"`, `"-Infinity"` and `"-0"`; any other string is a protocol error, and a request may also write -0.0 as the number `-0`. Float64 has no flat container form: `itemKind`, `okKind` and `errorKind` do not accept it, so Lists and Options of Float64 and Results with a Float64 side use the nested form (`itemType`/`okType`/`errorType`), as Unit does. Expectations, fake `cases` keys and mismatch reports compare Float64 bitwise after canonicalizing every NaN to one value: `"NaN"` matches any NaN, `"-0"` does not match `0`, and there is no tolerance. The generated runner reports Float64 results and call arguments by their exact bits, so nothing is rounded in transit. See the [decision](../decisions/float64-conversion-and-run-values.md).

Bits32 uses `{ "kind": "bits32", "value": <integer> }`, carried like Int64 as its unsigned value `0..4294967295`: requests may write a JSON integer or an exact decimal string of ASCII digits, and responses always write a decimal string (`"4294967295"`). A negative value, a value above `4294967295`, a sign, a fraction, hexadecimal text or any other string is a protocol error; values are never wrapped on input (use `Bits32FromInt64` in the program for that). Bits32 has no flat container form either, so Lists, Options and Results of Bits32 use the nested form. Expectations, fake `cases` keys and mismatch reports compare the 32 bits exactly. See the [decision](../decisions/bits32-domain.md).


Each argument, expectation, and result is limited to 32 composite layers along any path (List, Option, Result, Product and Union each count; scalar leaves do not), 8192 total value nodes (including scalar fields and container payloads), 4096 elements per List, 256 fields per Product or Union value, and 65536 aggregate String UTF-16 code units. A fake script has at most 256 operations, each with at most 256 responses and 256 argument-keyed cases of at most 256 arguments. The build is limited to 30 s and the run to 5 s (see below). The aggregate String and layer **output** limits are enforced by the generated runner as well. Output budget violations are process diagnostics; input budget violations reject before building (a wire value deeper than 32 layers is a protocol error). These are value-conversion bounds, not a sandbox or a bound on the function's internal allocations: the child process runs with the user's permissions and has **no memory bound**, so a function that allocates without limit is stopped only by the 5 s run limit or by the machine. A type is supported only if every **acyclic** path through containers, Result arguments and declared fields stays within eight composite layers and its expansion, with each recursive reference counted once, has at most 131072 type nodes; otherwise the request rejects with `RunResultTypeUnsupported` (result) or `RunContainerTypeMismatch` (item/payload) before building. Only values of recursive named types, such as `Node { next: Option<Node> }` or a `Tree` Union whose variant holds `List<Tree>`, can exceed eight layers, so the 32-layer value bound applies to them. The runner encodes each named result type with one generated function, so recursion does not expand the generated code. Responses for deep recursive values can nest more than 64 JSON levels; clients should parse with a matching depth allowance.

When an expectation does not match, the response's `mismatch` locates the first difference by semantic identity: `{ "path": [...], "expected": <tagged value>, "actual": <tagged value> }`. Path steps are `{ "kind": "field", "typeId", "fieldId" }` (plus `type` and `field` display names), `{ "kind": "item", "index" }` (zero-based List position), `{ "kind": "some" }`, `{ "kind": "ok" }` and `{ "kind": "err" }`; fields are visited in canonical stable-ID order. The path stops where the values stop sharing a shape: different Union variants, Result tags, Option presence, List lengths after an equal common prefix, or scalar values. `mismatch` is null when there is no expectation or it matches.

A failure raised by the program while it runs, rather than by the runner's value conversion, is `RunRuntimeFailure` with `exceptionType`, `message`, the entry `functionId`, `sourceSnapshotId`, and `frames`, innermost first: `{ "kind": "function", "functionId" }` or `{ "kind": "capabilityOperation", "operationId" }`. Frames are mapped from generated symbols through the emitted symbol manifest; frames without a semantic declaration (runtime helpers, the runner itself) are omitted, and at most 256 are kept. Unbounded `DirectCall` recursion is valid in the language. A self call in tail position runs as a loop ([expression authoring](expression-authoring.md#selfcall)), so an endless one ends as `RunTimeout`; other recursion is reported as `System.StackOverflowException`, with frames recovered from the runtime's crash report and a message saying the recursion was too deep, that a self call in tail position runs as a loop, and pointing to `ListFold` (over `StringCodePoints` for text); a small function reaches only several thousand nested calls. On Linux the runner process opts out of core dumps (`PR_SET_DUMPABLE` 0) before running the function, so a crash handler such as systemd-coredump does not hold the aborted child past the run's time limit. Output conversion limits (layers, value nodes, String budget, null Strings, unknown variants) remain `RunProcessFailure`, and timeouts remain `RunTimeout`, whose message names the timed-out step (the build or the pure function) and its limit.

A capability parameter takes a fake instead of a value: `{ "kind": "fakeCapability", "capabilityId": "<stable CapabilityId>", "operations": [{ "operationId": "<stable CapabilityOperationId>", "responses": [{ "kind": "return", "value": <tagged value> }, { "kind": "throw", "message": "..." }] }] }`. In this ordered form, each call to an operation consumes its next response in order (or use [argument-keyed cases](#argument-keyed-fake-responses)): `return` yields a value of the operation's declared result type, and `throw` raises a host exception from the operation, as a failing external implementation would. Operations that are not listed have no responses. `{ "kind": "awaitCancellation", "value": <tagged value> }` blocks like a long-running external process until the calling `ParallelAll` worker's or task's cancellation is requested, then returns the value. `return` and `throw` responses may add `"delayMillis": "<non-negative Int64>"`: the call then answers after that much virtual time. A delay is not interrupted by cancellation; use `awaitCancellation` for work that stops when asked. Both are accepted only for programs that use `ParallelAll`, a task construct or `CancellationRequested` (`RunBindingShapeMismatch` otherwise).

Such programs run on a **virtual clock**, so a run is deterministic. One thread runs at a time: a started task or `ParallelAll` worker waits for its turn, and the running thread gives way only when it blocks (on a delay, `awaitCancellation`, `TaskWait`, a `ParallelAll` join or a scope's exit) or finishes. The next thread to resume is, in order: an elapsed delay, by (due time, start order), so everything due at a time has happened before a wait observes it; then a thread that can continue (a new task, or a wait whose condition holds or whose limit has elapsed), lowest start order first, with the entry function first and tasks and workers numbered as they start. Only when nothing can continue does virtual time jump to the earliest pending due time or `TaskWait` limit. Due times saturate at `Int64.MaxValue`: a delay or limit that would overflow virtual time never elapses on its own, and virtual time never wraps negative. Real elapsed time never affects the result, and fake responses are consumed in that deterministic order. If every thread is blocked and nothing is due, the run fails with `RunRuntimeFailure` (`InvalidOperationException`, "Every task is blocked and no delay is pending…") instead of hanging. Fakes are thread-safe: responses are consumed atomically in call order within the selected queue, and `calls` are recorded in the order they happen across workers and tasks. A call with no response left fails with `RunBindingExhausted`; a `throw` fails with `RunRuntimeFailure` and `exceptionType` `FakeCapabilityException`. Both carry frames (starting with the `capabilityOperation` frame) and the calls made so far. Fakes are accepted only as top-level arguments whose parameter has exactly that capability type. The capability must exist, operations must be distinct members of it (at most 256, each with at most 256 responses), and return values must match the declared result type (`RunBindingShapeMismatch`). A fake inside another value or response is `RunBindingPlacement`. Because the program may call any operation, **every** operation of a faked capability needs parameter and result types that run values support; otherwise the request fails with `RunBindingTypeUnsupported`. Unit values use `{ "kind": "unit" }`; containers of Unit use the nested form. `failureType` is [retired](../decisions/capability-failure-type-retired.md): a request that sets it is a protocol error, and an older snapshot that still carries one fails as a session backend error; express expected failures as `Result` return values. Response values and throw messages count toward the argument's value, String and UTF-16 limits.

A capability parameter may instead be bound to an explicitly registered host implementation: `{ "kind": "hostCapability", "capabilityId": "<stable CapabilityId>", "implementation": "Example.Hosts.Directory" }`, with the request's `hostSources: ["Hosts.cs"]` listing the C# files that define it. Host sources are **disabled by default**: unless the session process was started with `--allow-host-sources` (a startup flag of `open`, `create`, `pin` and `upgrade`, never a request field), any request with `hostSources` or a `hostCapability` argument fails with `RunHostSourcesDisabled` before a source is read or anything is built. Relative paths resolve against the directory that contains the session's snapshot file (`--snapshot`), not the process working directory or an adapter's workspace; at most 16 existing `.cs` files of at most 1 MiB each are accepted, and `hostSources` must be present exactly when some argument is a `hostCapability` (otherwise `RunHostSourceInvalid`). `implementation` must be a dotted C# type name (`RunBindingShapeMismatch` otherwise) with a public parameterless constructor implementing the generated capability interface. Host authors write against the generated names reported by `emitCSharp`'s symbol manifest; a `String` parameter or result is the generated `NyStr`, which converts implicitly to and from `string`. The sources are compiled beside the generated program with warnings as errors, so compile errors are `RunProcessFailure`. The runner wraps the implementation in a generated decorator that records every call exactly as for fakes, so `calls` and runtime frames (host method and decorator as `capabilityOperation` frames, then callers) are reported for host bindings too. Host exceptions are `RunRuntimeFailure`; expected failures belong in the operation's `Result` type. Host code runs with the user's permissions in the bounded child process; enabling host sources and registering them are explicit trust decisions, not a sandbox. Scripted fakes need no opt-in.

For `ParallelAll`, host bindings must add `"supportsConcurrentCalls": true` (omitted/false means sequential only). This asserts support across all operations and aliases of the capability; every supplied host instance of that capability must agree. Scripted fakes already satisfy the shared-state contract. Unasserted worker bindings fail with `ConcurrentCapabilityBindingRequired`, including semantic IDs in `details`, before building or invoking host code. The [sharing contract](parallel-capability-sharing.md) specifies ordering and visibility. Fake response consumption and logging are atomic together; waits/returns/throws run outside that critical section, so cancellation remains possible.

Successful responses include `calls`, in recorded invocation order (not worker completion or source-index order): `{ "parameterId", "operationId", "arguments": [{ "capabilityParameterId", "value" }] }`, with arguments sorted by stable ID (display names are added beside these IDs; see below). A run may make at most 1024 calls, and calls are encoded with their own 8192-node and String budgets; exceeding them is a `RunProcessFailure`. Functions that declare effects but receive no capability are run like any other function. Declared effects need no binding, because only a capability value can perform one.

**String run values.** A String run value is any sequence of UTF-16 code units, like a String in the language: a lone high or low surrogate, or a low surrogate before a high one, is a valid value, not an error. On the wire it uses JSON's own escapes in both directions. A request spells a lone surrogate as `\uD800` (any `\uD800`–`\uDFFF` escape that does not form a pair), which standard JSON parsers such as JavaScript's `JSON.parse` read as that code unit. A response writes every lone surrogate the same way, with uppercase hex digits. JavaScript's `JSON.stringify` also escapes lone surrogates (in lowercase), and a request may use either case. This holds for top-level and nested Strings (List, Option and Result payloads, Product and Union fields), expectations, fake case arguments, fake return values, throw messages, recorded `calls`, `mismatch` values and the `message` of a runtime failure. Parsers that insist on well-formed UTF-16, such as .NET's `JsonElement.GetString`, refuse such a string, so a client that needs lone surrogates must read it with a parser that keeps them. Well-formed Strings are encoded exactly as before. Equality is ordinal over code units, so `\uD800` and `\uDC00` are different values and a lone half never matches a pair. The UTF-16 length limits count code units.

`runPure` accepts `{ "functionId": "<stable ID>", "arguments": [{ "kind": "string", "value": "..." }], "expected": { "kind": "string", "value": "..." } }` in addition to `id`/`op`. Values support `string`, `bool`, and `int64` (Int64 uses an exact decimal string in responses), `float64` as described above, plus flat Lists encoded as `{ "kind": "list", "itemKind": "int64", "items": ["1", "2"] }`. `itemKind` is required even for empty Lists and accepts `string`, `bool`, or `int64`. Items are raw scalar values; Int64 output items are decimal strings. Scalar Options use `{ "kind": "option", "itemKind": "int64", "hasValue": true, "value": "0" }` or `{ "kind": "option", "itemKind": "int64", "hasValue": false }`. `itemKind` is mandatory for None as well as Some. None forbids `value`; Some requires a non-null scalar value. Some(false), Some(0), and Some("") remain distinct from None. String validation and limits also apply to Some payloads. Scalar Results use `{ "kind": "result", "okKind": "int64", "errorKind": "string", "isOk": false, "value": "missing" }`. Both kinds and the boolean `isOk` tag are mandatory even for the inactive side; each kind is `string`, `bool`, or `int64`. `value` is a required non-null raw scalar of the active side's type. Int64 payloads are decimal strings in responses. Input/expectation String payloads have the same 65536 UTF-16 code-unit limit as scalar Strings. Result equality compares both type arguments, the Ok/Err tag, and the payload; different type arguments reject before execution, and equal payloads with different tags do not match. Program `Err` is a successful execution (`ok: true`), not a process failure. Products with scalar fields are also supported (see below). Unions, List/Option nesting, and nesting inside Product/Union fields and Result payloads are supported as described above. List inputs, expectations, and results are limited to 4096 elements; String List inputs/expectations have a 65536-code-unit aggregate limit. List equality is ordered, exact element equality; scalar/List and differing element types reject before execution. The generated runner converts output Lists via the existing public Fold API, without changing the backend List representation. Parameter count/types, fake bindings, result type, and expectation type are checked before building. An expectation mismatch is a successful execution with `matches: false`, not a protocol/semantic failure. The response includes `sourceSnapshotId`, `functionId`, `actual`, `expected` (or null), `matches` (or null), and `mismatch` (or null). The runner selects the entry and its transitive direct-call, function-value, callback and capability-implementation targets before semantic projection and execution lowering, conservatively including all branches. Unrelated unfinished functions and their missing-argument obligations, or unrelated functions with unordered effects, do not prevent that entry from running; reachable open obligations and unordered effects still reject. Selection changes only the execution view and never the persisted snapshot or its source identity. Behavioral verification determines concurrency from the selected functions' runtime operations; a retained but unused Task/OneShot field declaration alone does not force an otherwise sequential observation to unknown. Unrelated parallel functions do not impose concurrency requirements on a sequential entry. All type/capability declarations are retained and all capability operations remain externally bound, so an operation with a (retired) `failureType` anywhere in an older program still blocks the run. Strings in arguments, expectations, fake responses, results and calls are bounded by the runner; any sequence of UTF-16 code units is a valid String (see *String run values*). The session compiles the program in process with Roslyn, into a temporary directory, with the options of a Release `dotnet build` of the generated project: optimized, nullable enabled, warnings as errors, against the SDK's reference pack of the running .NET version. There is no MSBuild and no package restore. The SDK's code analyzers do not run. The build is limited to 30 s; the program then runs under a 5 s limit in the session's runner worker, a long-lived child process that ends when the session closes. When the `Nyrwvy.AuthoringSession` process opens a session, a background task compiles the generated runtime support once with Roslyn and starts the worker. The first run then waits neither for compiler start-up nor for the worker (about 1.8 s → 0.5 s measured; [verification](../verification/runpure-warmup-20261025.md)). The task reads no session state, and a failure in it only leaves those steps to the first run. Set `NYRWVY_RUNPURE_WARMUP=0` to skip it. The worker loads each run's built program into a fresh load context and runs its entry point on its main thread with standard output captured, so a run skips process start, runtime initialization and the compilation of framework code while the program's own code is compiled afresh, as in a child; the worker is replaced after 64 runs. A run that exceeds its limit, overflows the stack or crashes kills the worker, is reported as before (`RunTimeout`, the `System.StackOverflowException` runtime failure, `RunProcessFailure`), and the next run starts a new worker. Each run has fresh statics (its own load context) and a restored ambient execution context; a run with `hostSources` executes in a fresh child process of its own instead. Argument values and fake scripts are not compiled into the program: the program reads them from an input file, so every call of one entry over the same emitted code builds the same source. The session process keeps the built programs in a least-recently-used cache of 32 assemblies or 64 MiB, keyed by a SHA-256 fingerprint of the sources and the compiler, language, runtime and reference versions, so repeated calls skip the build. Failed builds are not cached. Results and diagnostics do not depend on whether a build was reused. See the [persistent worker decision](../decisions/runpure-persistent-worker.md). No app-specific C# harness or identity lookup by generated name is required. This is not an OS sandbox, general execution engine, or live capability runner. It requires the local .NET 10 SDK; runtime and host/process failures remain diagnostics rather than program `Result` values.

`proposalId` is the proposal transaction ID rendered as a stable-ID string. It is only a handle inside the live process and is not resumable across restart.

### Simulate review detail

Every `simulate*` request accepts optional `"detail": "compact" | "full"`; anything else is a `ProtocolError` before simulation. The default is `compact`. Compact returns `{ "proposalId", "detail", "review", "projection" }`; the proposal, validation and commit authority are unchanged ([decision](../decisions/compact-simulate-replies.md)).

- **compact** uses function identities/signatures and `body:{resultNodeId,nodeCount}` instead of full node lists. Small reviews retain receipt, readiness, diff node summaries (including literals/reference names), effects/evidence, aborts, callers/callees and obligations. The serialized **result** is bounded to 16,384 UTF-8 bytes, excluding the request-ID/ok envelope. Large arrays are prefixes, long text is a surrogate-safe prefix, and deep objects may be null; these are projections, not semantic values. Normal exact IDs/fingerprints are kept. An oversized identity is null rather than a misleading ID prefix; an exceptionally oversized receipt is null and explicitly listed for retrieval. `review.kind` and `readiness.kind` are retained, so an incomplete proposal never appears ready. Type/effect/capability reviews also obey the bound.
- **full** adds the per-node graph and `nodeTypes`. Parameter-type, result-type, Product-field-type and Capability-operation-signature migrations and union-variant evolutions have no function focus, so at `full` their review adds `rewrittenFunctions`: the complete proposed function (signature and body) of every function in `bodyRewrites` or `repairedFunctionIds`, in that order. Nodes are rendered as before: `kind` as a debug string, or with `structuredReview: true` as the structured scoped graph of `readFunction`. `structuredReview` alone does not select `full`.

`projection` reports `complete`, `requiresDetailedReview`, `maxBytes`, `originalBytes`, `omissionCount`, `omittedOmissionCount`, up to 32 `omissions:{path,kind,totalCount,shownCount}`, and `readOperation:"readProposal"`. The paths are RFC 6901 JSON pointers into the corresponding full review. A String count is UTF-16 code units (`kind:"stringUtf16"`); array counts are items and object counts are properties. Metadata itself is bounded, and its omitted count is explicit. **When requiresDetailedReview is true, retrieve the missing impact, obligations, effects or graph details before deciding to commit.** Truncation does not relax readiness, ownership or stale-base checks.

### Read a pending proposal

Semantic String literals use the same lossless UTF-16 JSON string handling as
String run values. Both exact-ID and name-resolved creation/replacement recipes
accept escaped lone surrogates. `readFunction`, structured full reviews, literal
summaries and `readProposal` preserve these code units using `\uXXXX` escapes;
U+FFFD is never substituted. The existing String/page/recipe limits are unchanged.
Truncation and pagination avoid splitting an actual surrogate pair, while a lone
surrogate is a valid one-unit page. Declaration names and IDs keep their existing
stricter decoding rules.

`readProposal` takes `{ "proposalId", "path"?: "", "offset"?: 0, "limit"?: 20, "structuredReview"?: true }`. It uses the stored pending review without resimulation or publication. `structuredReview:true` uses the same scoped graph as `readFunction`; false selects the existing debug-string full encoding. Keep the proposalId, path and encoding mode fixed while paging. The result is bounded to 8,192 UTF-8 bytes and reports:

```json
{"proposalId":"...","baseIsCurrent":true,"structuredReview":true,
 "path":"/review/diff/bodyRewrites/0/addedNodes","kind":"array",
 "offset":0,"totalCount":38,"returnedCount":20,"nextOffset":20,
 "value":["...node summaries..."],"projection":{"complete":true,"requiresDetailedReview":false,"...":"..."}}
```

`path` selects any full-review object, array, String or scalar. Object pages retain their property names; array pages retain exact item identities and order. Item/property limits are 1..20; String limits are 1..1024 UTF-16 code units. The endpoint may return fewer items to fit its bound. `returnedCount` is the count actually returned, `nextOffset` advances by that count and is null at the end. Follow it rather than assuming the requested limit was delivered. Inner omissions point to the original full-review paths and original array indices; drill into those paths to recover them. Strings never split a surrogate pair, and an offset inside a pair is rejected.

Useful paths include `/review/receipt`, `/review/readiness`, `/review/functionEffects`, `/review/diff/bodyRewrites`, `/review/diff/bodyRewrites/0/addedNodes`, and `/review/rewrittenFunctions/0/body/nodes` for a migration. First page an array of rewrite owners to obtain their exact IDs, then page the desired entry. The immutable proposal handle binds all pages even if the committed workspace advances; `baseIsCurrent:false` warns that commit will be stale, and reading never refreshes the proposal. Commit, reject, close or restart discards the handle (`ProposalNotFound`). `viewProposal` remains the human HTML projection.

### Opt-in change verification

`verifyChange` is a maintained, optional comparison of a pending structural
proposal with the current committed baseline. It reuses the runPure execution
path; it is not a new runtime, approval gate, proof system or specification
language. Calling it neither commits nor rejects the proposal. Ordinary commit
policy remains unchanged. Operations proposals and dependency-upgrade previews
without a structural candidate snapshot are unsupported.

```json
{
  "id": "compare",
  "op": "verifyChange",
  "proposalId": "<pending proposal ID>",
  "cases": [{
    "label": "preserve formatted result for this request",
    "functionId": "<stable function ID>",
    "arguments": [{ "kind": "string", "value": "request" }]
  }],
  "output": "views/change-check.html"
}
```

Each case has exactly `label`, `functionId`, `arguments`, and optionally
`expectedCandidate`. There must be 1–32 cases and each label must be nonblank.
Arguments and expectations use the exact-ID runPure value format, including
scripted fake capabilities. Omit `expectedCandidate` to preserve the baseline
result; supplying it requires that explicit result on the candidate. It is not
inferred from candidate output. Product/Union field order is canonicalized
recursively by runPure, including nested containers; actual field values remain
significant. Float64 uses the existing canonical NaN and signed-zero semantics.
`verifyChangeByName` takes the same request with each case's `function` by
display name and name-resolved run values: `arguments` resolve against the
committed snapshot, which both runs share, and `expectedCandidate` against the
candidate's declarations, so an expectation may name a type or variant the
proposal creates or renames. The reply is the one `verifyChange` gives, with the
case's `function` display name beside its `functionId`; `caseRequest` and
`casesDigest` cover the request as written. Unknown request/case fields,
including caller-supplied evidence, are rejected.

The caller can be an agent: concretize user intent into labels, reuse applicable
existing inputs/fake scripts, and supply independently chosen expectations for
intended changes before comparing the candidate. Conditions remain caller-owned;
changing them to fit candidate output is not verification. No separate formal
specification or manually maintained duplicate set of conditions is required.

Both sides run once with the same arguments and fresh identical fake response
queues. Successful sequential observations compare canonical results and the
complete ordered fake calls, including parameter/operation IDs and arguments.
Explicit expectations permit result changes only: differing effects still count
as counterexamples. Duration, allocations, unused fake responses and arbitrary
external state are not observations of this contract.

| Case status | Meaning under the supplied input/script |
| --- | --- |
| `tested-agreement` | Both sequential runs succeeded with equal results and ordered calls. |
| `intended-change-tested` | Both sequential runs succeeded, calls agree, and the candidate matches the explicit canonical expectation. |
| `counterexample` | Successful sequential runs differ in preserved observations, the explicit result mismatches, or a successful baseline is followed by a recognized mapped candidate program/fake failure. |
| `unknown` | The supported comparison cannot establish one of those observations. |

The recognized candidate-only failures are `FakeCapabilityException`,
`FakeArgumentsUnmatchedException`, `FakeResponsesExhaustedException`, and the
System exceptions `ArgumentException`, `ArgumentOutOfRangeException`,
`InvalidOperationException`, `DivideByZeroException`, `OverflowException`,
`IndexOutOfRangeException`, and `NullReferenceException`. A semantic frame for
that failure's entry function must be present. The closed list does not treat an
arbitrary exception message as a concrete regression. These are observed
counterexamples under the given fake scripts, not a claim about every valid
implementation/environment or deterministic behavior over all inputs.

Baseline failure, failure on both sides, unrecognized/unmapped exceptions,
stack/heap exhaustion, cancellation, invalid/unsupported values, compiler,
harness, process, IO and timeout diagnostics remain unknown. Known concurrent
or task-runtime entries remain unknown even if both outputs happen to agree or
the candidate alone fails. New functions lacking a runnable baseline are unknown.
Failure/cleanup/cancellation equivalence and concurrent partial-order trace
comparison are not implemented. Nothing here proves equivalence over a full
input domain. A program Result.Err is an ordinary successful result, not a runner
failure.

The outer success is `{ "evidence": ..., "reviewPath": "..." }`: it means a
report was computed/written, not that all cases passed. Evidence contains
`proposalId`, baseline/candidate snapshot IDs and fingerprints, the exact
`caseRequest` JSON string and its SHA-256 `casesDigest`, `verifierIdentity`,
`coverage`, `affectedFunctionIds`, `caseEntryFunctionIds`, and `cases`.
Verifier identity records observation policy/version, runtime/build context and
module identities. Current observation schema/policy is
`nyrwvy-change-verification-v5`; v5 preserves structured input diagnostics for
each side using the declarations captured by that execution, including candidate-only
expectation errors. Its finite-case observation policy remains the v4 policy.
Earlier experimental reports retain their
historical schemas and must not be interpreted as current observations.

Each reported case contains its label, function ID, arguments, optional expectation
(encoded as null when omitted), status and baseline/candidate observations.
A successful observation is `{ "actual", "calls", "matches", "mismatch" }`;
nullable matches/mismatch have the same meaning as runPure. A failed observation
is `{ "error": ... }` with the existing structured runPure diagnostic: `code`,
`message`, and applicable function/source snapshot IDs, exception type, semantic
frames and complete calls. For example an exhausted candidate has error code
`RunBindingExhausted` even when its case status is counterexample. Session errors
use the existing session-error shape. Display names are optional labels next to
stable IDs and use each side's declarations; names do not establish identity.
Unsupported input is a per-case unknown, whereas malformed wire input, invalid
case count/labels, stale/unavailable proposals or invalid session source fail the
outer request. Invalid case sets/unsupported proposal forms currently use
`DependencyFailure`; a stale committed base uses `ExternalModification`.

Source and pinned dependency selection are rechecked before execution and before
returning evidence. A proposal must still have the current committed base.
Rejected handles cannot be evaluated; another commit makes old-base handles
stale; closing/reopening drops in-memory proposal handles. Full resolved graph
fingerprints conservatively include dependencies and unrelated edits. They
identify revisions, not behavioral equivalence. Reports are historical,
unauthenticated artifacts; neither verifyChange nor commit accepts them back as
evidence authority. No successful verification-result cache or durable obligation
is introduced. Rerun against a new proposal after editing/reopening.

The review distinguishes structural readiness, behavioral status, affected
functions, and unique direct case entry points. Impact is the touched functions
and transitive callers across both graphs. Direct entry counts are requests, not
dynamic path/function coverage; a directly targeted function can still be unknown,
and callers without direct cases may remain unexercised.

Candidate execution denies hostCapability arguments even when the operator
allowed host sources for ordinary runPure. No hostSources field is accepted.
The existing runner's validation, value/output bounds, 30-second compilation
limit, five-second child execution limit, process cleanup and compilation cache
are reused. Up to 64 child executions can occur across 32 comparisons, sequentially;
there is no shorter aggregate-request deadline or latency guarantee. This is not
an OS sandbox. Verification preserves snapshot/dependency bytes, but writes the
requested HTML review and ordinary runner temporary/cache files. Output path
validation is the same snapshot-directory confinement as existing views.

### Inspected base snapshot

Every `simulate*` request accepts optional `"expectedSnapshotId": "<SnapshotId>"`, the snapshot the caller inspected (from `status`, or the `publishedSnapshotId` of its last commit receipt). When it is present it becomes the request's expected base, so a snapshot published in between, for example by another adapter on the same workspace, rejects the request with the workflow's existing stale-base code instead of simulating against the newer snapshot: `StructuralExpectedBaseMismatch` (body, target and function-creation requests), `ParameterTypeMigrationExpectedBaseMismatch`, `ResultTypeMigrationExpectedBaseMismatch`, `FieldTypeMigrationExpectedBaseMismatch`, `OperationSignatureMigrationExpectedBaseMismatch`, `TypeDeclarationExpectedBaseMismatch`, `UnionVariantEvolutionExpectedBaseMismatch`, `EffectDeclarationExpectedBaseMismatch`, `CapabilityDeclarationExpectedBaseMismatch`, or `StaleBaseSnapshot` for `simulateOperations`/`simulateOperationsByName`, each inside a `SimulationRejected` error. `simulateReplaceBodyByName` also accepts optional `"expectedResultNodeId"`, the result node the caller read; a different current result node is `StructuralExpectedResultMismatch`, as for `expectedCurrentResultNodeId` on `simulateReplaceBody`. Omitting either property simulates against the current snapshot and result node, as before. A `…ByName` request resolves names against the current snapshot first, so a name that no longer resolves is still a `ProtocolError`.

After commit, `readFunction` returns the published graph. `nodeCount` counts every node of the body, including those in nested branch, arm and Bind regions.

For name-resolved creation, `simulateCreateFunctionByName` accepts exactly one of `body` or `bodyFile`. `simulateCreateFunctionsByName` accepts exactly one of `functions` or `functionsFile`; the file contains the JSON array itself. Each function in the array may also use `bodyFile`. `simulateReplaceBodyByName` and `simulateReplaceTargetByName` accept exactly one of `replacement` or `replacementFile`. File paths resolve against the snapshot's directory, must remain inside it, cannot pass through links, and are limited to 1 MiB. Invalid paths and JSON are protocol errors.

### Create-function review projection

`simulateCreateFunction` (and `…ByName`) takes `displayName`, `parameters`, `resultType`, `requiredEffects`, `body` and an optional `typeParameters`: the function's type parameter names in declared order (`["T", "U"]`), each named in the types as `{ "kind": "typeParameter", "name": "T" }`. Without `typeParameters` the list is derived from the parameter types in first-appearance order; with it, every type parameter the request mentions must be listed and every listed one must be mentioned by a parameter type ([expression authoring](expression-authoring.md), generic functions). `declarations` and `readFunction` show a generic function's `typeParameters` (`typeParameterId`, `displayName`) in that order, and type parameter occurrences in its signature and body carry the owner's `displayName`. The Core function-creation proposal retains its full review model. The JSON-lines review of `simulateCreateFunction` returns the receipt/readiness, `createdFunction`, `bodyEffectRequirements` and `aborts`. It does not repeat the body through `materializedBody` or `proposedFocus`; at `detail: "full"`, `createdFunction` carries the complete body.

### Replace-body review projection

`simulateReplaceBody` already requires `expectedCurrentResultNodeId`, which callers obtain from the current function focus. Its review returns the receipt/readiness, a compact structural diff (owner function, old/new result node IDs, and added/removed node IDs), `proposedFunction`, `bodyEffectRequirements` and `aborts`, without complete `baseFocus` and `proposedFocus` projections. `ReplaceTarget` reviews keep both focuses (compact by default) and the targeted diff with node summaries: `previousTarget` is the replaced node and `proposedTarget` the node now at the target ID (the replacement's root keeps it), so a literal-for-literal edit, which adds no node, still shows the old and new value.

### Stable IDs and type references

Stable IDs are JSON strings. Existing IDs may be referenced where the semantic API already accepts them. New declaration/node identities are never supplied by the caller.

`TypeRef` uses the same shape and vocabulary as the strict snapshot codec: `primitive`, `named`, `capability`, and `builtinGeneric` with explicit generic arguments.

### Expression recipes

Expression requests carry recursively nested recipe objects with a `kind` discriminator. The discriminator follows the existing `ExpressionRecipe` case vocabulary in lower camel case, for example:

```json
{"kind":"int64WrappingAdd","left":{"kind":"parameterSlot","index":0},"right":{"kind":"int64Literal","value":1}}
```

References use stable IDs (`parameterId`, `fieldId`, `variantId`, `functionId`, `operationId`) already accepted by the corresponding `ExpressionRecipe` case. Function-creation bodies may use `parameterSlot`; replacement requests may not gain any additional slot semantics from the transport.

Calls and structured constructors use arrays of explicit target-ID/value pairs. Pattern references use `scopeDepth` plus `slot` (`field`, `value`, or `error`); a field slot additionally carries `fieldId`.

The transport parser is only a DTO-to-existing-authoring-intent adapter. Type inference, recipe bounds, materialization, ID allocation, effect checks, control-flow checks, graph construction, and declaration validation remain exclusively in the Core workflows.

## Name-resolved AI authoring

The maintained protocol also exposes a convenience layer for AI tool use when persistent stable IDs are not themselves the subject of the task. These operations resolve exact display names against the current session snapshot and immediately lower them to the existing stable-ID authoring requests:

- `simulateCreateTypeByName`
- `simulateCreateTypesByName`
- `simulateCreateFunctionByName`
- `simulateCreateFunctionsByName`
- `simulateReplaceBodyByName`
- `simulateCreateCapabilityByName`
- `simulateOperationsByName`
- `runPureByName`

This layer is not a textual source language and does not become program authority. Resolution happens inside the current single-writer session; ambiguous or missing names are rejected. `simulateCreateFunctionByName` also rejects an exact display name already held by any local or imported function before registering a proposal (`ProtocolError`). The exact-ID creation workflows enforce the same rule per declaration kind, so a retried create cannot make a name ambiguous: a function, type, effect or capability whose display name another declaration of that kind already has is rejected with `FunctionCreationDuplicateDisplayName`, `TypeDeclarationDuplicateDisplayName`, `EffectDeclarationDuplicateDisplayName` or `CapabilityDeclarationDuplicateDisplayName`, and a type or function rename whose resulting name collides is rejected with `DuplicateDisplayName` (only the transaction's final names count, so two declarations may exchange names). This is a guard on creation and rename, not a snapshot validation rule: existing snapshots and dependency sets that already contain duplicates still open (two dependencies may each declare a function with the same display name), and by-name requests against such a name fail as a `ProtocolError` naming the kind, for example `Ambiguous function 'keep'.`, instead of resolving to either declaration. Such declarations stay reachable through the exact-ID requests. Simulation, review, validation, system-owned identity allocation, commit policy, and publication are otherwise unchanged.

`declarations` now also returns `provenance: [{kind,id,ownership,sources:[{snapshotId,fingerprint}]}]`. Ownership is `local` or `imported`; local declarations have no sources. A declaration shared through a diamond lists every selected pin providing its identical content. For a flattened library these are its providing pins, not guessed original authors or lost upstream aliases. Reopen/move reconstructs this metadata from retained pins without reading original source paths.

Global declaration references in name-resolved requests and recipes accept an exact display-name string or an explicit selector `{id}` / `{name,dependencySnapshotId}`. Optional `name`, `dependencySnapshotId`, and `ownership` (`local` or `imported`) are guards on an exact-ID selector. Each selector must contain `id` or `name`; every guard must match one current declaration. An unknown ID never falls back to its name. A stale providing pin is rejected even if a declaration ID survives the update. In an existing function's replacement, a validated selector of that exact owner is a self call and supports `keepUnlisted`; selecting another same-named function still calls that other identity. Strings retain the existing ambiguity refusal. References immediately lower to the current typed stable IDs; no selector or alias becomes persisted program authority. This applies to function calls/values/callbacks/workers, type/capability references, required effects, reads and edits. Owner-local field/variant/parameter names retain their existing rules and exact-ID alternative.

For example, use `{kind:"directCall",function:{name:"render",dependencySnapshotId:"<pin from provenance>"},arguments:[]}` when two libraries provide different `render` functions. A named TypeRef takes the selector in its existing `name` slot: `{kind:"named",name:{id:"<TypeId>",name:"Measure"}}`. The ordinary `inspect`, `view` and `replace` tools accept function selectors, and `create_function.requiredEffects` accepts effect selectors. Imported selections stay read-only; selecting an imported function for a local edit does not authorize mutation.

The stable-ID operations remain the exact-identity surface for callers that already hold semantic identities. The name-resolved layer exists to remove incidental plumbing such as repeatedly discovering `TypeId`, `FieldId`, `VariantId`, `FunctionId`, `ParameterId`, or the current whole-body result node merely to express an otherwise unambiguous graph edit.

Within a named whole-body or targeted replacement, an explicit `{"kind":"typeParameter","name":"T"}` binds to the target function's already declared type parameter, including inside nested List/Option/Result types and scoped bodies. It keeps that parameter's stable identity; an unknown name is rejected instead of introducing a new parameter. The same owner binding applies to named Capability signature-repair bodies and signatures. New function creation still allocates fresh identities for the type parameters it declares (listed in `typeParameters`, or derived from its parameter types).

Name-resolved `TypeRef` uses `{"kind":"named","name":"ChangeRequest"}` and `{"kind":"capability","name":"Console"}`. Expression recipes retain the existing structural vocabulary, but semantic references use explicit owner/name selectors. For example:

```json
{
  "kind": "fieldAccess",
  "source": {"kind": "parameter", "name": "request"},
  "type": "ChangeRequest",
  "field": "environmentDependent"
}
```

A whole-body change therefore needs only the semantic target name and replacement structure:

```json
{
  "id": "replace-1",
  "op": "simulateReplaceBodyByName",
  "function": "requires_live",
  "replacement": {"kind": "boolLiteral", "value": false}
}
```

The session resolves the target `FunctionId` and current result node before constructing the ordinary reviewed replacement request.

### Self calls

A `directCall` whose `function` is the display name of the function being created (`simulateCreateFunctionByName`) or replaced (`simulateReplaceBodyByName`) resolves to a [`SelfCall`](expression-authoring.md#selfcall). Its `arguments` name the owner's own parameters, so a recursive function is created in one request:

```json
{"kind": "directCall", "function": "sumTo", "arguments": [
  {"parameter": "n", "value": {"kind": "int64WrappingSubtract", "left": {"kind": "parameter", "name": "n"}, "right": {"kind": "int64Literal", "value": 1}}}
]}
```

The exact-ID form is `{"kind":"selfCall","arguments":[{"slot":0,"value":<recipe>}]}`, with arguments keyed by zero-based parameter slot, because the new function's IDs are system-assigned. Both persist as an ordinary `DirectCall` to the owner. In `simulateReplaceBody`, an exact-ID `directCall` whose `functionId` is the function being replaced stays a `directCall` in the request and is typed as a self call: its arguments must have the owner's exact parameter types, so a generic function cannot call itself at other type arguments on any of the three forms ([expression authoring](expression-authoring.md#selfcall)).

A self call may add `"keepUnlisted": true` to pass every parameter it does not name through unchanged. A loop over `(deps, roots, root, stack, seen)` that only advances `root` is then written `{"kind": "directCall", "function": "visit", "keepUnlisted": true, "arguments": [{"parameter": "root", "value": …}]}`; the review and the stored graph show the full call. `keepUnlisted` on a call to another function is rejected.

Creation by name already rejects a display name held by any existing function, so a self call in a creation body cannot be ambiguous; if one were, it would fail as `Ambiguous function`. During replacement the target is already resolved, so a call naming the target's own display name is a self call by the target's ID, even if another function shares that name. Mutual recursion and a `functionReference` to the function being created are out of scope; they still need the placeholder-then-replace route. A callback (`listMap`, `listFilter`, `listAny`, `listAll`, `listSortBy`, `listFold`, `listEffectFold`), worker, task body, capability implementation or `functionReference` that names the function being created is a `ProtocolError` that says so and names that route: create the function with a placeholder body, create the functions it calls back, then replace its body with `simulateReplaceBodyByName`, which resolves the function's own name ([probe 8](../verification/rrawrlet-slice-probes-summary.md#probe-8-recursion-through-callbacks)).

### Recursive types

`simulateCreateTypesByName` takes `types: [{ "displayName", "typeKind" }]`, each in the `simulateCreateTypeByName` shape. A named type reference inside any member resolves first to a member of the group, then to a published type, so the members may name themselves and each other:

```json
{"id": "json-1", "op": "simulateCreateTypesByName", "types": [
  {"displayName": "Json", "typeKind": {"kind": "union", "variants": [
    {"displayName": "Str", "fields": [{"displayName": "value", "type": {"kind": "primitive", "primitive": "string"}}]},
    {"displayName": "Arr", "fields": [{"displayName": "items", "type": {"kind": "builtinGeneric", "generic": "list", "arguments": [{"kind": "named", "name": "Json"}]}}]},
    {"displayName": "Obj", "fields": [{"displayName": "members", "type": {"kind": "builtinGeneric", "generic": "list", "arguments": [{"kind": "named", "name": "Member"}]}}]}]}},
  {"displayName": "Member", "typeKind": {"kind": "product", "fields": [
    {"displayName": "key", "type": {"kind": "primitive", "primitive": "string"}},
    {"displayName": "value", "type": {"kind": "named", "name": "Json"}}]}}]}
```

`simulateCreateTypeByName` accepts its own display name the same way (for example `Tree` with `children: List<Tree>`). Both review as `{ "kind": "createTypes", "receipt", "readiness", "createdTypes": [...] }` in request order, and one `commit` publishes every member; a single declaration that names no member keeps the `createType` review. The transport gives each member a request-local reference that simulation replaces with an allocated TypeId, so no reference is persisted. A member that could never be constructed, because each of its Product fields or of its Union variants needs a group member without a value, is rejected as `TypeDeclarationUninhabited`; see the [type-declaration contract](type-declaration-authoring.md#type-groups).

`simulateCreateCapabilityByName` takes the `simulateCreateCapability` shape with name-resolved `TypeRef`s and `"effect": "<effect display name>"` in place of `effectId`. Like function creation, it rejects a display name already held by any local or imported capability. `simulateCreateEffect` already takes no references and has no separate name form.

`simulateOperationsByName` takes the `simulateOperations` request with every operation's targets by display name, each member resolved within its owner. Deletions and removals: `{ "kind": "deleteFunction", "function" }`, `{ "kind": "deleteType", "type" }`, `{ "kind": "deleteEffect", "effect" }`, `{ "kind": "deleteCapability", "capability" }`, `{ "kind": "deleteCapabilityOperation", "capability", "operation" }`, `{ "kind": "removeFunctionParameter", "function", "parameter" }`, `{ "kind": "removeUnionVariant", "type", "variant" }` and `{ "kind": "removeProductField", "type", "field" }`. Renames, each with `displayName`: `{ "kind": "renameFunction", "function" }`, `{ "kind": "renameType", "type" }`, `{ "kind": "renameField", "type", "field" }` for a Product field or `{ "kind": "renameField", "type", "variant", "field" }` for a Union variant field, `{ "kind": "renameVariant", "type", "variant" }`, `{ "kind": "renameParameter", "function", "parameter" }`, `{ "kind": "renameEffect", "effect" }`, `{ "kind": "renameCapability", "capability" }`, `{ "kind": "renameCapabilityOperation", "capability", "operation" }` and `{ "kind": "renameCapabilityParameter", "capability", "operation", "parameter" }`. Additions: `{ "kind": "addFunctionParameter", "function", "displayName", "type": <name-resolved TypeRef>, "callSites" }` (a type parameter the function already declares keeps its identity, another name introduces one, as in the exact form), `{ "kind": "addProductField", "type", "displayName", "fieldType": <name-resolved TypeRef>, "constructions" }` (`type` selects the Product, so the field's type is `fieldType`; a plan's `value` recipe is name-resolved against the function that owns its construct), `{ "kind": "addCapabilityOperation", "capability", "displayName", "parameters", "resultType", "effect", "implementations": [{ "constructNodeId", "function" }] }`, `{ "kind": "addUnionVariant", "type", "displayName", "fields": [{ "displayName", "type": <name-resolved TypeRef> }], "arms": [{ "matchNodeId", "body": <name-resolved recipe> }] }` (`type` selects the Union; each arm body resolves parameter names against the function that owns its match node and names a new field as `{ "kind": "patternReference", "scopeDepth": 0, "slot": "field", "type": "<Union>", "variant": "<new variant>", "field": "<new field>" }`, since the body is resolved against the declarations with the new variant already present), and `{ "kind": "addRequiredEffect" | "removeRequiredEffect", "function", "effect" }`. `{ "kind": "resolveMissingArgument", "obligationId", "valueNodeId" }` is accepted unchanged so a batch can mix it in. Node and obligation IDs stay exact: nodes have no names. Every name is resolved against the current snapshot before the batch is simulated (an unknown or ambiguous name is a `ProtocolError`), and the batch then runs exactly as the exact-ID operations, in order and with the same review; an unsupported `kind` is a `ProtocolError` naming the accepted kinds. Deleting dead helpers, including self-recursive ones, therefore needs no IDs: Visibility: `{ "kind": "setExported", "type" | "function" | "effect" | "capability", "exported" }`.

```json
{
  "id": "cleanup-1",
  "op": "simulateOperationsByName",
  "operations": [
    {"kind": "deleteFunction", "function": "splitFrom"},
    {"kind": "deleteFunction", "function": "utf8From"}
  ]
}
```

`runPureByName` takes the `runPure` request with `"function": "<display name>"` in place of `functionId`. Its run values use the same selectors as expression recipes, each resolved within its owner:

| Run value | Exact-ID key | Name key (resolved within) |
| --- | --- | --- |
| Product | `typeId`, fields `fieldId` | `type`, fields `field` (the Product) |
| Union | `typeId`, `variantId`, fields `fieldId` | `type`, `variant` (the Union), fields `field` (the variant) |
| Nested List/Option/Result | `itemType`/`okType`/`errorType` exact `TypeRef` | the same keys with name-resolved `TypeRef` |
| `hostCapability` | `capabilityId` | `capability` |
| `fakeCapability` | `capabilityId`, operations `operationId`, case arguments `capabilityParameterId` | `capability`, `operation` (the capability), `parameter` (the operation) |

```json
{"kind": "fakeCapability", "capability": "Provider", "operations": [
  {"operation": "lookup", "cases": [{"arguments": [{"parameter": "key", "value": {"kind": "string", "value": "a"}}],
                                     "responses": [{"kind": "return", "value": {"kind": "union", "type": "Answer", "variant": "Missing", "fields": []}}]}]}]}
```

Each operation accepts only its own vocabulary: exact-ID keys in a `…ByName` request, or name keys in an exact-ID request, fail as malformed input. The one exception is the display names that run output reports (below): an exact-ID Product/Union value may carry `type`, `variant` and field `field` beside its IDs, so a reported `actual` can be passed back as `expected` or a fake response; they are informational and ignored, and the IDs decide. An unknown or ambiguous name, or a name of the wrong kind (such as a Union for a Product value), is a `ProtocolError` before anything is built or run. Once resolved, the values pass through the ordinary `runPure` validation, so shape and binding failures keep their `Run*` codes.

**Display names in run output.** `runPure` and `runPureByName` report the same output: every exact ID stays as before, and the declaration's current display name is added as a sibling property under the name key of the name-resolved input form, so a by-name client needs no ID→name map built from `declarations`:

| Output object | Exact-ID property | Added display name |
| --- | --- | --- |
| Result / runtime failure / unsupported-run error | `functionId` | `function` |
| Product / Union value (in `actual`, `expected`, `mismatch`, call arguments) | `typeId`, `variantId`, fields `fieldId` | `type`, `variant`, fields `field` |
| Mismatch path `field` step | `typeId`, `fieldId` | `type`, `field` |
| Call (`calls`, including runtime failures) | `parameterId` (the function's capability parameter), `operationId`, arguments `capabilityParameterId` | `parameter`, `capability` and `operation`, arguments `parameter` |
| Runtime frame | `functionId` / `operationId` | `function` / `capability` and `operation` |

```json
{"parameterId": "…", "parameter": "provider", "operationId": "…", "capability": "Provider", "operation": "lookup",
 "arguments": [{"capabilityParameterId": "…", "parameter": "key", "value": {"kind": "string", "value": "a"}}]}
```

A name is omitted only when its ID is not declared in the current snapshot. Nested `itemType`/`okType`/`errorType` `TypeRef`s stay in exact-ID form. The change is additive: clients reading IDs are unaffected.

Validation and structural-edit diagnostics that name a field, capability operation or parameter, function or effect print the display name next to the ID, for example `Field 'task' (<id>) uses TaskScope…` (`TaskTypeInDeclaredType`) or `CapabilityInvoke operation 'lookup' (<id>) requires effect 'io' (<id>)…` (`ExpressionCapabilityMissingEffectRequirement`). Diagnostic codes are unchanged.

Runner shape/type errors keep their existing codes and now report `details: {path,expectedType,actualType,reason}` when a bounded input defect can be located. `path` starts with `arguments` and the parameter name, or `expected`, then names Product/Union constructors, fields, item indices, and Map key/value positions. Missing or undeclared fields use a null expected/actual type where no value or declaration exists. The message includes the path. Duplicate fields/items/keys and scalar flat-versus-tagged wire mismatches have explicit reasons; accepted wire representations and value budgets are unchanged. Malformed JSON and parser-level failures still use the protocol parser's diagnostics.

Input details follow the validation category of the returned error, even when several arguments or nested values are invalid. Generic/task entry refusals, unsupported results and runtime errors do not acquire unrelated input-defect details.

Proposals that would introduce such an ambiguity are refused earlier, at simulation, with an `InvalidProposedSnapshot` diagnostic whose message starts `AmbiguousEffectOrder:` and names the function, both nodes with their kinds and callee or operation names, and the Bind repair ([derived runtime ordering](runtime-ordering.md)); the lowering failure below remains for functions inherited unchanged from older snapshots. An `ExecutionLoweringFailure` caused by `AmbiguousEffectOrder` retains the exact function and node IDs and adds owner/operation display names, operand kinds, and a `Bind` repair hint. The author must choose the intended sequence; the tool never invents an order. Names supplement identities, so identical display names remain distinguishable. Startup diagnostics without declaration context retain their existing form.

This direction is consistent with evidence from structure-aware coding-agent interfaces such as [CODESTRUCT (ACL 2026)](https://aclanthology.org/2026.acl-long.607/), which found that operating on named AST entities instead of text spans can improve reliability and reduce token use. Nyrwvy does not treat that work as design authority or as evidence that every graph interface is superior. The relevant hypothesis is narrower: an AI-facing structured action space can remove text-position and identity-reconstruction work. Nyrwvy applies that idea to its authoritative typed semantic graph rather than translating the edit back into authoritative source text.

## Declaration visibility

Types, effects, capabilities and functions carry a visibility ([decision](../decisions/declaration-visibility.md)). A declaration is **private** unless its creation request says `"exported": true` (`simulateCreateType`, `simulateCreateTypeByName`, each item of `simulateCreateTypesByName`, `simulateCreateEffect`, `simulateCreateCapability`, `simulateCreateCapabilityByName`, `simulateCreateFunction` and `simulateCreateFunctionByName`; the shared `nyrwvy_create_type` and `nyrwvy_create_function` tools take `exported`), and `setExported` changes it afterwards. Inside its own snapshot every declaration is usable whatever its visibility. Across a dependency only exported declarations are: a dependency's private declarations are left out of `declarations` (whose entries carry `exported`), of provenance and of name resolution, a new exact-ID reference to one is `ImportedDeclarationNotExported`, and `setExported` on an imported declaration is `ImportedDeclarationModified`. `previewDependencyUpgrade`, `previewDependencyUpgrades` and the selection preview list each added, removed or changed declaration with its `exported` flag, exported ones first in each list, since only they can affect a dependent; an existing local reference to a declaration the new version no longer exports is reported as an `ImportedDeclarationNotExported` issue (`compatible: false`), and `simulateDependencyUpgrade` rejects such a selection with the same code. Making a declaration private that a dependent uses cannot be checked by the declaring session, which does not know its dependents; the dependent learns it from the preview. The session does not check that an exported signature mentions only exported declarations. Persistence: snapshot schema 21 (`nayamnyam.snapshot.v17`) writes `"exported": true` for an exported declaration and omits it for a private one; a document below 21 reads as all-exported ([schema versions](schema-evolution-policy.md#snapshot-schema-versions)). Visibility is part of both fingerprints.

## Snapshot migration

`Nyrwvy.AuthoringSession migrate --snapshot <local>` rewrites a workspace to the current snapshot schema (JSON 21, schema identifier `nayamnyam.snapshot.v17` in the migrate report) under the rules of the [schema evolution policy](schema-evolution-policy.md#migration-is-not-an-ordinary-semantic-edit). It is the migration step of the [legacy cutover](../plans/post-m2-roadmap.md#legacy-cutover-planned): once the old readers are removed, a document below the current version is opened by migrating it first. The command takes the single-writer lock, rewrites, validates, writes and exits; it starts no session and answers no JSONL request.

What it rewrites, in the local snapshot and in every dependency retained in the sidecar:

- A node of a [retired kind](../decisions/retired-authoring-kinds.md) becomes its replacement: `StringEqual` and `Int64Equal` become `ValueEqual`; `Int64GreaterThan(a, b)` becomes `Int64LessThan(b, a)`; `MapGetOrDefault(m, k, d)` becomes `OptionGetOrDefault(MapGet(m, k), d)`; `Int64LessThanOrEqual(a, b)` becomes `BoolNot(Int64LessThan(b, a))`; `Int64GreaterThanOrEqual(a, b)` becomes `BoolNot(Int64LessThan(a, b))`. The rewritten node keeps its ID on the node that yields the same value (the outer one), so every reference to it is unchanged; the inner node of a two-node replacement gets a deterministic ID derived from the replaced node's ID (`SnapshotMigration.innerNodeId`), so migrating the same document twice derives the same identities. These are the only new identities a migration creates.
- A legacy source-only dependency manifest (`path`, `snapshotId`, `fingerprint`) becomes retained content, exactly as `pin` retains it: the source at `path`, or the exact copy named by `--dependency`, must have the pinned fingerprint. A retained dependency's content is migrated like the local snapshot and re-embedded at the current schema; its manifest `fingerprint` and the local snapshot's `dependency.digest` are rebound to the migrated content.
- A document below schema 21 has its visibility and function type parameter lists made explicit: every declaration is written `"exported": true` (which is what it read as) and every generic function gets the derived list ([declaration visibility](../decisions/declaration-visibility.md), [declared function type parameters](../decisions/declared-function-type-parameters.md)). A document at 21 or later keeps the visibility and lists it declares.
- A snapshot (local or dependency) whose capability operation sets the retired `FailureType` is rejected with `MigrationRejected`, naming the operation, and nothing is written ([decision](../decisions/capability-failure-type-retired.md)).

Every other stable ID is preserved. The result is written at the current version in its explicit form (visibility markers and declared lists written even where the smallest version would omit them), after validating the resolved graph; a workspace with a dependency is replaced as a pair with the same rollback as an upgrade. A workspace already in that form is left byte-identical (`"changed": false`), so the command is idempotent.

The command prints a JSON report, the migration's evidence, and exits 0: `tool` and `toolVersion` (with the build's commit), `path`, `changed`, the source and target schema (`sourceSchemaVersion`/`sourceSchema`, `targetSchemaVersion`/`targetSchema`), the snapshot and semantic fingerprints `before` and `after` (of the resolved graph, as `status` reports them), `rewrites` (each retired kind rewritten, with its count), `declarationsMarkedExported`, `functionTypeParameterListsDeclared`, `semanticFingerprintExpectedEqual`, and `dependencies` with the same fields per retained member plus `storageBefore` (`embedded` or `legacySource`). `semanticFingerprintExpectedEqual` is true when the migration changed representation only (no retired node rewritten anywhere); the command checks semantic fingerprint equality for each such dependency and the resolved graph before replacing either file, rejecting drift with `MigrationRejected`. A rewritten retired node is a graph change: the same value is computed, which `runPure` shows, but the snapshot and semantic fingerprints move, so a dependent of the migrated snapshot must be migrated too (its sidecar is, when the command runs on it). A failure (`SnapshotFileNotFound`, `LockUnavailable`, `DependencyFailure`, `MigrationRejected`, a codec or validation failure) is written to stderr as `<code>: <message>` with exit status 2, as for a session that cannot start.

`--to <new path>` converts instead of rewriting in place: the migrated snapshot and its sidecar are created at the new path (and `<new path>.dependency.json`) in the form the new extension selects ([persistence format](#persistence-format): `.nyrec` for records, anything else JSON), the source files are left untouched, and both paths are locked while the command runs. The target and its sidecar must not exist (`SnapshotFileAlreadyExists`). The snapshot is created before its sidecar, and a failed sidecar creation removes the snapshot again, so a reported failure leaves no orphan at the target. A process killed between the two writes can still leave the target snapshot without its sidecar: opening it reports the missing sidecar, and since the source is untouched, deleting the target and running the command again recovers. The report carries `target` and `"changed": true`; its `after` fingerprints are computed from the text written, so they are evidence of the conversion. A conversion is representation-only by contract: `semanticFingerprintExpectedEqual` is true and a changed semantic fingerprint is rejected with `MigrationRejected`, so a document that still holds retired nodes is migrated in place first and converted afterwards. Each dependency keeps the embedded form its own extension selects. Run on a `.nyrec` workspace without `--to`, the command reads and writes records; a record document is always at the current schema.

Save stdout as the durable migration report. Validation, fingerprint and lock failures leave the snapshot and sidecar unchanged. A derived inner-node ID collision fails validation rather than replacing an existing identity. File replacement has the same persistence limits as an upgrade: a reported snapshot-write failure attempts sidecar rollback; rollback failure is reported explicitly, and a process interruption between the two replacements can leave a mismatched pair. While the pair is replaced the previous sidecar is kept as `<snapshot>.dependency.json.previous` and removed once both files are consistent again (after success, or after a successful rollback); when `open` finds a sidecar that does not match the snapshot but a `.previous` that does, it fails with `DependencyFailure` naming that file to restore over the sidecar, and never restores it silently. This command still does not promise a crash-atomic two-file transaction.

## Persistence format

The persisted form follows the file extension, with no content sniffing: a `.nyrec` path is written and read in the [record form](../decisions/snapshot-record-format.md) (`RecordCodec`), and every other path keeps the strict JSON snapshot codec exactly as before. Both forms are the same validated model: the record codec renders the JSON writer's output and decodes through the JSON reader, so fingerprints, the dependency digest and the sidecar wrapper are unchanged. A record decode failure is reported as `SnapshotCodecFailure` with the 1-based line and column of the offending record. Existing `.json` workspaces keep working unchanged; conversion is explicit through `migrate --to <path.nyrec>` ([snapshot migration](#snapshot-migration)). The [Nyason encoding direction](../concepts/nyason-and-storage.md) remains a separate concern and does not fork the session semantics.

## Non-goals

The session process itself speaks only JSON lines over stdio; it does not add MCP/HTTP/cloud transport (the [stdio MCP server](mcp-graph-tools.md) is a separate adapter over it), multiple simultaneous transports, orchestration, a database, semantic merge/rebase, caller-owned production IDs, raw graph mutation, runtime provider registration/implementation, a new evaluator/runtime, or compatibility changes to the frozen evaluation protocols.

## Program-defined capabilities

The exact-ID and name-resolved create/replace recipes accept
[`capabilityConstruct`](program-capability-implementations.md). Its mappings
persist in snapshot schema 10 (old graphs still write schema 9), survive pinned
dependencies and reopen, and appear in structured reads. `runPure` executes
program-constructed capabilities internally through the generated interface; no
new input/output value encoding or host source registration is required.

### Typed function abort

Both exact-ID and symbolic expression recipes accept
`{"kind":"abort","error":<recipe>}` at graph-result positions in a Result-returning
function. Focus and structural review expose `aborts` with owner, error and
continuation identities. Abort snapshots use JSON schema 11; their prior schema
encodings remain unchanged when no Abort is present. See the
[contract and compatibility table](typed-function-abort.md#representation-and-compatibility)
and [ordinary-tool example](../../examples/function-abort/README.md).

### Argument-keyed fake responses

Each `fakeCapability` operation accepts exactly one script mode:

- `responses`: the existing single call-order queue;
- `cases`: independent response queues selected by **all** operation argument values.

```json
{
  "operationId": "<published operation ID>",
  "cases": [
    {
      "arguments": [
        { "capabilityParameterId": "<published parameter ID>", "value": { "kind": "string", "value": "member-2" } }
      ],
      "responses": [
        { "kind": "return", "value": { "kind": "result", "okKind": "string", "errorKind": "string", "isOk": false, "value": "member 2 failed" } }
      ]
    }
  ]
}
```

Every case must supply each operation parameter exactly once with its declared
type. Argument and case array order does not select a winner: equality is exact,
including ordinal Strings, list order, active Option/Result payloads, named type
and variant identities, and Product/Union fields. Field and parameter order in
the request is irrelevant. Keys support the same bounded typed run values as
ordinary arguments; capabilities cannot be nested in a key. Float64 keys match
bitwise, with every NaN equal and -0.0 distinct from 0.0. Bits32 keys match by value.


Duplicate complete keys, missing/unknown/duplicate parameters, wrong types or
mixing modes fail before host code runs. Malformed wire shapes are `ProtocolError`;
semantic binding errors are `RunBindingShapeMismatch`. Invalid nested values keep
their existing diagnostics. A zero-argument operation has one possible key, `[]`.
There is no partial match, wildcard, implicit fallback, repeat-last response or
case precedence.

On a call, logging, exact selection and queue consumption happen under the same
lock. Unrelated keys never consume each other's responses. Concurrent calls with
the **same** arguments still consume their shared key's queue in call order.
Return, throw, `delayMillis` and `awaitCancellation` retain their existing behavior;
waiting and throwing occur after the consumption lock has been released.

An unmatched call, including an empty `cases` array, produces `RunBindingNoMatch`
with exception type `FakeArgumentsUnmatchedException`. A matched but exhausted
queue produces `RunBindingExhausted`. Both carry semantic frames and the call log,
including the failed call. Empty queues are allowed and never fall through to
another case. Omitted operations retain the existing exhausted-binding behavior.

Limits are 256 cases per operation, 256 arguments per case, and 256 total responses
per operation across all cases. Key values participate in the existing String,
node-count, nesting, type and placement checks. Running a script never changes
the committed snapshot or persists its queues.

Existing wire `responses` scripts need no migration; snapshot and IR schemas do
not change. Direct F# `PureRunFakeOperation` construction adds `Cases = None` for
ordered scripts, or `Cases = Some cases` with `Responses = []` for keyed scripts.

# Capability operation signature migration

Checkpoint (base a76c8ee, including #363 and #364): migrate one existing operation's argument types and result type as one ordinary structural proposal. Retain capability, operation, parameter and function IDs. Parameter count/order/names, effects and FailureType remain unchanged; expected failures continue to use Result. This bounded operation is type evolution, not arbitrary declaration editing.

The request supplies the complete operation parameter type map, result type and complete affected function repairs. A repair supplies the existing function parameter type map, result type and replacement recipe. This permits a constructed implementation and its callers to migrate together. Analyze nested CapabilityInvoke nodes, CapabilityConstruct mappings and all semantic function references to affected functions whose signatures change (recursively including changed callers). Require exactly this affected set; reject duplicates, unknown parameter IDs and missing/unrelated repairs. Materialize every body against all new signatures, then validate the whole candidate before registration/publication. Reuse structural receipts and stale commit rejection. Imported declarations remain read-only.

The batch example will declare FetchFailure = Retryable(String) | Permanent(String), migrate fetch from Result<String,String> to Result<String,FetchFailure>, and retry only Retryable up to the configured limit. Host and fake implementations adopt the changed boundary explicitly. Graph publication does not deploy a host atomically. Historical old/new response queues need explicit runPure expectations; verifyChange is only appropriate for unchanged compatible entries.

Verification: argument and return evolution, constructed implementations and direct callers, stable IDs, stale/incomplete/type-invalid rejection, imported declaration boundaries, session review/commit/save/reopen/emission/execution, and batch exceptions/cancellation/release. No migration DSL or new runtime failure semantics.

Implementation note: repairs propagate from actual operation uses and implementations; unrelated signatures cannot seed the repair set. All repaired signatures are installed before recipes materialize. The ordinary full-candidate validator checks the completed graph.

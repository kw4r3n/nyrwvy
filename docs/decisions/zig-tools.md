# Tools in Zig, starting with the Zig emitter

- **Status:** Accepted (first stage)
- **Date:** 2026-10-27
- **Plan:** [backend-neutral semantics and generated library bindings](../plans/multi-backend-and-bindings.md#9-tools), §9
- **Update 2026-11-02:** the F# emitter (`Nyrwvy.Backend.Zig`, `ZigBackend.runner`) and the three parity check modes (emitter, reader, lowering) are removed ([switch step 5](zig-session-host.md#the-switch)). runPure's Zig backend always lowers with `model-reader` and emits with the Zig emitter; the extended suite sets `NYRWVY_ZIG_TOOLS=1` instead. The F# session host followed the same day (tag `fsharp-host-final`), so every route described below as F# or as a choice between F# and Zig is history.

§9 makes the formats, not the F# implementation, the contracts, so the tools can later leave .NET (for fewer dependencies). This decision starts that move with one part whose input and output are both fixed text: the Zig backend's emitter, which turns Execution IR JSON into Zig source.

## Decision

- **Zig tools live under `tools/zig/<tool>/`** and build with the Zig pinned in `mise.toml` (0.17.0), one `zig build-exe main.zig` each, with no `build.zig` and no dependencies beyond `std`.
- **The emitter (`tools/zig/emitter`) is a port of `ZigBackend.runner`**: the program (`emit`), its scripted fakes (`fakeCapabilities`) and the runner's `main`, which dispatches every runnable function, or only the entry named after the IR file, decoding each argument from the command line. It reads one Execution IR JSON file (the form `ExecutionIrSerializer` writes) and prints the complete runner on standard output (exit 0), or one JSON string per unsupported construct on standard output (exit 2); JSON escaping keeps a multiline diagnostic within one line. `PureRun` decodes each JSON string and preserves the diagnostic’s original line breaks. Anything else is a failure.
- **runPure's Zig route uses it.** The authoring session builds it once per process into the per-user runner cache (`emitter-<hash of its sources>`, moved into place after the build), writes the IR to a temporary file there and reads the runner back, keeping it in memory by emitter build, entry and IR hash so a repeated run skips the tool (the emitter check, removed 2026-11-02, compared every call); F# keeps only the run itself (argument tokens, the build of the runner, the reply). The first stage ported `emit` and `fakeCapabilities` alone; the second (same day) moved the runner's `main`, entry selection, `typeOf` and `fakeArgument` too, so the route's code generation is entirely in Zig.
- **The F# emitter stays as the reference for this stage.** With `NYRWVY_ZIG_EMITTER_CHECK` set (the extended test settings set it), the Zig route also runs the F# emitter and fails with `RunBackendMismatch` on any byte difference, or when only one of them rejects the program; the message lists of two rejections are not compared. So every Zig parity test (`ZigBackendTests`) is also an emitter parity test, and one more test emits every repository snapshot, whole and per entry, through both.
- **Shared text is one file.** The runtime the emitter copies into every program is `tools/zig/emitter/runtime.zig` (and the runner's token and envelope support `runner_support.zig`), embedded in the F# assembly as a resource and in the Zig emitter by `@embedFile`. The case-mapping runs are computed from .NET's Unicode data in F#, the mapping the C# backend applies; the Zig emitter embeds a generated copy (`case_mapping.zig`), and a fast test fails when it differs from what .NET computes.

## Changes to the F# emitter

Its output had to become a function of the IR JSON alone, so the Zig port can reproduce it. Neither change alters what a program does.

- **Order:** functions, blocks, capabilities and operations, jump arguments, `ProductUpdate` fields and callback contexts are taken in the order the IR JSON lists them (sorted by ID). The Zig emitter uses the same ordinal UTF-16 code-unit ordering as F# `String.CompareOrdinal`, including supplementary characters.
- **Instance names:** a generic instance's suffix hashes the IR JSON of its type arguments instead of F#'s `%A` text, which only .NET can produce. The Zig emitter writes that JSON itself, with System.Text.Json's default escaping, because substituted type arguments are not in its input.

## Reason

The emitter's input and output are both text with a byte-exact reference, so the port can be checked completely and every existing Zig test checks it for free. It is also the part a Zig-only tool chain needs first: a runner for Zig programs that does not start .NET to generate them.

## Consequences

- runPure's Zig route needs the repository's `tools/zig/emitter` beside `mise.toml` (the place `zigDirectory` already finds); the first Zig run in a process may build the emitter (a few seconds, cached after).
- A change to the emitter is made in both languages until the F# one is retired; the extended suite reports any difference.
- Unsupported-construct diagnostics use F# `TypeRef` display spelling, including its multiline form; each complete diagnostic is JSON-string encoded on one stdout line and decoded by the matching `PureRun` path.
- The emitted source now crosses a process boundary, so runPure's 1 MiB output limit (`RunOutputTooLarge`) applies to it; the runtime and case mapping take about 70 KB, so only very large programs reach it.
- The check covers only the instruction kinds the extended suite reaches; on 2026-10-27 that is all 192 the emitter knows (one test exists only to reach the kinds no other Zig test used). A new kind needs a checked program too.

## Second tool: the snapshot reader

Snapshot reading and validation is about ten times the emitter's logic (about 7,800 lines of F# in the record codec, the JSON codec, schema, migration and validator, against about 800), so it moves in three slices, each checked against its F# stage:

1. **Record text to the writer's JSON** (done, `tools/zig/snapshot-reader`): every record-form check of `RecordCodec` (grammar, canonical order and spelling, block structure, dangling references, the depth limit), stopping where `RecordCodec` hands the JSON to `SnapshotCodec`'s reader. Its reference was `RecordCodec.toJson`, which returns that JSON, or the record error, including the `position=` placement error that `deserialize` reports only after the model check; since the read path it is `RecordCodec.toJsonDeferred`, the JSON together with that deferred error. Usage: `snapshot-reader [--dependency <subjects>] <in.nyrec> <out.json> [<in> <out> ...]`, one `ok`, `deferred <line>:<column>: <message>` (the JSON is written), `error MaximumDepthExceeded: 1000` or `error <line>:<column>: <message>` line per pair; columns count UTF-16 code units as the F# reader does. `--dependency` names a file of the dependency's subjects, one `domain:uuid` per line (`RecordCodec.dependencySubjects`, written by F#), which a resolved local's records may reference without a record of their own; that set is all `decodeWith (Some dependency)` uses the dependency for, so the tool takes it rather than the dependency's JSON, which it has no reader for (the marker's digest and the merged model are the model reader's stage). Input that is not valid UTF-8 is decoded with U+FFFD per maximal subpart (`std.unicode.fmtUtf8`, the WHATWG decoder), as .NET's `UTF8Encoding` does. The per-kind key table moved to `tools/zig/snapshot-reader/record_kinds.txt`, embedded on both sides.
2. **The JSON model reader** (done for schema versions 21 to 24, `tools/zig/model-reader`): every shape check of `SnapshotCodec`'s reader (each object's properties, value types, stable IDs, integers as `TryGetInt64` reads them, float bits, omitted-rather-than-empty lists, true-or-omitted markers), the schema version and the construct minimums, then the writer's canonical JSON for the decoded model (order, spelling, schema 24). Its reference is `SnapshotCodec.toCanonicalJson`, which is `deserialize` without `SnapshotValidator.validate`, followed by the writer. Usage: `model-reader <in.json> <out.json> [<in> <out> ...]`, one `ok`, `skip legacy schema <n>` or `error <Case>: <message>` line per pair (the `SnapshotCodecError` case; a backslash inside a message is written `\\`, a line break `\n`). The per-kind reader table (context, properties in reading order with their shapes, the writer's order where it differs) is `tools/zig/model-reader/model_kinds.txt`, extracted once from the F# reader and checked by the comparison; the construct rows above schema 21 and the supported range are `schema_minimums.txt`, generated from `SnapshotSchema` and compared by a fast test.
3. **Semantic validation** (`SnapshotValidator.validate`, `Validation.fs`: 185 distinct codes, plus the 7 of `CapabilityImplementations.validate`, which it reports for `CapabilityConstruct`), split into sub-slices by what a rule needs from outside the decoded model:
   - **3a. Model-only rules** (done, `model-reader --validate`, 39 codes in `tools/zig/model-reader/validation_codes.txt`): the parent self-reference; duplicate IDs of every declaration, member, graph node, pattern binding and obligation; duplicate open obligations per call and parameter; blank display names; unknown effects of capability operations and functions and a function's duplicate effect; declared type parameters (blank or duplicate names, duplicate IDs, one ID shared across declarations, not inferable from the parameter types, a type parameter in a capability operation, irregular recursion); obligation targets, parameters and resolutions. They use only structural walks (`ValueGraph.collectNodes`, `SemanticFacts.collectPatternBindings`, `TypeParameters.occurring`), no inference or substitution.
   - **3b. Type references and node payloads** (done, 8 more codes): `UnknownNamedType`, `NamedTypeArityMismatch`, `UnknownCapabilityType`, `BuiltinGenericArityMismatch`, `TaskTypeInDeclaredType` on declarations, pattern bindings and the 11 `validateTypeRef` sites of `validateGraph` (their messages carry no function prefix: `validateTypeRef` uses the outer `add`); `TypeParameterNotDeclared` (`SemanticNodeShape.payloadTypeRefs`); `TaskTypeAtCapabilityBoundary` (`TaskTypes.bearing`); `GraphNodeDependencyCycle` (`SemanticNodeShape.dependencies`). The Set item and Map key equatability checks (`EquatableTypes`) are ported here too, but their codes were listed only with 3c, which emits them again from typed nodes.
   - **3c. Typed graph rules** (done, 132 more codes): the per-function loop. Its base is the node type resolver of `SemanticFacts` (`Resolver` in `main.zig`): the F# resolver resolves every node eagerly when it is created, by a post-order search over `nodesById` in ordinal ID order, and memoises every result, including the `None` of a node met again on the current path. A later query only reads the memo, so the order in which rules ask does not matter, but the order of the search does: on a dependency cycle it decides which node is cut. The search is ported exactly, with `directValueReferences` in operand order from `tools/zig/model-reader/node_references.txt` (per kind, the properties it reads; a fast test checks it against F# on the all-kinds snapshots with a distinct ID per reference). `DiagnosticText.typeRef` and `EquatableTypes.describeIn`/`explainIn` are separate renderers, as in F#. The rules follow `validateGraph`'s traversal (scopes of value nodes and pattern bindings, nested graphs) in groups, one commit each: graph structure (results, scopes, unknown parameters and pattern references, lone surrogates, Bool operands, Conditional, abort values, the function result); scalar operands (String, Int64, Float64, Bits32 and Bytes, as one table over operand positions, and ValueEqual); List, Set, Map, Option and Result inputs; products, unions, abort and the matches; callbacks, effect bodies and tasks (folds, the List/Set/Map/Option/Result callbacks with their context bindings and `PureFunctions.isPure`, UseResource, ExceptionCatch, CancellationShield, TaskScope, TaskStart, ParallelAll, TaskWait, OneShot, TaskCancel); calls, function values and capabilities (with `CapabilityImplementations.validate`). A code is listed only once every site that emits it is ported; until then its ported sites run and report nothing (`add` skips unlisted codes). Two codes cannot occur on this path and stay unlisted: `NullStringLiteral` (the reader requires a string) and `EmptyUnionMatchArm` (the reader requires a variant per arm).
   - **3d. Order and waiting** (done 2026-10-28, the last 4 codes, so all 183 that can occur are listed): `AmbiguousEffectOrder` (ported as `GraphOrder.tryAbortOrderConflict`; since 2026-10-28 `tryEffectOrderConflict` in every function with `semanticObservableFunctions`, see [the amendment](proposal-time-effect-ordering.md#amendment-full-validation-applies-the-runtime-rule-2026-10-28); with the semantic view: per graph level the observable nodes sorted by ID, the first pair with no dependency path either way, else the nested graphs in order; the topological fast path of `tryUnorderedPair` is not ported, because it returns early only when every pair is ordered, where the pairwise search finds none either), `MustNotWaitFunctionWaits` (`Waiting.derive` and `describe`: the rounds over the functions in list order, which see what the same round added and so decide the path), `OneShotScopePayloadUnsupported` (`validateTypeRef`, `OneShotPayloadRequirements.invalidCallbackUses` and `.violates` on a direct call's substitution) and `TaskBoundValueCrossesTask` (`rejectTaskBound` on the item or source, context bindings and worker result of TaskStart and ParallelAll, and `TaskCrossingRequirements.invalidInstantiations`, distinct per node and callee). Both requirement analyses share `instantiations` (each function reference whose callee's type parameters follow from its arguments and its node's iteration values, by kind) and a monotone fixed point, whose result does not depend on the order of its rounds. The callback and crossing issues carry no function prefix, nor does the waiting one (its loop follows the per-function loop).

The first slice is checked by an extended test, not inside runPure: the reader is a library stage with no process of its own to compare. The test feeds both readers the repository's `.nyrec` snapshots, the record-format fixtures, one snapshot per node kind (`RecordCodecAllKindsTests`), about 600 deterministic mutations of them (lines dropped, repeated, swapped, cut, blanked, a wrong character), and targeted cases for string spelling, the depth limit, the header's dependency marker and schema range, and 120 texts with ill-formed UTF-8 inserted (stray, truncated, overlong, surrogate and out-of-range sequences, in a name and anywhere), whose reference is `Encoding.UTF8.GetString` of the bytes; it compares the JSON byte for byte, or the full error line, and requires both outcomes to occur. For resolved locals it splits each original into a dependency (its types, effects and capabilities, or every function but the last) and a local naming those subjects (`RecordCodec.serializeResolved`, kept only when the local does not decode without the dependency), and compares each with 40 mutations against `RecordCodec.toJsonDeferredResolved` with `--dependency`, and each again without it. On 2026-10-28 that is 1,130 unresolved texts (246 accepted, 14 deferred, 870 rejected) and 62 resolved locals with 2,604 texts (116 accepted, 43 deferred, 2,445 rejected).

The second slice has its own extended test on the same pattern: the all-kinds snapshots, the record-format fixtures and the repository's `.nyrec` snapshots (through `RecordCodec.toJson`), each all-kinds snapshot relabelled 21 to 23, deterministic structural mutations (a property dropped, added, retyped or duplicated with either copy first, an ID blanked or broken, an array rotated, the schema version or a node kind changed, a string or marker replaced), for the first node of each kind an unsupported property and every property dropped and retyped, and targeted cases (escaped names, lone surrogates, float bits, integer spellings, visibility markers, type nesting on both sides of the depth limit, cut texts). It compares the JSON byte for byte, or the error line; `InvalidJson` and the `Invalid JSON string encoding:` messages, which carry .NET's text, are compared by case and prefix only. On 2026-10-27 that is about 3,200 texts: about 1,000 accepted, 2,200 rejected with about 780 distinct messages, 13 legacy documents skipped, and no input on which the F# writer throws.

Sub-slice 3a is a mode of the model reader rather than a new tool: it needs the reader's parsed document and its shape verdict, and a separate tool would duplicate the parser or import across tool directories. After a successful shape read it walks the parsed document, not the canonical output: the F# reader keeps document order and the writer sorts, and the validator's `Map.ofList` and node-owner lookups are last-wins under duplicate IDs. Usage: `model-reader --validate <in.json> [<in> ...]`; per input the reader's `error`/`skip` line, or one `issue <Code>: <message>` line per issue (line breaks written `\n`) and `end`. Its reference is `SnapshotValidator.validate` of `SnapshotCodec.readUnvalidated` (the shape-decoded model, without dependency resolution), filtered to the listed codes. Filtering is sound: `validate` only accumulates issues, with no early return or section gated on another rule's issue, and sorts them by (code, message) ordinally at the end, so the listed rules' issues and their order do not depend on the excluded rules. The Zig side sorts the same way over UTF-16 code units. Inside the per-function loop (whose `add` prefixes "In function …: ") the rules read derived facts (node types and completions from the resolver, which is ported whole, purity, type matching, the requirement analyses), never another rule's issue. A code is listed only when every site that emits it is ported, so no listed code loses an issue to an unported site; since 3d every code that can occur is listed, and the filter drops only the two that cannot. The one coupling left is the F# validator throwing on a model (`DiagnosticText.typeRef` on `Exception` with type arguments, say); the test counts such inputs and skips them (none so far).

The extended test (`ZigValidatorTests.fs`) uses the slice-2 originals (all-kinds snapshots, record-format fixtures, repository snapshots), named edits that keep the shape valid and break the listed rules, random combinations of two or three edits, and two slice-2 shape mutations per original. The 3a edits copy declarations, take another's ID, blank display names, point references nowhere, declare type parameters and add obligations. The 3b and 3c edits break type references (unknown, extra or missing arguments, task scopes, types that are not equatable, undeclared type parameters), make dependency cycles (self references, a nested node naming its enclosing node), point every `…NodeId` operand at literals of one type, at literals by position in three rotations and at typed containers (List, Set, Map, Option, Result) by position in six, end graphs in literals, add abort nodes, change function signatures (an extra or a dropped parameter, Bytes parameter and result types, a required effect, a type parameter), add self calls, and duplicate, retarget, drop or retype field bindings, union match arms, context and argument bindings and capability implementations. The 3d edits add whole generic functions to every original: a task-bound capability whose values reach a ParallelAll source, a TaskStart item and context binding and a worker result, and a generic function forwarding its type parameter into a ParallelAll, called with the capability type; a function returning `OneShot<T>` called with a TaskScope list directly, through a generic forwarder and as a ListMap callback; and must-not-wait on every function, may-wait on every operation, with a call, a ListMap callback and a capability operation that reach a wait. Effect order needs no edit of its own: the abort edits already leave abort nodes unordered against effects. It compares the issue lines exactly, requires every listed code to occur and both clean and failing models. On 2026-10-28 (before the lowering test added an open-obligation edit) that is 13,976 texts: 450 clean, 13,129 with listed issues, 391 shape rejections, 6 legacy skipped, no F# validator failures; the 3d codes occur 271 (`AmbiguousEffectOrder`), 1,192 (`MustNotWaitFunctionWaits`), 944 (`OneShotScopePayloadUnsupported`) and 1,644 times (`TaskBoundValueCrossesTask`). Fast tests check that each listed code is a code of `Validation.fs` (or `CapabilityImplementations.fs`) and that `node_references.txt` follows `directValueReferences`. Limits: each node kind's rules rest mostly on its one all-kinds snapshot, so a few codes occur only once to four times (`ValueEqualOperandTypeMismatch`, `ValueEqualTypeNotEquatable`, `EmptyProductUpdate`, the invalid and unknown product construct and update targets, `ListAppendItemTypeMismatch`, the three `…ItemTypeNotEquatable` list codes, `FunctionInvokeArgumentTypeMismatch`, `FunctionInvokeArityMismatch`, `UnknownCapabilityConstructTarget`, `DuplicateCapabilityImplementation`, `CapabilityImplementationSetMismatch`, `ImpureCapabilityImplementation`, `CapabilityArgumentTypeMismatch`); the obligation rules rest on the few originals with a direct call taking arguments; last-wins lookups under duplicated node IDs across functions are exercised only through random combinations; the 3d sites rest mostly on the added functions, one shape each.

Limits of the second slice: versions 9 to 20 (and so migration) are reported as `skip legacy schema <n>` and not compared, and will not be ported (decided 2026-10-28: the F# reader and its migration keep handling them); no semantic validation, so it accepts models `deserialize` rejects as `InvalidSnapshot`; input that is not valid UTF-8 is rejected outright. `MaximumDepthExceeded` cannot occur on this path: the writer's depth equals the input's, which JsonDocument already limits to 1,000.

Limits of the first slice: none left of the two first recorded (2026-10-28: resolved locals read with `--dependency`, ill-formed UTF-8 decoded as U+FFFD). The tool decodes bytes as `Encoding.UTF8.GetString` does: a leading byte order mark stays in the text, where `File.ReadAllText` would drop it; the session hands the tool text it has already decoded, so this does not reach it.

## The read path in Zig (done, 2026-10-28)

The authoring session decodes every snapshot it opens through `SessionStorage.decodeWith` (`Session.fs`): `RecordCodec.deserialize` for `.nyrec`, `SnapshotCodec.deserialize` otherwise, and the `…Resolved` variants against a pinned dependency. The Zig reader takes over the verdict of that call (accept, or the error the user sees) the way runPure's Zig route takes over the emitter: Zig by default, the F# reader kept as the reference under a check variable.

- **Where the tool runner lives.** `zigTool` and its helpers (the compiler lookup, the per-user cache, the owner-only directories, process launch) move from `PureRun.fs` to a new `ZigTools.fs` compiled before `Session.fs`. Both the read path and runPure then share one build cache and one per-process table. `ZigTools` reports a build or launch failure as plain text (`Result<_, string>`), and each caller maps it: runPure to its `RunIoFailure` and process diagnostics, as now, and the session to the fallback below.
- **What runs.** For an unresolved source (`dependency = None`): a `.nyrec` source goes through `snapshot-reader` (record text to JSON, then `model-reader --validate` on that JSON); a `.json` source goes through `model-reader --validate` directly. The tools take files, so the source is written to a temporary file in the per-user tool cache (owner-only, as runPure's IR files) and deleted afterwards. The lines map back as follows:
  - `snapshot-reader`'s `error <line>:<column>: <message>` becomes `InvalidShape "line …, column …: …"`, which is what `recordFailure` makes of a record error today.
  - The record path must compose to `RecordCodec.deserialize`, not to `toJson`, so `snapshot-reader` gains two outcomes. The depth error, which `deserialize` reports as `MaximumDepthExceeded 1000` (its `Model`), prints as `error MaximumDepthExceeded: 1000`. The deferred `position=` placement error, which `deserialize` reports only when the model check passes, prints as `deferred <line>:<column>: <message>`, after the JSON has been written. The session then runs `model-reader --validate`. A model error or issue wins, as in `readModel`; otherwise the deferred error is returned, as `InvalidShape "line …, column …: …"`. The snapshot reader's parity test changes its reference to match (the JSON together with the deferred error, and the depth case).
  - `model-reader`'s `error <Case>: <message>` becomes that `SnapshotCodecError` case (`\n` restored).
  - `issue` lines become `InvalidSnapshot` with the issues in the order printed.
  - `end` with no issues means accepted.
- **Building the model on success.** The F# `Snapshot` value is still built in F#, by `SnapshotCodec.readUnvalidated` on the same JSON (the record path's JSON is the snapshot reader's output), and so is the record path's re-encoding of an earlier `schema=`. Zig decides validity and diagnostics, and `SnapshotValidator.validate` no longer runs on this path. If `readUnvalidated` rejects what Zig accepted, the F# error is returned: that is a parity bug, and returning the F# error keeps the session from opening a model nobody validated.
- **What stays on F#.** These cases still go to the F# reader:
  - a source resolved against a dependency: the snapshot reader can read its records (`--dependency`), but the model reader neither checks the dependency marker nor validates the resolved model (assessed below);
  - legacy schemas 9 to 20: `model-reader` prints `skip legacy schema <n>`, the F# reader and its migration handle them, and they are not ported (decided 2026-10-28; the F# migration code stays);
- **Check mode.** With `NYRWVY_ZIG_READER_CHECK` set (`tests/extended.runsettings` sets it next to the emitter's), the F# reader also runs, any difference is an error, and the F# fallback below is off, so a broken toolchain fails the tests rather than silently passing on F#. The comparison:
  - both accept: the two snapshots must serialize to the same writer JSON;
  - both reject: the same case and message, except `InvalidJson` and the `Invalid JSON string encoding:` messages, which carry .NET's text and are compared by case and prefix, as the extended tests do;
  - a difference becomes `AuthoringSessionError.IoFailure "ReaderMismatch: …"`. That reuses an existing case rather than widening the public error union, and it never occurs outside check mode.
- **When Zig is unavailable.** The read path cannot run without Zig. A machine without a `zig` (or `NYRWVY_ZIG`) would then be unable to open any snapshot, where today only the Zig run backend needs it. So: if the tool cannot be built or started (a launch or build failure, not a reader verdict), the session falls back to the F# reader and records that once per process on stderr. `NYRWVY_SNAPSHOT_READER=fsharp` forces the F# reader, for a machine without Zig or to rule the Zig reader out while debugging.
- **Cost.** One or two short processes per decode, plus the first build per tool version (the same cache as runPure, about a minute once). Decoding happens on open, reload and dependency selection, not per edit.
- **Visible change.** On the `.json` path, text that is not valid JSON, and a string or property name holding a lone surrogate, now report the Zig reader's message instead of .NET's (same case and prefix); every other error text is identical, as the parity tests show.
- **Verification.** The extended suite runs every session test that opens a snapshot under check mode; that is the real-path coverage, as runPure's tests are for the emitter. A fast test covers the routing: the F# reader for a dependency, a legacy schema, and `NYRWVY_SNAPSHOT_READER=fsharp`. The snapshot reader's parity test is updated for the new protocol.
- **Out of scope.** `Nyrwvy.Viewer` (`ViewerArtifact.fs`) keeps the F# reader: it is a separate program with no Zig tool runner. The writer stays F#.

As built (2026-10-28), with these differences from the design above:

- `ZigTools` (`tools/Nyrwvy.AuthoringSession/ZigTools.fs`, compiled after `PureRunWorker.fs`, whose `BoundedOutput` it uses) reports a failure as a code and a plain-text message, not a bare string, so runPure keeps its `RunStartupFailure`, `RunTimeout`, `RunProcessFailure` and other codes; the session joins them as `<code>: <message>`. The general process launch moved with it, and runPure's dotnet launches use it too.
- The session side is `ZigSnapshotReader` in `Session.fs`: `verdict` maps the tools' lines (a record error first, then a model error or issues, then the deferred placement error), `read` runs the tools on owner-only temporary files in the tool cache and deletes them, `compare` is the check. The snapshot reader's parity reference is `RecordCodec.toJsonDeferred` (the JSON with the deferred error; `toJson` stays for the model reader's tests).
- The fallback also covers a tool that exits non-zero or prints lines outside the protocol, and it is sticky: after the first failure the process reads with F# without retrying the build (a failed build can take up to its 300 s limit). A timeout or more than 1 MiB of output falls back for that source only. A source the tools cannot take as UTF-8 (a lone surrogate, possible only in an embedded `snapshotRecords` string) goes to F# without a note. `NYRWVY_SNAPSHOT_READER=fsharp` wins over check mode.
- The fallback note is a second stderr line before the `<code>: <message>` line of a session that cannot start; the startup and migrate CLI tests ignore it, so they pass on a machine without Zig (as the fast CI job is). `docs/specs/agent-authoring-session.md` does not mention the note yet.
- Coverage of check mode: the extended settings run only `Suite=Extended` tests, so the fast session tests do not run under check mode in `test-extended.fish`; the extended tests that open snapshots do (runPure's, among others). On 2026-10-28 the Authoring, persistence, migration and record codec tests (381, fast and extended) passed with `NYRWVY_ZIG_READER_CHECK=1`, with no mismatch. The Node test harnesses set neither check variable, as for the emitter.
- The model reader writes a backslash in a message as `\\` and a line break as `\n` (or `\r`), so the session reads every message back exactly. The snapshot reader's messages need no escaping, because record text has no line breaks inside a value.

Resolved sources (assessed 2026-10-28, not built). The F# path is `readDocument (Some dependency)` in `SnapshotCodec.fs` (about 15 lines: the `Resolved snapshot` property set with `dependency`, the marker's two properties, its `snapshotId` and `digest` against `dependencyDigest`, the SHA-256 of `writeSnapshot None dependency`, checked before the schema version, and the error for a dependency too deep to hash: "The selected dependency exceeds the maximum JSON depth."), `resolveDependency` (7 lines: the dependency's declarations and obligations prepended to the local's) and `SnapshotValidator.validate` on the resolved model, which the model reader already ports; the record stage is done. A port needs: `model-reader --validate --dependency <canonical.json> --marker <id> <digest>` (F# passes the expected marker, since the model reader writes only schema 24, not the minimum-version JSON the digest hashes); the resolved property set and marker check in the shape reader; and `validate` run on a root whose arrays are the dependency's followed by the local's (it reads only the root's five arrays and `parentSnapshotId`, which stay the local's). That is about 60 to 90 lines of Zig, 30 of F# in `ZigSnapshotReader` (route a dependency, write the subjects and the dependency JSON) and a resolved corpus in `ZigValidatorTests`, built as the snapshot reader's is.

## Third tool: the Execution IR lowering (done, 2026-10-28)

The one F# stage left between the Zig model reader and the Zig emitter is `TypedSemanticIr.project` followed by `ExecutionIr.lower` (about 2,900 lines with `ExecutionIrAnalysis`, `ExecutionIrDeclarations` and `ExecutionCallGraph.forSnapshotEntry`). Porting it lets a Zig tool chain go from a snapshot to the runPure runner without .NET. It moves in two stages, each compared byte for byte through the serializers that already exist (`TypedSemanticIrSerializer`, `ExecutionIrSerializer`), which become the references.

- **A mode of the model reader.** Both stages need what the reader already has: the parsed document, the shape verdict, the complete validator (readiness is `SnapshotValidator.validate` plus open obligations) and the node completion resolver (`Resolver`, ported exactly in 3c), which gives every typed node its type. A separate tool would duplicate all of that. The new code is a section of `main.zig` per stage: a separate file would need most of the reader's declarations made public.
- **Stage 1: typed semantic IR** (done 2026-10-28). `model-reader --typed-ir <in.json> <out.json> <entry|-> [...]` (`-` for the whole model): the shape read, then `ExecutionCallGraph.forSnapshotEntry` when an entry is given (the selected functions and the obligations whose call node they hold, in document order; an unknown entry selects nothing, which is not an error), and readiness on that selection. The validator runs on the filtered `functions` and `obligations` arrays, not on the whole document: some rules depend on which functions exist and in what order (`Waiting.derive`'s rounds, the crossing instantiations), and F# validates the selection. Then the projection with each node's completion from the resolver (`MissingNodeType` when it has none), and the `TypedSemanticIrSerializer` JSON (schema 14, `Utf8JsonWriter`'s default escaping, as the emitter already writes). Output: `ok`, `skip legacy schema <n>`, the reader's `error <Case>: <message>`, `error InvalidSnapshot: <n> issues`, `error IncompleteSnapshot: <ids>` or `error MissingNodeType: <functionId> <nodeId>`. The node properties are `model_kinds.txt`'s, in the model writer's order, without the declared types the node's type replaces (except `exceptionRethrow`'s and `oneShotCreate`'s) and a product's `typeId`, and with two renames (`patternBindingId` to `bindingId`, `targetFunctionId` to `functionId`); that rule needed no table of its own. As built, the stage-1 test (`ZigLoweringTests.fs`) runs every validator-corpus text that decodes whole and with each of its first six functions as entry: on 2026-10-28, 93,683 cases from 13,550 texts, 32,902 projected (the JSON identical), 60,770 invalid and 11 incomplete (a validator edit drops a call's argument and opens its obligation), with no F# failure; `MissingNodeType` never occurs (the validator appears to reject every node without a type first; it stays ported, untested). The tool takes its inputs as arguments, so the test runs it in batches of 1,000.
- **Stage 2: Execution IR** (done 2026-10-28). `--execution-ir`, same arguments: stage 1's typed program in memory (not re-read from its JSON), then `ExecutionIr.lower` (effect-order validation, the block and instruction scheduling, tail self calls, declarations) and the `ExecutionIrSerializer` JSON, the input the Zig emitter reads. The lowering's `ExecutionIrError` cases print as `error <Case>: <ids>`. The emitter's IR reader is not reused for writing: it reads into the emitter's own structures, and the writer is a separate, mechanical port.
- **Order.** The lowering already orders by ID: functions, blocks and the arms it walks are sorted, and its scheduler (Kahn's algorithm) takes the lowest ready ID, Bytes updates last. The projection keeps document order where the serializer sorts anyway. So the output is a function of the model JSON, and the F# side needs no change; if the port finds a list-order dependence, it is fixed in F# first, as the emitter's was.
- **References and tests.** Each stage gets an extended test on the validator tests' corpus (the all-kinds snapshots, record-format fixtures, repository snapshots, and the named edits that keep models valid): every model whole and with each function as entry, against `TypedSemanticIr.project` (stage 2: then `ExecutionIr.lower`) of `SnapshotCodec.readUnvalidated` on the same JSON, the JSON compared byte for byte and the error by case and IDs; invalid models are compared by case only (their issues are the validator test's subject). It requires both outcomes and reports the counts.
- **The real path, stage 2.** The session's `Project` (used by runPure on both backends) gains a check like the emitter's: with `NYRWVY_ZIG_LOWERING_CHECK` set (the extended settings set it), it writes the snapshot it projects with the canonical writer, runs `model-reader --execution-ir --entry` on it and fails with a mismatch when the JSON differs from `ExecutionIrSerializer.serialize` of the F# result. So every runPure test is also a lowering parity test. runPure itself keeps the F# lowering: its in-memory `ExecutionProgram` serves argument decoding, entry reach and the C# backend, and switching the Zig route's input to the model JSON is a later step once the check has run for a while.
- **Details to port exactly.** `UnionMatchArm.canonicalVariantIds` and the `variantId`/`variantIds` spelling; `ExecutionIrIds` (`Uri.EscapeDataString` on IDs, .NET's unreserved set); `isExactSelfCall`'s type equality.
- **Check failures.** Under `NYRWVY_ZIG_LOWERING_CHECK`, a Zig tool that cannot be built or run is a failure, as under the emitter's check, not a fallback. A resolved local is projected from the merged model; the check covers it only if the canonical writer writes that model as a schema-24 document the reader accepts, which is verified before the check is wired, and skipped (and recorded here) otherwise.
- **Coverage.** The corpus's valid models are mostly the all-kinds snapshots, one node per kind, so the scheduler's tie-breaking, the Bytes-update deferral and tail self calls are reached mostly through the session check over runPure's programs; stage 2's test adds the repository's example snapshots where they are cheap to load.
- **Out of scope.** Resolved sources on the read path (the 60 to 90 lines assessed above) stay deferred until after stage 2. The C# backend's and the Viewer's uses of the lowering; `ExecutionIrBytesOwnership`, which the backends call after lowering; legacy schemas (skipped as by the reader).

Stage 2 as built (2026-10-28), with these differences from the design above:

- **Effect order is checked again.** The design assumed `validateEffectOrder` could not fail on a ready model. It could: the validator applied the historical admission rule (`GraphOrder.tryAbortOrderConflict`: only functions with an Abort, and only callees that declare effects are observable), while the lowering applies the runtime rule (`tryUnorderedEffects` in every function, with `observableFunctions`' closure over calls, effect callbacks, workers and bodies). The first test run found 3,402 cases where F# reported `AmbiguousEffectOrder` and Zig lowered, so the Zig lowering ports `observableFunctions` and runs the validator's `unorderedEffects` with the typed view, which differs only in visiting nested graphs in the typed graph's order (nodes by ID, union arms by their first variant); the descriptor is the semantic one, which `EffectClassificationConsistencyTests` keeps equal to the typed one. Since 2026-10-28 full validation applies the runtime rule too ([amendment](proposal-time-effect-ordering.md#amendment-full-validation-applies-the-runtime-rule-2026-10-28)), so those cases are now `InvalidSnapshot` and a ready model no longer fails lowering on effect order.
- **Instructions are table-driven.** A simple node's instruction has its typed properties in order, under the names `tools/zig/model-reader/instruction_kinds.txt` lists (extracted once from `ExecutionIrSerializer`; a fast test checks that it lists every kind not written by hand, the comparison checks the names): a node reference (a property `node_references.txt` lists) becomes the value bound to that node, an argument list becomes `{target, valueId}` pairs sorted by target, anything else is written as in the typed IR. Parameter and pattern references, the eight structured kinds, the pattern extractions and the terminators are written by hand.
- **Errors.** The lowering's other errors (`MissingNodeValue`, `MissingPatternValue`, `MissingFunctionParameter`, `UnresolvedDependencies`, `UnterminatedBlock`) are ported but never occur on a ready model in the corpus; where several apply, the one Zig reports first may differ from F#'s, which checks some operands in another order (a callback's context before its source, say).
- **The session check** runs at all three projection sites: the whole committed snapshot (`ProjectExecution`, also used by C# emission), each entry of it (`ProjectEntryExecution`, runPure's path) and a proposal's snapshot. The JSON is `AgentWorkspace.serializeCurrentSnapshot` (or `SnapshotCodec.serialize` of the proposal), which for a resolved local is the merged model as a plain schema-24 document, so resolved workspaces are checked too. A mismatch or a tool that cannot run is `IoFailure "LoweringMismatch: …"`; a snapshot the writer rejects (it validates the whole snapshot, where an entry's projection validates only what the entry reaches) is not checked; outside check mode nothing runs, the snapshot is not even serialized.
- **Counts.** The stage-2 test compares the same 93,683 cases as stage 1: 29,500 lowered (the JSON identical), 3,402 `AmbiguousEffectOrder`, 60,770 invalid, 11 incomplete, no F# failure.

## runPure on the Zig lowering (done, 2026-10-28)

runPure's Zig route gets its Execution IR from `model-reader --execution-ir` instead of the F# lowering, so on that route the model goes from the snapshot's JSON through Zig tools only (reader, lowering, emitter); .NET keeps the session, the run and the reply.

- **Input.** `AuthoringExecutionContext` gains `ModelJson: unit -> Result<string, SnapshotCodecError>`: the canonical JSON of the snapshot the context projects (`AgentWorkspace.serializeCurrentSnapshot` for the committed snapshot, `SnapshotCodec.serialize` for a proposal's, inside a `SnapshotComputationScope` as `Project` is), the same text the lowering check feeds the tool. The route writes it to an owner-only file in the tool cache and runs `model-reader --execution-ir`; the emitter reads the IR file the lowering wrote.
- **Whole, then entry, as today.** For the committed snapshot (`ProjectAll` is `Some`) the route lowers the whole model (`-`) and emits it with no entry filter; when that lowering prints an `error` line, or the emitter cannot take the whole, it lowers the entry and emits that with the entry filter. For a proposal it lowers the entry only. Today's entry fallback also prunes the entry's program by IR call targets (`ExecutionCallGraph.forEntry`); that second pruning goes. `callbackTargets` covers every reference role `forSnapshotEntry` follows, so it removes only functions referenced solely by nodes the lowering drops (after an Abort in the same graph); such a function is now emitted too, which can only make the entry emit fail where it passed if that function holds a construct the Zig backend does not support.
- **What still uses F#.** The fake capabilities' operations come from `context.Declarations` and the snapshot ID from the context, so the run needs no `ExecutionProgram`. The one exception is the waiting-response shape check (`awaitCancellation`/`delayMillis` need a program that uses the concurrency runtime), which reads the entry's F# program; it runs only when a fake response waits.
- **Errors.** An `error` line from the entry lowering (an incomplete selection, say) makes the route return what `context.Project` returns for that entry, so diagnostics stay identical; that path pays for both.
- **Fallback.** When `model-reader` cannot be built or started (`RunProcessFailure`, `RunStartupFailure`), the route uses the F# programs from `context.Project`/`ProjectAll` as today, sticky for the process with one stderr note; anything else (a crash or non-zero exit, a timeout, more than 1 MiB of output, lines outside the protocol, an I/O failure on its files, a `ModelJson` the writer rejects) falls back for that run only. The emitter and the runner still need Zig, as today.
- **Cache.** Lowered IR texts are kept per (snapshot fingerprint, entry) for the last fingerprint seen, cleared when it changes, so the cache holds one snapshot's IR at most (a session runs many cases of one snapshot between edits).
- **Check mode.** Under `NYRWVY_ZIG_LOWERING_CHECK` the route also takes the F# programs and fails with `RunBackendMismatch` when an IR text differs or only one side rejects; the fallback is then off. Each entry is then lowered by Zig twice, since `context.Project` runs the session's own check (`ZigLowering.check`); that stays for the projection's other users (the C# backend, C# emission). The emitter check (`NYRWVY_ZIG_EMITTER_CHECK`) keeps comparing the F# emitter on the F# program.
- **Known limits** (Opus review, 2026-10-28): under check mode a mismatch on the whole program only drops to the entry's IR, as the session's check did before; with only the emitter check on, a whole program that Zig lowers and F# does not is an error instead of a drop to the entry; a commit landing between the context's creation and the run makes Zig lower the context's snapshot while the F# references read the new one, which only the checks can notice; the waiting-response check always projects the entry in F#.
- **Out of scope.** The C# backend's route, which needs the F# program; resolved sources on the read path.

## Validating each model once (done, 2026-10-28)

The speed measurement of #534 showed the Zig path paying for validation three times where once is enough. Opening a snapshot runs the Zig validator on its bytes, then `SemanticWorkspace.create` runs the F# validator on the Snapshot built from them. Every runPure context writes the snapshot with the F# writer (which looks up or runs validation) and `model-reader --execution-ir` validates it again for readiness. The changes below make each model validated once on the default path. The check modes keep comparing exactly as now.

- **Open.** When the Zig reader accepted the bytes and F# built the Snapshot from them (`readUnvalidated`), the session records that Snapshot as valid, so `SemanticWorkspace.create` does not validate it again. The recording is `SnapshotCodec.readZigValidated`, which reads the JSON and marks the Snapshot it returns in a reference-keyed table that `SnapshotValidator.validate` consults first. Only the caller holding bytes the Zig validator accepted uses it. Under `NYRWVY_ZIG_READER_CHECK`, or when F# read the source, nothing is recorded.
- **The model JSON for runPure.** After an open through the Zig reader, the session keeps the bytes the Zig validator accepted (for a `.nyrec` source, the snapshot reader's JSON), keyed by the workspace object as the projections are. `ModelJson` returns them with a mark that they are validated. In every other case it calls the writer, as now: after a commit, for a resolved workspace or an F#-read source, and for a proposal's snapshot. The writer's validation is retained per snapshot, so that call only writes.
- **No second validation in the lowering.** `model-reader --execution-ir --validated` prepares the validator's context (declaration tables, owners) without running its rules, then does the readiness steps that are not validation (the selection, open obligations, node types and `MissingNodeType`) and the lowering. It is passed only for JSON the Zig validator accepted as these same bytes. Input that was not validated may make it panic; the route's per-run fallback absorbs that. Under `NYRWVY_ZIG_LOWERING_CHECK` the flag is never passed, so the tool validates as now and the comparison is unchanged. The writer's JSON of a snapshot F# validated counts too (decided 2026-10-28, closing the question left open here): the writer only encodes a model that passed `SnapshotValidator.validate`, so a resolved snapshot (read by F#) and a proposal's candidate also skip the second validation. The writer and the Zig validator are kept in step by the extended lowering and reader comparisons, which still run with the flag off.
- **Why skipping holds for an entry.** Readiness validates the entry's selection, not the whole model. The selection keeps every declaration and, with its body, every function the entry reaches, and every obligation on those functions' call nodes, so each rule sees what it sees in the whole model. The lowering test checks this claim: for every model whose whole lowers, no entry of it is invalid. It also checks that `--validated` changes no output: every lowered case again with the flag, byte for byte.

## A resolved snapshot validated in Zig (done, 2026-10-28)

The standing rule from 2026-10-28: once the Zig path beats F# on `evaluation/zig-speed`, that path drops its F# work. The overlapped read (F# builds the model while `model-reader --validate` runs) made the Zig-decided open faster than the F# reader. So a resolved JSON snapshot, one with a dependency sidecar, is now decided in Zig too:
- **F#'s part.** F# writes the dependency's JSON at the current schema version (the text is kept per dependency object; each read writes it to a temporary file). It reads the local document as `deserializeResolved` does: the marker and its digest, the version, the shape and the local construct minimums. The merged model is left for Zig to validate (`SnapshotCodec.readResolvedUnvalidated`).
- **Zig's part.** `model-reader --validate --dependency <dependency.json> <local.json>` accepts the `dependency` marker and splices each declaration array, the dependency's first. It then validates the merged model with the same rules. A dependency at another schema version prints `skip`, and F# reads the snapshot.
- **Errors.** F#'s errors in the local document come first, as in `deserializeResolved`. Zig reports only the merged model's issues; any other Zig rejection leaves the decision to F#.
- **Reuse.** An accepted merged model is recorded as valid and kept for `resolveDependency`, so the workspace does not validate it again.
- **The check.** Under `NYRWVY_ZIG_READER_CHECK` both readers run, and the merged models are compared.
- **Not covered.** A resolved record (`.nyrec`) still reads with F#. Its snapshot-reader step needs the dependency's subjects (`--dependency`), which the session does not pass yet.

## Session timings as input for the next step (2026-10-28)

`evaluation/zig-speed/README.md` ("Where an AuthoringSession spends its time on Rhifill") times the session host on Rhifill, as input for choosing between (a) stopping the port at the toolchain (reader, validator, lowering, emitter) and (b) porting the whole session to a long-running Zig process. Not decided here. The measured facts:
- A new host takes about 0.6 s to its first reply. Most of it is not yet attributed, most likely first-run JIT of the session code; the runtime start is about 30 ms and the open about 33 ms.
- Requests on an open session take 0–3 ms for reads, about 45 ms for a proposal and about 23 ms for a commit.
- Rhifill's runPure is on the C# backend, where the first run of an entry costs 0.4–0.6 s of C# emit and compile and a repeat about 8 ms.

## F# and Zig on equal terms (measured 2026-10-28, no decision)

`evaluation/zig-speed` ("F# and Zig on equal terms") times validate, lower and emit in both languages: from the same JSON, as a cold process, and warm in-process. Warm, task-outcomes is a draw (F# up to 25% faster on validate and emit), and Zig is 1.1–1.4× faster on Rhifill. Cold, a JIT F# process costs 330–790 ms against Zig's 3–46 ms, ReadyToRun about half that, and Native AOT 9–104 ms. So most of the earlier gap came from F# process start and JIT, not from the work itself. Native AOT needs changes before it is usable: reflection-based JSON in `ExecutionIrSerializer`, F# `printf`/`%A` (wrong or throwing under AOT), and the host's Rhifill open. These numbers are input to the open question of whether a mixed F#/Zig runtime is acceptable; nothing is routed differently.

## Direction: a whole Zig session host, no mixed runtime (decided 2026-10-28)

The owner chose to port the whole session to Zig rather than keep a mixed F#/Zig runtime. The equal-terms measurement showed that most of the gap was F# process start and JIT, and that warm work is close in both languages. A process that runs F# and spawns Zig tools for some steps keeps two implementations live on the same path. So:
- **Default path is F# only.** The session's reader and validator are F# unless `NYRWVY_ZIG_TOOLS=1` is set (`ZigTools.enabled`). runPure's Zig *backend* (compiling and running the generated Zig) is a run target, not a tool; since 2026-11-02 its source always comes from the Zig lowering (F# when `model-reader` reports an error or cannot run) and the Zig emitter.
- **Parity modes (removed 2026-11-02).** The check variables also enabled the Zig routes, so the extended suite ran both and failed on any difference. The extended suite now sets `NYRWVY_ZIG_TOOLS=1`; `tests/benchmark.runsettings` sets it too, so `ZigSpeed` keeps timing the Zig routes.
- **The standing rule above (switch a path to Zig once it is faster) is withdrawn.** The Zig tools become the base of a separate Zig session host. That host reaches parity with the F# host step by step, and then replaces it in one switch. The F# host is then marked deprecated and kept on the remote under a tag. The plan is [zig-session-host.md](zig-session-host.md).

**Step 8a candidate (unmerged to main):** the cutover PR makes native `nyrwvy-host` the default and marks the F# host deprecated for normal use, retaining it as reference code and for legacy-schema migration. `NYRWVY_HOST_EXECUTABLE` selects an operator override; relative paths are rooted at the repository, `.dll` overrides use `dotnet` as an explicit legacy escape hatch, and native overrides execute directly. The .NET SDK remains needed for the C# backend, while launching the non-C# host does not require F#. Direct typed reads and all known snapshot-model bridges are verified; Linux Release, focused, maintained, adapter, and benchmark checks passed. Portability code targets Linux, macOS and Windows, but only Linux has final runtime verification. Hosted macOS/Windows jobs did not start because of an account-level runner restriction; the owner has deferred additional hosted runs. This execution hold does not change product support scope. See the [typed-read migration and platform verification](zig-session-host.md#step-8-blocker--typed-read-architecture-confirmed). Main keeps its F# default; no merge, deprecation or final-host tag has occurred. Golden capture and F# removal remain separate later work.

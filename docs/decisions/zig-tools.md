# Tools in Zig, starting with the Zig emitter

- **Status:** Accepted (first stage)
- **Date:** 2026-10-27
- **Plan:** [backend-neutral semantics and generated library bindings](../plans/multi-backend-and-bindings.md#9-tools), §9

§9 makes the formats, not the F# implementation, the contracts, so the tools can later leave .NET (for fewer dependencies). This decision starts that move with one part whose input and output are both fixed text: the Zig backend's emitter, which turns Execution IR JSON into Zig source.

## Decision

- **Zig tools live under `tools/zig/<tool>/`** and build with the Zig pinned in `mise.toml` (0.17.0), one `zig build-exe main.zig` each, with no `build.zig` and no dependencies beyond `std`.
- **The emitter (`tools/zig/emitter`) is a port of `ZigBackend.runner`**: the program (`emit`), its scripted fakes (`fakeCapabilities`) and the runner's `main`, which dispatches every runnable function, or only the entry named after the IR file, decoding each argument from the command line. It reads one Execution IR JSON file (the form `ExecutionIrSerializer` writes) and prints the complete runner on standard output (exit 0), or the unsupported constructs one per line (exit 2). Anything else is a failure.
- **runPure's Zig route uses it.** The authoring session builds it once per process into the per-user runner cache (`emitter-<hash of its sources>`, moved into place after the build), writes the IR to a temporary file there and reads the runner back; F# keeps only the run itself (argument tokens, the build of the runner, the reply). The first stage ported `emit` and `fakeCapabilities` alone; the second (same day) moved the runner's `main`, entry selection, `typeOf` and `fakeArgument` too, so the route's code generation is entirely in Zig.
- **The F# emitter stays as the reference for this stage.** With `NYRWVY_ZIG_EMITTER_CHECK` set (the extended test settings set it), the Zig route also runs the F# emitter and fails with `RunBackendMismatch` on any byte difference, or when only one of them rejects the program; the message lists of two rejections are not compared. So every Zig parity test (`ZigBackendTests`) is also an emitter parity test, and one more test emits every repository snapshot, whole and per entry, through both.
- **Shared text is one file.** The runtime the emitter copies into every program is `tools/zig/emitter/runtime.zig` (and the runner's token and envelope support `runner_support.zig`), embedded in the F# assembly as a resource and in the Zig emitter by `@embedFile`. The case-mapping runs are computed from .NET's Unicode data in F#, the mapping the C# backend applies; the Zig emitter embeds a generated copy (`case_mapping.zig`), and a fast test fails when it differs from what .NET computes.

## Changes to the F# emitter

Its output had to become a function of the IR JSON alone, so the Zig port can reproduce it. Neither change alters what a program does.

- **Order:** functions, blocks, capabilities and operations, jump arguments, `ProductUpdate` fields and callback contexts are taken in the order the IR JSON lists them (sorted by ID), not in the in-memory list order.
- **Instance names:** a generic instance's suffix hashes the IR JSON of its type arguments instead of F#'s `%A` text, which only .NET can produce. The Zig emitter writes that JSON itself, with System.Text.Json's default escaping, because substituted type arguments are not in its input.

## Reason

The emitter's input and output are both text with a byte-exact reference, so the port can be checked completely and every existing Zig test checks it for free. It is also the part a Zig-only tool chain needs first: a runner for Zig programs that does not start .NET to generate them.

## Consequences

- runPure's Zig route needs the repository's `tools/zig/emitter` beside `mise.toml` (the place `zigDirectory` already finds); the first Zig run in a process may build the emitter (a few seconds, cached after).
- A change to the emitter is made in both languages until the F# one is retired; the extended suite reports any difference.
- Unsupported-construct messages name a type by its IR JSON on the Zig route, not by F#'s `%A` text.
- The emitted source now crosses a process boundary, so runPure's 1 MiB output limit (`RunOutputTooLarge`) applies to it; the runtime and case mapping take about 70 KB, so only very large programs reach it.
- The check covers only the instruction kinds the extended suite reaches; on 2026-10-27 that is all 192 the emitter knows (one test exists only to reach the kinds no other Zig test used). A new kind needs a checked program too.
- Strings compare by UTF-8 bytes in Zig and by UTF-16 code units in F#; the two orders differ only beyond the Basic Multilingual Plane, which stable IDs never use.

## Second tool: the snapshot reader

Snapshot reading and validation is about ten times the emitter's logic (about 7,800 lines of F# in the record codec, the JSON codec, schema, migration and validator, against about 800), so it moves in three slices, each checked against its F# stage:

1. **Record text to the writer's JSON** (done, `tools/zig/snapshot-reader`): every record-form check of `RecordCodec` (grammar, canonical order and spelling, block structure, dangling references, the depth limit), stopping where `RecordCodec` hands the JSON to `SnapshotCodec`'s reader. Its reference is `RecordCodec.toJson`, which returns that JSON, or the record error, including the `position=` placement error that `deserialize` reports only after the model check. Usage: `snapshot-reader <in.nyrec> <out.json> [<in> <out> ...]`, one `ok` or `error <line>:<column>: <message>` line per pair; columns count UTF-16 code units as the F# reader does. The per-kind key table moved to `tools/zig/snapshot-reader/record_kinds.txt`, embedded on both sides.
2. **The JSON model reader** (done for schema versions 21 to 24, `tools/zig/model-reader`): every shape check of `SnapshotCodec`'s reader (each object's properties, value types, stable IDs, integers as `TryGetInt64` reads them, float bits, omitted-rather-than-empty lists, true-or-omitted markers), the schema version and the construct minimums, then the writer's canonical JSON for the decoded model (order, spelling, schema 24). Its reference is `SnapshotCodec.toCanonicalJson`, which is `deserialize` without `SnapshotValidator.validate`, followed by the writer. Usage: `model-reader <in.json> <out.json> [<in> <out> ...]`, one `ok`, `skip legacy schema <n>` or `error <Case>: <message>` line per pair (the `SnapshotCodecError` case; a line break inside a message is written `\n`). The per-kind reader table (context, properties in reading order with their shapes, the writer's order where it differs) is `tools/zig/model-reader/model_kinds.txt`, extracted once from the F# reader and checked by the comparison; the construct rows above schema 21 and the supported range are `schema_minimums.txt`, generated from `SnapshotSchema` and compared by a fast test.
3. **Semantic validation** (`SnapshotValidator.validate`, `Validation.fs`: 185 distinct codes, plus the 7 of `CapabilityImplementations.validate`, which it reports for `CapabilityConstruct`), split into sub-slices by what a rule needs from outside the decoded model:
   - **3a. Model-only rules** (done, `model-reader --validate`, 39 codes in `tools/zig/model-reader/validation_codes.txt`): the parent self-reference; duplicate IDs of every declaration, member, graph node, pattern binding and obligation; duplicate open obligations per call and parameter; blank display names; unknown effects of capability operations and functions and a function's duplicate effect; declared type parameters (blank or duplicate names, duplicate IDs, one ID shared across declarations, not inferable from the parameter types, a type parameter in a capability operation, irregular recursion); obligation targets, parameters and resolutions. They use only structural walks (`ValueGraph.collectNodes`, `SemanticFacts.collectPatternBindings`, `TypeParameters.occurring`), no inference or substitution.
   - **3b. Type references and node payloads** (done, 8 more codes): `UnknownNamedType`, `NamedTypeArityMismatch`, `UnknownCapabilityType`, `BuiltinGenericArityMismatch`, `TaskTypeInDeclaredType` on declarations, pattern bindings and the 11 `validateTypeRef` sites of `validateGraph` (their messages carry no function prefix: `validateTypeRef` uses the outer `add`); `TypeParameterNotDeclared` (`SemanticNodeShape.payloadTypeRefs`); `TaskTypeAtCapabilityBoundary` (`TaskTypes.bearing`); `GraphNodeDependencyCycle` (`SemanticNodeShape.dependencies`). The Set item and Map key equatability checks (`EquatableTypes`) are ported here too, but their codes were listed only with 3c, which emits them again from typed nodes.
   - **3c. Typed graph rules** (done, 132 more codes): the per-function loop. Its base is the node type resolver of `SemanticFacts` (`Resolver` in `main.zig`): the F# resolver resolves every node eagerly when it is created, by a post-order search over `nodesById` in ordinal ID order, and memoises every result, including the `None` of a node met again on the current path. A later query only reads the memo, so the order in which rules ask does not matter, but the order of the search does: on a dependency cycle it decides which node is cut. The search is ported exactly, with `directValueReferences` in operand order from `tools/zig/model-reader/node_references.txt` (per kind, the properties it reads; a fast test checks it against F# on the all-kinds snapshots with a distinct ID per reference). `DiagnosticText.typeRef` and `EquatableTypes.describeIn`/`explainIn` are separate renderers, as in F#. The rules follow `validateGraph`'s traversal (scopes of value nodes and pattern bindings, nested graphs) in groups, one commit each: graph structure (results, scopes, unknown parameters and pattern references, lone surrogates, Bool operands, Conditional, abort values, the function result); scalar operands (String, Int64, Float64, Bits32 and Bytes, as one table over operand positions, and ValueEqual); List, Set, Map, Option and Result inputs; products, unions, abort and the matches; callbacks, effect bodies and tasks (folds, the List/Set/Map/Option/Result callbacks with their context bindings and `PureFunctions.isPure`, UseResource, ExceptionCatch, CancellationShield, TaskScope, TaskStart, ParallelAll, TaskWait, OneShot, TaskCancel); calls, function values and capabilities (with `CapabilityImplementations.validate`). A code is listed only once every site that emits it is ported; until then its ported sites run and report nothing (`add` skips unlisted codes). Two codes cannot occur on this path and stay unlisted: `NullStringLiteral` (the reader requires a string) and `EmptyUnionMatchArm` (the reader requires a variant per arm).
   - **3d. Order and waiting** (done 2026-10-28, the last 4 codes, so all 183 that can occur are listed): `AmbiguousEffectOrder` (`GraphOrder.tryAbortOrderConflict` with the semantic view: per graph level the observable nodes sorted by ID, the first pair with no dependency path either way, else the nested graphs in order; the topological fast path of `tryUnorderedPair` is not ported, because it returns early only when every pair is ordered, where the pairwise search finds none either), `MustNotWaitFunctionWaits` (`Waiting.derive` and `describe`: the rounds over the functions in list order, which see what the same round added and so decide the path), `OneShotScopePayloadUnsupported` (`validateTypeRef`, `OneShotPayloadRequirements.invalidCallbackUses` and `.violates` on a direct call's substitution) and `TaskBoundValueCrossesTask` (`rejectTaskBound` on the item or source, context bindings and worker result of TaskStart and ParallelAll, and `TaskCrossingRequirements.invalidInstantiations`, distinct per node and callee). Both requirement analyses share `instantiations` (each function reference whose callee's type parameters follow from its arguments and its node's iteration values, by kind) and a monotone fixed point, whose result does not depend on the order of its rounds. The callback and crossing issues carry no function prefix, nor does the waiting one (its loop follows the per-function loop).

The first slice is checked by an extended test, not inside runPure: the reader is a library stage with no process of its own to compare. The test feeds both readers the repository's `.nyrec` snapshots, the record-format fixtures, one snapshot per node kind (`RecordCodecAllKindsTests`), about 600 deterministic mutations of them (lines dropped, repeated, swapped, cut, blanked, a wrong character), and targeted cases for string spelling, the depth limit, the header's dependency marker and schema range; it compares the JSON byte for byte, or the full error line, and requires both outcomes to occur. On 2026-10-27 that is about 1,000 texts: about 240 accepted, the rest rejected with about 60 distinct messages.

The second slice has its own extended test on the same pattern: the all-kinds snapshots, the record-format fixtures and the repository's `.nyrec` snapshots (through `RecordCodec.toJson`), each all-kinds snapshot relabelled 21 to 23, deterministic structural mutations (a property dropped, added, retyped or duplicated with either copy first, an ID blanked or broken, an array rotated, the schema version or a node kind changed, a string or marker replaced), for the first node of each kind an unsupported property and every property dropped and retyped, and targeted cases (escaped names, lone surrogates, float bits, integer spellings, visibility markers, type nesting on both sides of the depth limit, cut texts). It compares the JSON byte for byte, or the error line; `InvalidJson` and the `Invalid JSON string encoding:` messages, which carry .NET's text, are compared by case and prefix only. On 2026-10-27 that is about 3,200 texts: about 1,000 accepted, 2,200 rejected with about 780 distinct messages, 13 legacy documents skipped, and no input on which the F# writer throws.

Sub-slice 3a is a mode of the model reader rather than a new tool: it needs the reader's parsed document and its shape verdict, and a separate tool would duplicate the parser or import across tool directories. After a successful shape read it walks the parsed document, not the canonical output: the F# reader keeps document order and the writer sorts, and the validator's `Map.ofList` and node-owner lookups are last-wins under duplicate IDs. Usage: `model-reader --validate <in.json> [<in> ...]`; per input the reader's `error`/`skip` line, or one `issue <Code>: <message>` line per issue (line breaks written `\n`) and `end`. Its reference is `SnapshotValidator.validate` of `SnapshotCodec.readUnvalidated` (the shape-decoded model, without dependency resolution), filtered to the listed codes. Filtering is sound: `validate` only accumulates issues, with no early return or section gated on another rule's issue, and sorts them by (code, message) ordinally at the end, so the listed rules' issues and their order do not depend on the excluded rules. The Zig side sorts the same way over UTF-16 code units. Inside the per-function loop (whose `add` prefixes "In function …: ") the rules read derived facts (node types and completions from the resolver, which is ported whole, purity, type matching, the requirement analyses), never another rule's issue. A code is listed only when every site that emits it is ported, so no listed code loses an issue to an unported site; since 3d every code that can occur is listed, and the filter drops only the two that cannot. The one coupling left is the F# validator throwing on a model (`DiagnosticText.typeRef` on `Exception` with type arguments, say); the test counts such inputs and skips them (none so far).

The extended test (`ZigValidatorTests.fs`) uses the slice-2 originals (all-kinds snapshots, record-format fixtures, repository snapshots), named edits that keep the shape valid and break the listed rules, random combinations of two or three edits, and two slice-2 shape mutations per original. The 3a edits copy declarations, take another's ID, blank display names, point references nowhere, declare type parameters and add obligations. The 3b and 3c edits break type references (unknown, extra or missing arguments, task scopes, types that are not equatable, undeclared type parameters), make dependency cycles (self references, a nested node naming its enclosing node), point every `…NodeId` operand at literals of one type, at literals by position in three rotations and at typed containers (List, Set, Map, Option, Result) by position in six, end graphs in literals, add abort nodes, change function signatures (an extra or a dropped parameter, Bytes parameter and result types, a required effect, a type parameter), add self calls, and duplicate, retarget, drop or retype field bindings, union match arms, context and argument bindings and capability implementations. The 3d edits add whole generic functions to every original: a task-bound capability whose values reach a ParallelAll source, a TaskStart item and context binding and a worker result, and a generic function forwarding its type parameter into a ParallelAll, called with the capability type; a function returning `OneShot<T>` called with a TaskScope list directly, through a generic forwarder and as a ListMap callback; and must-not-wait on every function, may-wait on every operation, with a call that reaches a TaskWait. Effect order needs no edit of its own: the abort edits already leave abort nodes unordered against effects. It compares the issue lines exactly, requires every listed code to occur and both clean and failing models. On 2026-10-28 that is 13,976 texts: 450 clean, 13,129 with listed issues, 391 shape rejections, 6 legacy skipped, no F# validator failures; the 3d codes occur 271 (`AmbiguousEffectOrder`), 727 (`MustNotWaitFunctionWaits`), 944 (`OneShotScopePayloadUnsupported`) and 1,406 times (`TaskBoundValueCrossesTask`). Fast tests check that each listed code is a code of `Validation.fs` (or `CapabilityImplementations.fs`) and that `node_references.txt` follows `directValueReferences`. Limits: each node kind's rules rest mostly on its one all-kinds snapshot, so a few codes occur only once to four times (`ValueEqualOperandTypeMismatch`, `ValueEqualTypeNotEquatable`, `EmptyProductUpdate`, the invalid and unknown product construct and update targets, `ListAppendItemTypeMismatch`, the three `…ItemTypeNotEquatable` list codes, `FunctionInvokeArgumentTypeMismatch`, `FunctionInvokeArityMismatch`, `UnknownCapabilityConstructTarget`, `DuplicateCapabilityImplementation`, `CapabilityImplementationSetMismatch`, `ImpureCapabilityImplementation`, `CapabilityArgumentTypeMismatch`); the obligation rules rest on the few originals with a direct call taking arguments; last-wins lookups under duplicated node IDs across functions are exercised only through random combinations; the 3d sites rest mostly on the added functions, so a few message forms occur only where an original happens to supply them (a ParallelAll context binding of a task-bound value, a waiting capability operation, a wait reached through a callback rather than a direct call).

Limits of the second slice: versions 9 to 20 (and so migration) are reported as `skip legacy schema <n>` and not compared; no semantic validation, so it accepts models `deserialize` rejects as `InvalidSnapshot`; input that is not valid UTF-8 is rejected outright. `MaximumDepthExceeded` cannot occur on this path: the writer's depth equals the input's, which JsonDocument already limits to 1,000.

Limits of the first slice: a local snapshot that names its dependency's subjects is rejected (the dependency is not read yet), and input that is not valid UTF-8 is rejected outright, where the F# reader sees U+FFFD.

## Revisit conditions

Retire the F# emitter (and the check) once the Zig emitter has run unchanged through several backend slices; the legacy versions of slice 2 and slice 3 of the snapshot reader follow (see above).

# Declaration visibility, private by default

- **Status:** Accepted
- **Date:** 2026-10-19
- **Roadmap:** [legacy cutover](../plans/post-m2-roadmap.md#legacy-cutover-planned) ("also in the cutover"; owner decision of 2026-10-19), implemented ahead of the cutover as snapshot schema 21 / Nyason `nayamnyam.snapshot.v17`

Every declaration of a snapshot was usable from every snapshot that depended on it. A library could not keep a helper function, an internal type or an internal capability to itself: whatever it declared, a dependent could name, call and build values of, so an upgrade of the library had to treat every declaration as part of its contract ([pinned dependencies](../specs/agent-authoring-session.md#pinned-snapshot-dependencies)).

## Decision

- **Visibility.** Types, effects, capabilities and functions carry a visibility: exported or private (`Exported: bool` on `SemanticType`, `SemanticEffect`, `SemanticCapability` and `SemanticFunction`). A new declaration is private unless its creation request says `"exported": true` (`simulateCreateType`/`ByName`, `simulateCreateTypesByName` items, `simulateCreateEffect`, `simulateCreateCapability`/`ByName`, `simulateCreateFunction`/`ByName`; the shared `nyrwvy_create_type` and `nyrwvy_create_function` tools take `exported`). The structural operation `setExported` (`simulateOperations` with `typeId`, `functionId`, `effectId` or `capabilityId`; `simulateOperationsByName` with `type`, `function`, `effect` or `capability`; each with `exported`) changes one declaration's visibility and nothing else; the review's `diff.visibilityChanges` lists the net changes (`kind`, `id`, `displayName`, `exported`), the same visibility is `VisibilityUnchanged`, and a set-and-reset batch is `NoChange`. `declarations`, the function summaries of reviews and the viewer show `exported`.
- **Inside one snapshot nothing changes.** Every declaration is usable locally whatever its visibility; validation, execution and the C# backend are unchanged, since a resolved program is still one graph and an exported function may call a private one.
- **Across a dependency.** A dependent sees only the exported declarations of its dependency: the private ones are left out of `declarations`, of provenance and of name resolution, so a by-name request that names one fails as an unknown name. A proposal whose candidate refers to a private imported declaration by exact ID (in a signature, field type, operation type, required effect or body) is rejected before registration with `ImportedDeclarationNotExported`, beside `ImportedDeclarationModified`; `setExported` on an imported declaration is `ImportedDeclarationModified`. An upgrade preview lists exported additions, removals and changes first and private ones after them, each with its `exported` flag, and reports an existing local reference to a declaration the new version no longer exports as an `ImportedDeclarationNotExported` issue, so the preview is incompatible and `simulateDependencyUpgrade` rejects it with the same code.
- **Persistence.** Visibility is the construct `DeclarationVisibility` of snapshot schema 21 / Nyason `nayamnyam.snapshot.v17`. From that version on an exported declaration carries `"exported": true` (Nyason `exported true`) and a private one omits the marker, so a snapshot of private declarations keeps its bytes minimal; `"exported": false` is rejected so that private has one spelling. A document below schema 21 has no visibility, and every declaration in it reads as exported, which is what its declarations meant when it was written. The internal fingerprint encoding uses the smallest version that holds every construct: an all-exported snapshot can keep its older canonical bytes. Ordinary writers now always persist schema 21 with explicit markers; see the [writer follow-up](../verification/current-schema-typed-values-20261019.md).
- **Fingerprints.** Visibility is part of both the snapshot fingerprint and the semantic fingerprint, because it changes what a dependent may use: the fingerprints go through the codec, and a private declaration changes the bytes. An existing document (schema 9 to 20) keeps its fingerprints: it reads as all-exported and the internal canonical encoding yields the same bytes at the same version; the semantic fingerprint's normalized snapshot does the same. Current persistence can change the representation without changing either hash. Marking a declaration private is therefore a semantic change, and `DependencyGraph.combine` treats the same identity with different visibility in two dependencies as a conflict.
- **Migration.** The cutover's migration command marks every declaration of an existing snapshot exported and writes it at the current version with explicit markers, so existing dependents keep working; until then the version-gated default gives the same reading.

## Reason

Private by default is the owner's choice: a declaration becomes part of a library's contract only by an explicit act, and an upgrade preview can then separate contract changes from internal ones. The marker spelling (`exported` present or absent) follows the convention of the other optional constructs, keeps private snapshots smallest, and lets the reader of an older version decide by version alone, without a per-declaration default that would change meaning silently. The alternatives considered:

- **A `visibility` enumeration** (`"visibility": "private"` written for every declaration): one more token on every declaration of every new snapshot for two values, and a new required property that no older reader could ignore.
- **Hiding at the semantic core** (filtering private declarations out of the resolved graph): breaks the resolved program, since an exported function may call a private one; the core keeps every declaration, and visibility is a policy of the authoring surface like read-only imports.
- **Visibility outside the fingerprint:** a dependent could not tell from a fingerprint that its dependency's contract shrank; and the codec-based fingerprints include it anyway once it is in the bytes.

## Consequences

- A library author exports deliberately. A function that a dependent should call needs `exported: true`, and so do the types, effects and capabilities in its signature: the session does not check that an exported signature mentions only exported declarations, so a dependent that cannot name a private type in an exported signature cannot build a value of it by name; `setExported` fixes that after the fact.
- Making a declaration private that a dependent already uses cannot be checked by the library's session, which does not know its dependents; the dependent learns it from the upgrade preview (`ImportedDeclarationNotExported`) and keeps its current pin until the library exports it again.
- Private imported declarations have no display name on the dependent's side; a diagnostic that mentions one shows its ID.
- `docs/specs/agent-authoring-session.md`, the [type](../specs/type-declaration-authoring.md), [effect](../specs/effect-declaration-authoring.md) and [capability](../specs/capability-declaration-authoring.md) declaration specs and the [schema policy](../specs/schema-evolution-policy.md#snapshot-schema-versions) describe the contract; `DeclarationVisibilityTests` covers the codecs, the legacy default, the fingerprints, the hiding, the rejections, the upgrade preview order and the operations.

## Revisit conditions

Namespaces, qualified names and first-class modules stay out of scope until a program needs them. Revisit a check that an exported signature names only exported declarations when a probe shows a dependent blocked by a private type in an exported signature more than once.

# Wait and task-bound attributes

- **Status:** Accepted
- **Date:** 2026-10-27
- **Plan:** [backend-neutral semantics and generated library bindings](../plans/multi-backend-and-bindings.md#3-operations-that-wait), §3 and the task-bound part of §7, Order step 2; implemented as snapshot schema 24 / Nyason `nayamnyam.snapshot.v20`

A JavaScript backend has to make every function that can wait `async`, a UI entry (a key handler that must return `Handled`, a render callback) must not block its thread on any backend, and a UI toolkit's objects must stay on the thread that created them. Nothing in the graph said which operations wait or which capabilities belong to one task.

## Decision

- **May wait.** A capability operation carries `MayWait` (wire and JSON `"mayWait": true`, record `may-wait=true`); the default is false. It means the operation can wait for an external event for an unbounded time; it is a property of the operation, not of a backend.
- **Derived "may wait" fact** (`Waiting.derive`, `src/Nyrwvy.Semantics/Waiting.fs`). A function may wait when its body has a builtin wait — `TaskWait`, `OneShotWait`, `ParallelAll` (it joins its workers) or `TaskScope` (closing it joins its tasks), the points where the C# runtime blocks — or invokes a `MayWait` operation (including a `UseResource` release), or runs a function that may wait: direct calls, list and Option/Result callbacks, `ListEffectFold` folders, `ExceptionCatch` bodies and handlers, `CancellationShield`, `UseResource` and `TaskScope` bodies, and `TaskStart` and `ParallelAll` workers. Nothing declares it, so unlike [body effect requirements](../specs/body-effect-requirements.md) it is transitive. Function values (`FunctionReference`) and capability implementations are not followed: validation already requires both to be transitively pure (`ImpureFunctionReference`, `ImpureCapabilityImplementation`), and a pure function contains no builtin wait and no capability call. The fact is never persisted. `readFunction`, function focuses and the creation and body-replacement reviews show `"mayWait": true` with a `waitPath` (`helper (node '…') -> TaskWait (node '…')`) when it holds; the viewer shows the same line.
- **Bounded waits count.** A `TaskWait` or `OneShotWait` with a limit still waits, as `ParallelAll` and `TaskScope` do: a limit bounds the wait, it does not let a UI thread return at once.
- **Must not wait.** A function carries `MustNotWait` (`"mustNotWait": true`, record `must-not-wait=true`). Validation rejects a must-not-wait function that may wait with `MustNotWaitFunctionWaits`, naming the path to the waiting builtin or operation. The check holds on every backend.
- **Task-bound capability.** A capability carries `TaskBound` (`"taskBound": true`, record `task-bound=true`): its values belong to the task that created them. Validation rejects `TaskBoundValueCrossesTask` when a value whose type can hold one — directly, or inside containers, function types and declared Products and Unions, traversed as `TaskTypes.bearing` traverses task handles — is a `TaskStart` item or context binding, a `ParallelAll` source list or context binding, or the result of a `TaskStart` or `ParallelAll` worker. A generic function whose type parameter reaches such a position, directly or through generic calls that forward it, is checked per instantiation: the call or callback node that instantiates it with a type that can hold a task-bound capability is rejected with the same code (`TaskCrossingRequirements`, mirroring the OneShot payload requirements). This is stricter than [parallel capability sharing](../specs/parallel-capability-sharing.md), which only asks providers to support concurrent calls.
- **Authoring.** Creation takes the markers: `mayWait` on each capability operation of `simulateCreateCapability`/`ByName` and of `addCapabilityOperation`, `taskBound` on `simulateCreateCapability`/`ByName`, and `mustNotWait` on `simulateCreateFunction`/`ByName` and on `simulateCreateFunctionsByName` items (the shared `nyrwvy_create_function` tool takes it too). Three operations change one marker and nothing else: `setMayWait` (`operationId`, or by name `capability` and `operation`), `setTaskBound` (`capabilityId` or `capability`) and `setMustNotWait` (`functionId` or `function`), each with the value under the marker's own name. The review's `diff.attributeChanges` lists the net changes (`attribute`, `id`, `displayName`, `value`); the same value is `AttributeUnchanged` and a set-and-reset batch is `NoChange`. A change to a marker of an imported capability or operation is `ImportedDeclarationModified`. `declarations` and the function summaries show each marker when it is true.
- **Persistence.** The markers are the construct `WaitAttributes` of snapshot schema 24 / Nyason `nayamnyam.snapshot.v20`, written only when true; `false` is rejected so there is one spelling. Their default is false, so unlike [declaration visibility](declaration-visibility.md) no version-gated reading is needed: a document without them reads unchanged at any version, a snapshot that uses none keeps its minimum version, canonical bytes and fingerprints, and a document below 24 that carries one is rejected as needing schema 24. Ordinary writers write 24, the current version. As for visibility, the fingerprints go through the codec, so a true marker is part of both fingerprints without a new fingerprint domain: a snapshot without markers hashes the same bytes as before.
- **Dependencies.** The markers of imported declarations are read-only, and validation sees the resolved graph, so a dependent's must-not-wait function that reaches an imported waiting operation is rejected, and a dependency upgrade that marks an operation the dependent reaches makes the upgrade preview incompatible.
- **Backends.** C# and Zig block a thread and need no change. The JavaScript lowering (`async` for every function that may wait) and the mapping-table report for an unmarked operation bound to an asynchronous target come with those backends.
- **`libraries/host`** marks `Fs.readText`, `Fs.readBytes`, `Fs.writeBytes`, `Process.run`, `Pty.read` and `Ptys.close` (it waits for the child after the hangup); the change was made through the authoring session with `setMayWait`.

## Reason

"May wait" has to be derived because nobody declares it on functions; making callers declare it would repeat effect requirements for a fact the graph already implies. The three markers follow the spelling of the other optional markers (present when true, omitted otherwise), so a snapshot that does not use them is unchanged, and a new schema version keeps an older reader from silently dropping a marker it does not know ([closed decoding rule](../specs/schema-evolution-policy.md#closed-decoding-rule)). Rejecting task-bound values at task boundaries, including worker results, is the only check that can be made without tracking which task created a value.

## Consequences

- A must-not-wait entry that needs a file or a process result has to receive it from elsewhere (for example a task that publishes it through a `OneShot`), as a UI thread must anyway.
- A program-defined capability's operations default to not waiting; its implementations are pure, so they cannot wait.
- `OneShot` payloads are not checked for task-bound values: completing a cell in one task and waiting on it in another moves the value across tasks. Left out until a program uses task-bound capabilities with one-shot handoff.
- `docs/reference/language-subset.md`, the [capability declaration](../specs/capability-declaration-authoring.md) spec, the [schema policy](../specs/schema-evolution-policy.md#snapshot-schema-versions) and the [parallel capability sharing](../specs/parallel-capability-sharing.md) contract describe the rules; `WaitAttributesTests` covers the derivation, the rejections, the codecs and the wire forms.

## Revisit conditions

Revisit bounded waits when a must-not-wait entry needs a zero-limit poll of a task or cell (`TaskWait` with limit 0) that cannot block. Revisit the task-bound check if a toolkit needs to hand an object to another task explicitly (a marshalling operation) or if `OneShot` handoffs of task-bound values appear.

# Declared function type parameters

- **Status:** Accepted
- **Date:** 2026-10-19
- **Roadmap:** part of the [legacy cutover](../plans/post-m2-roadmap.md#legacy-cutover-planned) (owner decision of 2026-10-19), implemented ahead of the removal step so that the cutover's single migration covers it

Until this change a function had no type parameter list of its own: its type parameters were whatever `TypeRef.TypeParameter` occurrences its parameter types contained, in first-appearance order, and every occurrence carried its own display name. A Product or Union, by contrast, declares its type parameters in order ([generic types](generic-types.md)). The implicit rule had no place to attach anything to a type parameter (a later constraint such as `equatable`, or a documented order for the backend's generic method), and the per-occurrence names needed their own consistency check (`TypeParameterDisplayNameConflict`) and were duplicated through every body type reference.

## Decision

- **Declared list.** `SemanticFunction.TypeParameters` lists a function's type parameters in order, `(TypeParameterId * displayName)`, exactly as `SemanticType.TypeParameters` does. `TypeRef.TypeParameter` carries the identity only; the display name lives with the declaring function or type, and presentation (diagnostics, wire output, the viewer, the C# backend) looks it up there (`TypeParameters.names`).
- **Validation.** Every type parameter a function's parameter types, result type, pattern bindings or body type references mention must be in its list (`TypeParameterNotDeclared`), and every listed type parameter must be mentioned by at least one parameter type (`TypeParameterNotInferable`), so a call can still derive every type argument by structural matching: the semantics of calls, callbacks and self calls are unchanged. Names in one list are nonblank and distinct (`TypeParameterDisplayNameBlank`, `DuplicateTypeParameterName`, `DuplicateTypeParameterId`); a type parameter still belongs to exactly one function or type (`TypeParameterSharedAcrossFunctions`). `TypeParameterDisplayNameConflict` is gone, since an occurrence has no name to conflict.
- **Declared but unmentioned is rejected, not allowed.** A type parameter that no parameter type mentions could only be chosen explicitly at each call, which the language does not offer (type arguments are always derived by matching); allowing it would make such a function uncallable in a well-typed way. The old rule implied the same restriction.
- **Creation.** A function creation request may list `typeParameters` (wire: `"typeParameters": ["T", "U"]`, each named in the types as `{ "kind": "typeParameter", "name": "T" }`); the list fixes the order. Without it the list is derived from the parameter types in first-appearance order, the old rule, so existing clients and transcripts keep working. A request whose list misses a mentioned name, lists an unmentioned one, or repeats a name is rejected (`FunctionCreationTypeParameterNotDeclared`, `FunctionCreationTypeParameterNotInferable`, `FunctionCreationDuplicateTypeParameter`). Creation then gives each declared type parameter a fresh system-owned identity, as before. A request-local identity is spelled as its name (`{ "kind": "typeParameter", "name": "T" }` is the type parameter with ID text `T`), which is what names it in a rejection.
- **Signature edits.** `addFunctionParameter` appends a type parameter the new parameter type introduces to the list; `removeFunctionParameter` drops the type parameters no remaining parameter type mentions, and a result or body that still uses one fails validation as `TypeParameterNotDeclared`, as before. Migrations keep an existing function's identities.
- **Order is the backend's order.** The C# backend emits a generic method's type parameters in declared order; the typed semantic IR and Execution IR carry the list (`typeParameters` on a function, as on a type), and type parameter occurrences in the IR carry no name.
- **Persistence.** Snapshot JSON 21 / Nyason `nayamnyam.snapshot.v17` write a function's `typeParameters` (omitted when empty, like a type's) and type parameter occurrences without `displayName`. A function whose list is exactly the one its parameter types imply uses no new construct, so such a snapshot is still written at its earlier version in the earlier form (names on the occurrences, no list on the function): its bytes, snapshot fingerprint and semantic fingerprint are unchanged. Only a list in another order needs version 21 (`DeclaredFunctionTypeParameters` in `SnapshotSchema.minimumVersions`). Reading a document below 21 derives each function's list from its parameter types in first-appearance order and takes each name from the occurrences, exactly the old rule, so every existing snapshot decodes to the same semantic state and keeps its fingerprints; a document below 21 that carries an explicit list is read so that the reader can name the construct and the version it needs. The semantic fingerprint domain stays at `v6`: for every snapshot that was representable before, the normalized bytes are identical, and the declared order enters the fingerprint only for a snapshot that could not exist before.
- **Review kind rename.** The `fieldlessUnionVariantEvolution` review kind, a known misnomer since the workflow gained field-bearing variants ([authoring-surface queries and parity](authoring-surface-queries-and-parity.md)), is `unionVariantEvolution`. The rename shares this review-shape change, as that record asked; its wire name `simulateAddUnionVariantLike` is unchanged.

## Reason

A declared list makes a function's generic interface explicit and gives a later per-parameter fact (a constraint, a variance, a documentation string) a place to live without another replacing change to the snapshot schema, while the implicit rule stays available as the default so no client has to change. Keeping the semantics identical (matching derives every type argument; every type parameter is mentioned by a parameter type) means no program means anything different after the change, and writing a derived list in the old form means no stored snapshot changes its bytes or fingerprints merely by being read and saved again. Dropping the per-occurrence names removes duplicated state and a validation rule whose only job was to keep that duplication consistent.

## Consequences

- `TypeRef.TypeParameter` is a single-field case; code that rendered a type must take the names from the owning declaration (`DiagnosticText.typeRefIn`, `WireEncodeCommon.typeRefIn`, `EquatableTypes.describeIn`). A diagnostic about a function being created names its type parameters from the request.
- Wire output of a function (`declarations`, `readFunction`, reviews) carries `typeParameters` for a generic function, in declared order, and each type parameter occurrence in a declaration or body carries `displayName` when its owner is known; the exact-ID input form accepts and ignores `displayName`.
- The IR debug writers move to schema version 14.
- `DeclaredFunctionTypeParametersTests` covers the pre-21 writing form and legacy reading (derived order, names from occurrences, unchanged bytes and fingerprints, equality with an explicit twin), the version-21 form, the validator rules, the backend's generic method order and wire creation with explicit and derived lists. `SnapshotSchemaTests` has the version row.
- The migration command of the cutover derives each list from the occurrences, which is the same as reading the document.

## Revisit conditions

- A program needs a constraint on a type parameter (`equatable` for a generic `Set<T>` item, numeric operations over `T`); the list is where it would be declared.
- A program needs a function type parameter that no parameter type mentions (explicit type arguments at a call); that would be a language change, not a relaxation of `TypeParameterNotInferable`.

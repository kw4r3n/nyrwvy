# Authoring-surface queries and name-resolved parity

- **Status:** Accepted
- **Date:** 2026-10-18
- **Roadmap:** [selection rule](../plans/post-m2-roadmap.md#selection-rule-from-here) (an operation is added when its existence is warranted); the T1 row of the [general-purpose programming roadmap](../plans/general-purpose-programming-roadmap.md)

Four gaps of the maintained authoring surface were observed while agents maintained programs through the session: a Capability operation could be deleted but not added once the Capability existed, so a new operation meant recreating the Capability under new identities and repairing every user; a deletion rejected with "still referenced" named only the first blocking issue and offered no way to list the sites to repair; the session kept pending proposals but could not list them, so an agent that lost a `proposalId` could neither commit nor reject it; and several operations existed only in exact-ID form (`verifyChange`, the parameter and result type migrations, renames, additions) although the equivalent deletions, removals and body edits had `…ByName` forms. The Union variant evolution workflow also still carried a `Fieldless` name from the slice it was written for.

## Decision

- **`addCapabilityOperation`** joins the ordinary `simulateOperations` set, the counterpart of `deleteCapabilityOperation`. The Capability keeps its ID; the operation and parameter IDs are system-owned. Because a [program implementation](../specs/program-capability-implementations.md) must cover exactly the Capability's operations, the request carries one implementation plan `(constructNodeId, functionId)` per `capabilityConstruct` of the Capability and is rejected with `CapabilityImplementationPlanMismatch` otherwise, the same exhaustive-plan rule `addProductField` applies to constructions and `addFunctionParameter` to call sites. No obligation kind is added: a missing-argument obligation records a value an agent can supply later without changing a type, whereas a construction missing an implementation is a type-level hole the backend cannot emit, so a construction must be made whole in the same publication. Each plan is checked with the implementation contract (signature, purity, monomorphism) before the proposal is built, so the rejection names the validator's own code and the construction. The diff reports `capabilityOperationsAdded` and `capabilityImplementationsBound`, present only when non-empty.
- **`references`** lists every site of the current snapshot that refers to a function, type, variant, field, effect, capability or capability operation: declaration signatures (parameter and result types, required effects, field types, operation signatures and effects) and body nodes with a role (`directCall`, `construct`, `fieldAccess`, `match`, `invoke`, `implementation`, `typeArgument`, `patternBinding`, …), nested bodies included. It takes the subject by exact ID or by display names, and is also reachable as the `references` view of `nyrwvy_inspect`. It replaces the session's unused `GetUses`/`GetDependencies`/`GetCallers`/`GetCallees` members, which no operation reached: callers and callees stay in the function focus, and node-level uses and dependencies are the focus's dependency facts. The deletion-safety rejections (`TypeStillReferenced` and its siblings) now list every blocking validation issue, not the first.
- **`proposals`** lists the pending proposals with their kind, base snapshot, whether that base is still current, and a one-line summary naming the targets by display name; `status` reports `pendingProposalCount`. Summaries are presentation only: the review is read with `readProposal`, and commit still binds the exact reviewed proposal.
- **Name-resolved parity:** `verifyChangeByName`, `simulateParameterTypeMigrationByName`, `simulateResultTypeMigrationByName` and `simulateAddUnionVariantLikeByName` join their exact-ID forms, and `simulateOperationsByName` accepts every operation kind: the renames, `addFunctionParameter`, `addProductField` (with `fieldType`, since `type` selects the Product), `addCapabilityOperation`, `addRequiredEffect`, `removeRequiredEffect`, `removeProductField` and, unchanged, `resolveMissingArgument`. Node and obligation IDs stay exact, since nodes have no names. `verifyChangeByName` resolves case arguments against the committed snapshot both runs share and `expectedCandidate` against the candidate's declarations, so an expectation may name a type the proposal creates. `commit`'s `allowIncomplete` is documented as the one way to publish a proposal with open obligations and kept.
- **Rename:** `AgentFieldlessUnionVariantEvolutionWorkflow` and its request, review, proposal and commit-result types drop `Fieldless` (`AgentUnionVariantEvolutionWorkflow`, `AgentAddUnionVariantLikeRequest`, …). The wire name `simulateAddUnionVariantLike` and the review kind `fieldlessUnionVariantEvolution` are unchanged, so recorded transcripts and clients keep working; the review kind is a known misnomer to retire with the next review-shape change.

## Reason

Each addition is warranted by a concrete maintenance step an agent could not complete without recreating identities or guessing: adding an operation to a Capability already in use, repairing every reference before a deletion the engine would otherwise reject one issue at a time, recovering a lost proposal handle, and verifying or migrating by name when the surrounding tools already work by name. Each reuses an existing mechanism (exhaustive plans, the semantic diff, the session's proposal registry, the symbolic resolvers) rather than adding a new one, and none changes the snapshot schema or any persisted construct.

## Consequences

- `SemanticOperation` and `AgentOperationIntent` gain `AddCapabilityOperation`; `SemanticDiff` gains `CapabilityOperationsAdded` and `CapabilityImplementationsBound`; `ChangeReviewQuery` counts the owners of bound constructions as affected. Adding an operation to an imported Capability is `ImportedDeclarationModified`. `deleteCapabilityOperation` rejects an operation added in the same batch (`CapabilityOperationCreatedInTransaction`), as `removeProductField` does for a new field.
- `AgentCapabilityOperationIntent` and `AgentCapabilityParameterIntent` move to `AgentWorkflow.fs`, where both the declaration workflow and the new operation intent can use them; their namespace and shape are unchanged.
- `SemanticQuery.references` and the `ReferenceSubject`/`ReferenceOwner`/`ReferenceSite` types are the one implementation behind the wire `references`, `AgentWorkspace.references` and `AuthoringSession.References`; `SemanticQueryError` gains `SubjectNotFound`.
- `AuthoringSessionStatus` gains `PendingProposalCount`; the `status` reply gains `pendingProposalCount`. `AuthoringSession.PendingProposals` and the `proposals` operation are new; `ProposalSummary` in `Session.fs` owns the one-line summaries.
- `nyrwvy_inspect` gains the `dependency`, `proposals` and `references` views and a `target` argument for the last; the tool descriptions of `nyrwvy_commit` and `nyrwvy_request` name `allowIncomplete` and the new operations. The adapters' schemas stay strict.
- `AuthoringSurfaceExtensionTests` covers every item over the JSONL protocol, including the documented JSON shapes of `addRequiredEffect`, `removeRequiredEffect`, `resolveMissingArgument` and `renameType`; the "does not implement" sentences of the type, effect and capability declaration specifications now say what later slices added.

## Deferred: a plain `addUnionVariant`

`simulateAddUnionVariantLike` keeps every `MatchUnion` exhaustive by copying or joining the source variant's arm. A plain `addUnionVariant` with arbitrary fields needs another way to make existing exhaustive matches whole, and none of the existing mechanisms fits it cleanly, so it is not implemented. The options, for when a program needs it:

1. **Arm recipes in the request:** one `{ matchNodeId, body: <recipe> }` per `MatchUnion` over the Union, with the new variant's fields as pattern slots, rejected as incomplete like `addFunctionParameter` plans. This keeps every snapshot exhaustive and reviewable, but it is a structural workflow of its own (recipes are materialized per match, in each match's lexical scope), not an `AgentOperationIntent`, so it would be a `simulateAddUnionVariant` next to the migrations rather than a `simulateOperations` member.
2. **Missing-arm obligations:** add the variant with no arm and record one obligation per `MatchUnion`, resolved later by a targeted replacement that adds the arm, like missing-argument obligations. This needs a second obligation kind through `Snapshot.Obligations`, readiness, the codecs (a schema version), the validator (a match may be non-exhaustive only while such an obligation is open) and the C# backend (an unmatched variant must fail at run time rather than be unrepresentable), which is a persisted-construct change, not a reuse.
3. **A default arm:** add the variant to a chosen existing arm per match (`{ matchNodeId, joinArm: [variants] }`), sharing that arm's body as a shared arm already does. This fits the current engine exactly but only when the chosen arm binds no fields of the new variant, and it silently gives the new variant another variant's behavior, which is the review hazard the "like" operation avoids by making the copy explicit.

Option 1 is the recommended design when the need arrives; option 3 is a small extension of the "like" operation (`sourceVariant` per match instead of once) if the uses turn out to be field-free.

## Revisit conditions

- A Capability's operation needs removing and re-adding with a changed parameter list in one publication; today that is a migration for types and a delete-plus-add across two publications for shape.
- `references` is used on programs large enough that one request per subject is too slow or too large; it would then page or take several subjects.
- A client needs the `fieldlessUnionVariantEvolution` review kind renamed; do it together with the next change to that review's shape.
- A program needs a plain `addUnionVariant`; implement option 1 above.
